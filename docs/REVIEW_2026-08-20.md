## 1. 지금 잘 되어 있는 것

고칠 것을 말하기 전에, 무너뜨리면 안 되는 것을 먼저 짚는다.

**단일 경로 — 같은 규칙을 두 번 쓰지 않는다.**
AI가 만든 문제를 승인할 때 별도 등록 로직을 두지 않고, 관리자가 손으로 등록하는 것과 똑같은 문을
지나가게 했다. "AI 문제만 규칙이 어긋난 채 들어오는" 사고가 구조적으로 불가능해진다. 초안이 들어오는
입구가 둘(버튼·배치 파일)로 갈렸을 때도 검증을 한 곳으로 모았다.

```
LlmProblemService.approve()   → AdminProblemService.create()
LlmProblemService.saveDrafts() ← 관리자 버튼 · 배치 파일 흡수 공용
```

**우아한 저하 — Redis가 죽어도 서비스는 산다.**
요청 제한은 통과시키고, refresh 토큰은 발급을 건너뛰고, 문서 캐시는 DB로 넘어간다. 세 곳이 제각각이
아니라 같은 판단을 공유한다 — 2026-08-20에 로컬 Redis가 실제로 끊겼을 때 앱이 멀쩡히 돌아간 것이 증거다.

**주석에 "왜"가 남아 있다.**
대부분의 주석이 무엇을 하는지가 아니라 왜 그렇게 했는지, 무엇을 버렸는지를 적고 있다. 6개월 뒤에
읽어도 판단을 복원할 수 있는 상태이고, 이 프로젝트의 목적(학습·면접)에 정확히 맞는다.

## 2. UI · UX

제품이 내건 약속은 "매일 조금씩"이다. 매일 하는 행동이 어디서 일어나는지를 기준으로 봤다.

### 2.1 매일 쓰는 앱인데 모바일 대응이 분기 하나 (가장 큰 격차)

CSS 488줄에 미디어 쿼리가 `max-width: 560px` 하나뿐이고, 그 안에서 하는 일도 여백·글자 크기 축소와
네비게이션 정리가 전부다. 습관을 만드는 제품에서 습관은 폰에서 생긴다. 퀴즈 플레이어의 보기 버튼 크기,
데일리 진행 바, 복습 카드가 좁은 화면에서 어떻게 보이는지가 이 제품의 핵심 화면인데 지금은 데스크톱
레이아웃을 줄여 쓰는 수준이다.

- 근거: `css/style.css:476` — 파일 전체에서 유일한 미디어 쿼리
- 제안: 플레이어·데일리·복습 세 화면만 모바일 우선으로 다시 잡으면 전체를 손대지 않고도 체감이 크게 달라진다.

### 2.2 aria 속성이 한 곳도 없다

사용자 화면 9개 전부에서 `aria-`로 시작하는 속성이 0건이다. 퀴즈 플레이어는 키보드 조작(숫자키 선택·
엔터 제출)을 잘 지원하는데, 화면 낭독기 사용자에게는 지금 몇 번 문제인지, 답이 맞았는지가 전달되지
않는다. 키보드까지 해 둔 상태라 나머지 절반이 아까운 자리다.

- 근거: `player.js:59` Enter 제출·숫자키 선택 구현됨 / `static/*.html` aria-* 0건
- 제안: 채점 결과 영역에 `aria-live="polite"`, 보기 목록에 `role="radiogroup"` 정도면 대부분 해결된다.

### 2.3 오답노트와 복습이 사용자에겐 같은 것으로 보인다

코드 주석에는 "오답노트=기록, 복습=할 일"로 역할이 분명히 갈려 있다. 그런데 홈에서는 두 카드가 나란히
놓여 있고, 둘 다 "내가 틀린 문제"를 보여준다. 오답노트가 복습 단계 배지를 달아 두 페이지를 잇고 있다는
사실 자체가, 사용자 머릿속에서는 하나라는 신호로 읽힌다.

- 근거: `index.html:39-48` 두 카드 나란히 / `wrong-answers.html:81-87` 복습 배지 → review.html 링크
- 선택지: 합치거나(한 화면 두 탭: "오늘 할 일" / "지난 오답"), 홈에서 오답노트를 복습 화면 안으로
  접어 넣어 대표 메뉴를 하나로 줄인다.

### 2.4 다크 모드가 없다

`prefers-color-scheme`이 0건이다. 색을 전부 CSS 변수로 빼 둔 덕에 `:root` 한 블록만 추가하면 되는
상태라, 비용 대비 효과가 좋은 자리다.

## 3. 기능 합체 · 분리

파일 수가 아니라 "같은 것이 몇 번 반복되는가"와 "한 파일이 몇 가지 일을 하는가"로 봤다.

### 3.1 합체 — 스냅샷 내보내기 4개가 줄 번호까지 같다

가장 확실한 중복이다. 네 클래스의 import 위치, `run()`, 이벤트 리스너, `export()`가 거의 같은 줄에 있다.
다른 것은 "무엇을 조회해 어떤 DTO로 쓰는가"뿐이다. 스냅샷이 하나 늘 때마다 이 150줄이 통째로 복사되고,
규칙이 바뀌면 네 곳을 같이 고쳐야 한다.

| 클래스 | 줄 수 | 공통 구조 |
|---|---|---|
| `ExistingQuestionsExporter` | 176 | ApplicationRunner + AFTER_COMMIT 리스너 + 비교 후 변경 시에만 쓰기 |
| `ExistingDocumentsExporter` | 164 | 〃 |
| `RejectionNotesExporter` | ~150 | 〃 |
| `TopicQueueExporter` | 157 | 〃 |

제안: "무엇을 뽑을지"만 다른 전략으로 보고, 공통 뼈대(언제 도는가·어디에 쓰는가·바뀌었을 때만 쓰기)를
한 곳으로 모으면 약 650줄이 절반 이하가 된다.

### 3.2 분리 — 한 클래스가 1,085줄

`DraftGeneratorCli`가 프로젝트 최대 클래스이고 2위와도 차이가 크다. 배치 진행 순서, 날짜 주기 계산,
파일 쓰기, 생성 결과 품질 경고가 한 파일에 같이 있다. GitHub Actions에서만 돌아 눈에 잘 안 띄는
코드일수록 쪼개 둘 값이 크다.

```
llm/cli/DraftGeneratorCli.java        1,085줄
llm/client/ClaudeProblemGenerator       667줄
llm/client/ClaudeDocumentGenerator      547줄
```

### 3.3 분리 — AI 검수 화면에 흐름이 둘

`admin/llm.html`이 671줄로 관리 화면 중 가장 크고, 문제 검수와 문서 검수를 함께 담고 있다. 예전에
1,417줄짜리 `admin.html`을 다섯 페이지로 쪼갠 전례가 그대로 적용되는 자리다. 다만 "오늘 들어온 것을
한 번에 처리한다"는 검수의 성격상 지금 구조에도 근거가 있어, 크기만으로 밀어붙일 문제는 아니다.

### 3.4 경계 — LLM 패키지가 전체의 36%

149개 중 53개가 `llm` 아래에 있다. 학습 제품(퀴즈·복습·데일리·문서)을 다 합친 것보다 콘텐츠를 만들어
내는 파이프라인이 크다. 나쁘다는 뜻은 아니다 — 이 프로젝트에서 가장 어려운 일이 거기 있으니 자연스러운
결과다. 다만 이 덩어리는 **웹앱과 수명주기가 다르다**: CLI로 돌고, GitHub Actions가 부르고, 배포 주기도
다르다. 별도 Gradle 모듈로 떼면 웹앱이 Anthropic SDK에 의존하지 않게 되고 기동 시간과 이미지 크기가
함께 줄어든다. 지금 당장 필요한 일은 아니다.

## 4. 효율화

실제로 측정됐거나 코드에서 횟수를 셀 수 있는 것만 적었다.

### 4.1 배지 하나 그리려고 API를 최대 20번 부른다 (즉시 고칠 것)

오답노트가 열릴 때마다 복습 현황 전체를 50개씩 **순차로** 최대 20페이지 받아 온다. 그것도 목록을 그리기
**전에** 기다린다. 화면에 필요한 건 지금 페이지 20개 문제의 복습 단계뿐인데, 내 복습 항목 1,000개를 다
받아 오는 셈이다. 문제를 풀수록 홈이 아니라 오답노트가 먼저 느려진다.

```js
// wrong-answers.html:67-77
for (let p = 0; p < 20; p++)
  await api(`/api/me/reviews?size=50&page=${p}`);   // 순차 · 블로킹
// wrong-answers.html:142
loadReviewMap().then(load);                          // 첫 렌더를 막는다
```

제안: `problemIds`를 받는 조회를 하나 열어 1회로 줄이거나, 목록을 먼저 그리고 배지를 나중에 채운다.
지금 순서는 "깜빡임을 막으려고" 택한 것인데, 20회 왕복은 깜빡임보다 비싼 대가다.

### 4.2 자유 퀴즈가 `ORDER BY RAND()`로 뽑는다 (이미 측정됨)

성능 실험에서 이미 15배 차이를 직접 재 뒀다(docs/08). 문제가 수백 개인 지금은 문제가 아니지만, LLM
배치가 매일 문제를 쌓는 구조라 이 숫자는 **단조롭게 증가**한다. 알고 있는 폭탄이라 언제 터질지도 계산할
수 있는, 드물게 편한 상황이다.

- 근거: `ProblemRepository.java:37-45`
- 제안: 지금 고치기보다, 문제 수 임계치를 정해 두고 대시보드에 그 수를 띄워 두는 편이 낫다.

### 4.3 일괄 승인이 50건이면 파일을 100번 다시 쓴다

일괄 승인은 건마다 트랜잭션을 끊는데, 커밋마다 스냅샷 내보내기 2개가 깨어난다. 부분 성공을 얻는 대가로
치른 것이고 상한을 50건으로 묶어 뒀지만, 마지막 한 번만 쓰면 되는 일이다. 일괄 처리 중에는 이벤트를
모았다가 끝에 한 번만 내보내면 된다. 지금 당장은 상한 50건이 충분한 방어다.

### 4.4 Redis 캐시가 문서 1건 조회에만 쓰인다

Redis는 요청 제한과 refresh 토큰에 잘 쓰이고 있지만, 캐시로는 개념 문서 상세 하나뿐이다
(`DocumentService.java:53`). 자주 읽고 드물게 바뀌는 것 — 도메인별 통계 뷰, 개념 문서 목록 — 이
캐시를 안 쓰고 있다.

## 6. 확인했지만 문제가 아니었던 것

지적하려다 실제로 열어 보고 접은 항목이다. 이미 처리돼 있으니 손대지 말 것.

- **N+1** — 퀴즈·복습 목록이 보기(choice)를 지연 로딩해 N+1이 날 자리인데,
  `default_batch_fetch_size: 100`이 이미 걸려 있어 추가 쿼리 1번으로 끝난다.
- **표 레이아웃** — 관리 화면 표가 좁은 화면에서 깨질 줄 알았는데
  `.table-wrap { overflow-x: auto }`가 네 페이지 모두에 적용돼 있다.
- **Flyway 결번** — 마이그레이션 번호가 V1 다음 V4로 뛰어 이력이 어긋날까 싶었지만, 실제 DB의
  `flyway_schema_history`를 조회해 보니 결번 없이 깨끗하다. 콘텐츠 시드를 걷어낼 때 DB를 다시 만든 덕이다.
- **키보드 조작** — 퀴즈 플레이어는 숫자키로 보기를 고르고 엔터로 제출하는 조작이 이미 구현돼 있다.
