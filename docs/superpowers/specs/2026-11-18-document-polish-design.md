# 개념 문서 윤문 단계 추가 설계

claude.ai 대화(2026-11-18)에서 정한 내용이다. 구현 전에 이 문서와 `docs/28-content-flow.md` 4장을 먼저 읽는다.

## 왜 추가하는가

- 문서가 "읽을 만해야" 한다. 지금은 생성 프롬프트(`prompts/document/*-system.txt`, 약 390줄·14개 절) 한 번에 정확성과 문체를 함께 요구한다.
- 성격이 다른 두 일을 한 호출에 몰면 둘 다 어중간해진다. 생성은 내용, 윤문은 문장으로 나눈다.

## 최종 순서 (`DocumentBatch.generateDocument`)

| 단계 | 하는 일 | 지금과 비교 |
|---|---|---|
| 1 | 입문편 생성 → 심화편 생성(윤문 전 입문편 첨부) | 그대로 |
| 2 | **원본 저장** | 그대로 유지한다. 윤문 중 job이 죽어도 생성 비용을 날리지 않는 안전장치다 |
| 3 | 두 편 윤문. **동시 제출** | 신설 |
| 4 | 보존 대조 + 형식 검사(코드). 통과한 편만 윤문본으로 교체 | 신설. 형식 검사(`reportDraftChecks`)는 윤문 뒤로 옮긴다 |
| 5 | 두 편 사실 검수. **동시 제출** → 지적 덧붙여 저장 → 사용 표시 | 지금은 입문·심화를 순차로 2회 부른다 |

- 교체 저장은 `attachFactFindings`처럼 임시 파일에 쓴 뒤 바꿔 끼운다.
- 사실 검수 목적은 "나가기 전 사실 오류만 잡기"다. 윤문 전 사실 검수는 두지 않는다.

## 시간 제한

- `ClaudeCalls.BATCH_DEADLINE` 45분, 워크플로 `timeout-minutes: 300`.
- 순차 단계는 생성 2 + 윤문 1 + 사실 검수 1 = 4개로 유지한다.
- `ClaudeCalls`의 Batch 제출은 요청 1건 전용(`customId "only"`)이다. 여러 건 묶음 제출을 새로 만들지 말고, 두 편 호출을 **동시에** 제출해 같은 효과를 낸다.

## 보존 대조 (코드)

윤문 전후에 아래가 같아야 한다. 하나라도 다르면 그 편은 원본을 유지한다.

| 대상 | 이유 |
|---|---|
| 소제목 | 문제 해설이 "입문편의 ○○ 절"로 가리킨다 |
| 수치 | 의미 변화를 잡는 가장 싼 방법 |
| 코드 블록·그림 블록·링크 | 윤문이 건드릴 대상이 아니다 |
| `용어 한눈에` 표의 용어 | 용어 통일 |
| 조건어(기본적으로·대부분·~인 경우 등) | 빠지면 참이지만 과장된 문장이 된다. 사실 검수가 못 잡는 영역 |

## 윤문본 채택 기준

- 원본에 없던 형식 경고가 윤문본에 **새로 생기지 않을 때만** 채택한다. 원본에도 경고가 흔해 "통과"는 기준이 될 수 없다.
- 차단 항목이 하나라도 새로 생기면 원본 유지.
- 응답이 `MAX_TOKENS`에서 잘리면 대조 실패로 본다. 윤문은 문서 전체를 다시 출력하므로 생성과 같은 64,000을 쓴다.

## 실패 처리

- 윤문 호출 실패·시간 초과·대조 실패는 모두 원본 유지, job은 계속 진행한다.
- 요약 화면(`appendToStepSummary`)에 편마다 "윤문 적용 / 원본 유지(사유)" 한 줄을 남긴다.

## 파일 형식

- 원본 본문을 `GeneratedDocumentItem`에 새 필드로 둔다(이름은 구현 때 정한다). 기존 파일은 이 필드가 없으므로 null을 허용한다.
- **주의:** `DocumentBatch`·`SourceDocumentFinder`는 `JsonMappers.STRICT`로 읽는다. 레코드에 필드를 정식으로 추가하지 않으면 1~3일차 문제 배치가 파일을 못 읽는다.
- 문제 배치가 근거로 읽는 `contentMd`는 윤문본이어야 한다(`SourceQuoteRule` 인용이 맞으려면).

## 윤문 프롬프트

- `prompts/document-polish/system.txt` 신설. 지시는 "내용은 그대로, 문장만 고친다".
- 생성 프롬프트의 `[문체]` `[덜어낼 것]` `[강조와 줄바꿈]` `[절과 절을 잇는다]` 중 세부 문장 다듬기는 윤문 프롬프트로 옮긴다. 종결어미·용어 규칙은 생성 쪽에도 남긴다. 원본이 너무 거칠면 윤문이 많이 고쳐 의미가 바뀔 위험이 커진다.
- 기준은 `docs/WRITING_STYLE.md`와 `humanize-korean` 스킬의 패턴 목록을 쓴다.

## 설정과 평가

- `llm.generation.polish-enabled` 설정을 둔다. 기본은 꺼 둔다.
- 켜기 전에 `eval-samples/documents` 4편으로 윤문 전후의 사실 지적 수, 형식 경고 수, 대조 실패율을 비교한다.
- 결과에 따라 프롬프트를 고친다. 순서는 다시 바꾸지 않는다.

## 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| 문제의 질문·보기 윤문 | 정답이 바뀔 수 있다 |
| 윤문 전 사실 검수 | 지적은 사람이 보는 표시일 뿐이라 최종본 1회로 충분하다 |
| 문단 단위 선별 윤문 | 가독성 지표가 먼저 있어야 한다. 첫 구현은 전체 윤문 |
