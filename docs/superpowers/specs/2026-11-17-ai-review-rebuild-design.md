# 문제 AI 검수 다시 짜기 설계

2026-11-17. 객관식 문제 검수를 "풀이"와 "편집" 두 호출로 다시 짠다.
이 문서는 `2026-11-16-explanation-review-design.md`와 그 구현 계획을 대신한다. 해설 기준표는 그 문서의 것을 그대로 쓴다.

## 왜 다시 짜는가

지금 검수는 단계가 많은데, 효과가 확인된 단계는 둘뿐이다.

| 지금 단계 | 실제 결과 |
|---|---|
| AI B: 정답을 모른 채 문서를 보고 풀기 | 정답 오류를 잡는다. 측정에서 심은 오류 5/7 적발 |
| 고친 문장을 붙인 제안 | 보기 단서 누설 제안 21건이 모두 받아들여졌다 |
| 고칠 글 없이 지적만 내기 | 28건 중 27건이 고쳐지지 않은 채 승인됐다 |
| AI 난이도 판정 | 9건 중 4건이 헛경보였다 |
| AI A: 보기만 보고 단서 찾기 | 코드의 길이 1.3배 규칙과 겹친다. 그 규칙에 걸린 문제만 A를 부른다 |
| AI C: 다 푼 뒤 해설 대조·고친 문장 | 해설은 "정답과 반대로 말하는가"만 본다. 문서를 받지 않는다 |

검수를 엮는 코드도 두 벌이다. 배치(`DraftGeneratorCli`)와 관리 화면(`LlmProblemService`)이 따로 엮어서 문서 지적 연결이 관리 화면 경로에서 빠졌다.

사용자는 해설을 이 서비스의 핵심 가치로 본다. 그런데 지금은 해설을 깊게 보는 단계가 없다.

## 목표

- 검수 호출을 둘로 줄인다. **풀이**는 정답이 맞는지 보고, **편집**은 고친 글을 만든다.
- 지적에는 늘 고친 글을 붙인다. 고칠 글이 없는 지적은 정답·근거 결함일 때만 낸다.
- 해설과 오답 설명은 AI가 고쳐 초안에 직접 넣는다. 질문과 보기는 고친 안을 제안으로만 붙인다.
- 배치와 관리 화면이 같은 검수 입구 하나를 쓴다.
- 쓰지 않는 코드를 지운다.

## 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| AI가 질문·보기·정답을 직접 고치기 | 질문이나 보기가 바뀌면 정답이 바뀔 수 있다. 다시 풀어 확인하려면 호출이 하나 더 든다 |
| AI 난이도 판정 | 헛경보가 절반이다. 난이도는 생성 때 정한 값을 믿는다 |
| 자동 승인·자동 거절 | 승인은 사람이 한다. 고쳐진 초안도 일괄 승인에 그대로 둔다(2026-11-16 결정) |
| 이미 승인된 문제 다시 검수하기 | 대기 중인 초안만 다룬다 |
| 문서 사실 검수 바꾸기 | 심은 오류 21/21을 잡았다. 그대로 둔다 |
| 코드 문제 검수(`ClaudeCodeProblemReviewer`) 바꾸기 | 흐름이 달라 이번에는 두고, 이 설계가 자리 잡은 뒤 맞춘다 |
| 문서·문제 수정 API에 검사 붙이기, 문제 PUT의 documentSlug 버그 | 검수와 따로 고칠 일이다. 이 작업 뒤에 한다 |

## 고른 방법

| 방법 | 장단점 | 결정 |
|---|---|---|
| ① 풀이 + 편집, 두 번 부르기 | 정답을 모르고 푸는 객관성을 지킨다. 지적마다 고친 글이 붙는다. 편집이 문서에 없는 내용을 넣을 수 있어 코드 재검사가 꼭 있어야 한다 | **고름** |
| ② 한 번에 풀고 고치기 | 가장 싸다. 정답을 보고 풀게 되어 틀린 정답을 믿기 쉽다 | 버림 |
| ③ AI 검수 빼기 | 요금이 0원이다. 정답·해설 오류를 사람이 모두 찾아야 한다 | 버림 |

## 흐름

```
생성 → 코드 검사(버릴 것은 버림, 나머지는 경고) → 저장
     → 풀이: 정답 가린 채 문서를 보고 푼다
     → 편집: 정답을 알고 문서·풀이·코드 경고를 보며 고친 글을 만든다
     → 코드 재검사
         해설·오답 설명: 통과하면 넣고, 옛 글은 지적에 남긴다. 실패하면 제안으로 남긴다
         질문·보기: 늘 제안으로 남긴다(검수함에서 눌러 적용)
     → 문서 사실 지적 연결(코드)
     → 초안·결과 파일 갱신 → 검수함 → 사람이 승인
```

배치와 관리 화면은 이 흐름을 한 입구로 부른다.

```java
// 새 입구. 배치 CLI와 LlmProblemService가 같이 쓴다
ProblemReviewPipeline.review(List<GeneratedProblemItem> problems, SourceDocument source,
                             List<FactCheckFinding> facts) -> Reviewed(problems, findings)
// facts: 문서 파일에 실린 사실 검수 지적. 관리 화면 경로처럼 없으면 null
```

관리 화면은 지금처럼 초안을 먼저 저장한다. 그래야 검수(30초~1분) 중에 앱이 꺼져도 요금을 낸 생성 결과가 남는다. 검수가 끝나면 `Reviewed.problems`로 저장한 초안의 해설·오답 설명을 고쳐 다시 저장한다.

### 1. 코드 검사

| 구분 | 할 일 |
|---|---|
| 버리는 규칙(`ProblemItemRule.defectOf`) | 그대로 둔다 |
| 경고 규칙 | 그대로 둔다. 생성 요약(`YieldReporter`)과 검수함(`checksOf`)이 이미 같은 함수(`qualityWarningsOf`)를 부른다 |
| 해설 형식 | 새 `ExplanationFormRule`(A4·B1·B3·B5·C2·C4)이 맡는다. `ProblemItemRule`의 해설 길이·절 안내·오답 설명 길이 경고는 이것으로 옮긴다 |
| 경고의 쓰임 | 편집 호출에 "코드가 찾은 문제"로 넘긴다. 편집이 고친 뒤 다시 돌려 사라졌는지 본다 |
| 단서 경고 세 개 | 지운다. "정답이 가장 긴 보기(1.3배)", "정답이 질문을 되풀이함", 묶음의 "정답이 가장 긴 문항 몰림"이다. AI의 문장 비교·길이 판정과 같은 근거라 믿기 어렵다(사용자 결정, 2026-11-17). 생성 프롬프트의 보기 길이 지침은 둔다 |

해설 형식 규칙은 켜기 전에 승인된 문제 654개에 돌려 헛경보 비율을 잰다. 요금은 들지 않는다. 사람이 이미 통과시킨 해설을 절반쯤 건다면 해설이 아니라 규칙이 틀린 것이니, 규칙을 고친다.

### 2. 풀이 호출

지금 B를 줄여 쓴다. 보기를 섞고 정답 표시와 해설을 가리고 근거 문서를 준다. 사고 과정(thinking)을 켠다.

| 칸 | 뜻 | 지금 B와 견주면 |
|---|---|---|
| `answerReason`, `chosenNo` | 직접 푼 이유와 고른 보기 | 그대로 |
| `otherCorrectNo`, 이유 | 정답으로 방어할 수 있는 다른 보기 | 그대로 |
| `supportQuote` | 정답을 받치는 문서 문장, 글자 그대로 | 그대로. 코드가 원문과 대조한다 |
| `answerInQuestionQuote` | 질문 안에 정답이 그대로 적혀 있으면 그 구절을 글자 그대로. 아니면 빈 문자열 | `revealReason`을 좁혔다. 코드가 그 구절이 질문에 있는지 대조한다 |

뺀 칸은 이렇다.

- 난이도 관찰 셋(`asksDefinition`·`conditionQuote`·`elsewhereCount`)과 의견 넷(`awkwardQuote`·`awkwardFix`·`readabilityNote`·`overallNote`).
- 문장 비교·길이·말투로 단서를 찾는 판정. 사용자가 검수해 보니 엉터리였다(2026-11-17). 질문에 정답이 그대로 적힌 경우만 남긴다.

### 3. 편집 호출

정답을 아는 호출이라 보기를 섞지 않는다. 사고 과정은 끈다(측정 뒤 바꿀 수 있다).

- 입력: 근거 문서, 문제(질문·보기·표시된 정답), 해설, 오답 설명, 풀이 결과, 코드 경고.
- 풀이가 다른 보기를 고른 문제는 편집에 넘기지 않는다. 정답부터 의심스러운 문제의 해설을 고치면 틀린 정답을 굳힌다. 이 문제에는 "정답 의심" 결함만 붙인다.
- 문제마다 할 일:
  1. 해설·오답 설명을 기준표(A1~C4)로 보고, 걸린 기준과 걸린 문장 인용을 적는다.
  2. 걸린 기준이 있으면 고친 해설 전체와 고친 오답 설명(걸린 보기만)을 낸다.
  3. 풀이가 `answerInQuestionQuote`를 냈으면, 그 구절을 걷어 낸 고친 질문을 하나 낸다. 뜻과 정답은 그대로 둔다.
- 지킬 것: 정답과 보기 뜻은 그대로 둔다. 근거 문서에 없는 사실을 더하지 않는다. 해설은 생성 프롬프트 `[해설]`·`[오답 설명]` 절의 꼴을 따른다.

### 4. 코드 재검사

| 고친 것 | 넣는 조건 | 못 넘으면 |
|---|---|---|
| 해설 | `ExplanationFormRule` 통과, 원래와 다름, "그래서" 줄이 정답 보기 글의 낱말을 담음 | 제안으로 남긴다 |
| 오답 설명 | 정답이 아닌 실제 보기, 30자 이상, 원래와 다름 | 버린다 |
| 보기·질문 | 넣지 않는다. 늘 제안이다. `defectOf`를 통과한 안만 붙인다 | 버린다 |
| 걸린 문장 인용 | 해설·오답 설명에 글자 그대로 있어야 근거로 싣는다 | 그 근거만 버린다 |

### 5. 지적

종류를 셋으로 줄인다.

| 등급 | 뜻 | 종류 |
|---|---|---|
| 결함 | 사람이 반드시 봐야 한다. 고칠 글이 없다 | 정답 의심, 정답이 둘일 수 있음, 문서에 근거 없음, 근거 문단에 사실 지적, 자료 어긋남 |
| 고쳐 넣음 | AI가 고쳐 넣었다. 옛 글이 detail에 있다. 처리된 것으로 저장한다 | 해설 고침, 오답 설명 고침 |
| 제안 | 고친 안이 붙어 있다. 검수함에서 눌러 적용한다 | 질문에 정답이 적힘, 해설 고친 안(재검사 실패) |

옛 종류(`DIFFICULTY_MISMATCH`, `AWKWARD_SENTENCE` 등)는 enum에 남겨 둔다. 승인된 문제 654개와 대기 초안의 저장된 지적을 읽을 때 필요하다. 새 코드는 만들지 않는다. 코드 문제 검수가 쓰는 종류(`CODE_COMMENT_REVEALS` 등)도 그대로 둔다.

### 6. 검수함

- 해설이 고쳐진 초안에 "AI가 해설을 고침" 표시를 단다.
- 지적을 펼치면 옛 글과 새 글을 나란히 보여 준다.
- 제안은 지금처럼 버튼으로 적용한다(`apply-suggestion`).

### 실패했을 때

| 실패 | 처리 |
|---|---|
| 풀이 호출 | 편집도 부르지 않는다. 코드 경고만 붙이고 초안은 그대로 저장한다 |
| 편집 호출 | 풀이 결함 지적은 살리고, 고친 글은 없다 |

지금 배치와 같은 원칙이다. 요금을 낸 생성 결과를 검수 실패 때문에 버리지 않는다.

## 재기

병합 전에 `evalProblemReview`로 잰다. 작업은 작업용 브랜치에서 하고 문턱을 넘으면 main에 합친다. 그래야 측정하지 않은 검수가 매일 배치에서 돌지 않는다.

1. 지금 표본(`eval-samples/problem-review.json`)으로 정답 결함 적발률이 지금(5/7) 아래로 떨어지지 않는지 본다.
2. 해설 결함을 심은 표본을 더한다. 기준마다 1~2개, 멀쩡한 문제 10개를 섞는다.
3. 고친 해설이 원래 정답과 문서 사실을 지켰는지 사람이 읽는다.

문턱은 적발률 80% 이상, 멀쩡한 문제 열 개에 헛경보 두 건 이하다. 측정 1회는 요금이 들어 돌리기 전에 횟수와 비용을 묻는다.
