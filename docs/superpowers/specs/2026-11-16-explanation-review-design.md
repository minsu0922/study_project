# 해설 검수 강화 설계

> 2026-11-17: 이 문서는 [문제 AI 검수 다시 짜기 설계](../specs/2026-11-17-ai-review-rebuild-design.md)로 대신했다. 해설 기준표만 그쪽이 가져다 쓴다.

2026-11-16. 문제 검수(docs/22)에 해설 품질 검수를 더하고, AI가 고친 해설을 초안에 직접 넣는다.

## 왜 하는가

해설은 이 서비스의 핵심 가치다(생성 프롬프트 `[해설]` 절). 학습자는 문제를 틀린 직후 해설과 오답 설명을 읽고 개념을 바로잡는다.

지금 해설을 깊게 보는 단계가 없다.

| 단계 | 지금 하는 일 |
|---|---|
| 생성 | 프롬프트 지침, 코드 검사(150~700자 경고, 보기를 번호로 가리키면 버림) |
| AI 검수 C(`after-solve`) | 해설이 정답·검수자 풀이와 반대로 말하는지만 본다. "덜 자세한 것은 어긋남이 아니다"로 넘기고, 해설을 고치지 않는다 |

11-16에 문제 55개를 손으로 대조했을 때 해설 결함이 실제로 있었다. 근거 문서와 다른 편의 절을 가리켰고(48455·48457), 지문에 없는 "VPN"이 해설에 나왔다(48444).

지적만 내면 고쳐지지 않는다는 실측도 있다. 10-07~12에 지적 28건 중 27건이 고쳐지지 않은 채 승인됐다. 고친 문장을 붙인 보기 단서 누설은 21건이 모두 받아들여졌다(docs/22 §6).

## 목표

- 해설과 오답 설명을 아래 기준표(A·B·C)로 검수한다.
- 기준에 걸린 해설과 오답 설명은 AI가 고쳐 초안에 직접 넣는다.
- 옛 글은 지적에 남겨, 승인하는 사람이 무엇이 바뀌었는지 본다.
- 코드로 셀 수 있는 기준은 코드가 생성 직후(1차)와 고친 뒤(재검사) 두 번 본다.

## 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| 질문·보기·정답을 AI가 직접 고치기 | 정답이 바뀌면 문제 전체가 틀린다. 지금처럼 제안만 둔다 |
| 생성 직후 AI 자기 검토 호출 | 사용자가 1차는 코드 검사만 두기로 정했다(요금 없음) |
| 자동 승인·자동 거절 | 승인은 사람이 한다(docs/22 §8) |
| 이미 승인된 문제 고치기 | 대기 중인 초안만 다룬다 |
| 코드 문제(`ClaudeCodeProblemReviewer`) | 해설 형태와 검수 흐름이 달라 따로 다룬다 |
| D1 문체를 고치기 | 의견으로만 남긴다. 문체 다시 쓰기는 뜻이 바뀔 위험이 크다 |
| 문서·문제 품질 검수 | 해설 다음 순서로 따로 설계한다 |

## 기준표

등급의 결함·다듬기·의견은 지금의 `ProblemReview.Grade`와 같다. A·B·C에 걸리면 고친다.

| # | 기준 (아니오면 걸림) | 보는 쪽 | 등급 |
|---|---|---|---|
| A1 | 해설이 표시된 정답을 정답으로 설명하는가 | AI | 결함 |
| A2 | 해설·오답 설명의 사실이 근거 문서·검수자 풀이와 맞는가 | AI | 결함 |
| A3 | 예시 속 계산과 값이 맞는가 | AI | 결함 |
| A4 | 다시 읽을 절이 그 편 문서에 실제로 있는가 | 코드 | 결함 |
| B1 | "규칙:"으로 시작하고, 그 규칙이 이 문제의 정답이 기대는 원리인가 | 시작은 코드, 내용은 AI | 다듬기 |
| B2 | 처음 나온 용어를 그 자리에서 풀었는가 | AI | 다듬기 |
| B3 | 예시가 구체적인 값으로 한 걸음씩 가는가(걸음 3줄 이상) | 줄 수는 코드, 값은 AI | 다듬기 |
| B4 | 지문에 상황이 있으면 그 상황을 예시로 썼는가 | AI | 다듬기 |
| B5 | "그래서"로 정답을 확인하며 맺는가 | 코드 | 다듬기 |
| B6 | 순서 문제면 흔히 뒤바꾸는 두 단계를 짚었는가 | AI | 다듬기 |
| C1 | 해설이 오답을 하나씩 설명하지 않는가 | AI | 다듬기 |
| C2 | 오답 설명마다 무엇과 헷갈렸는지 밝혔는가(30자 이상) | 길이는 코드, 내용은 AI | 다듬기 |
| C3 | 오답 설명이 다른 보기를 가리키지 않고 혼자 읽혀도 통하는가 | 번호는 코드, 내용은 AI | 다듬기 |
| C4 | 150~700자이고 같은 말을 되풀이하지 않는가 | 길이는 코드, 되풀이는 AI | 다듬기 |
| D1 | 번역투·흐린 말투 없이 쉬운가(WRITING_STYLE 3절) | AI | 의견 |

## 고른 방법

| 방법 | 장단점 | 결정 |
|---|---|---|
| 1. 기존 C 호출을 넓힘 | 요금이 거의 늘지 않는다. C는 문서를 받지 않아 A2·A3를 문서와 대조하지 못하고, 문제 5개의 고친 해설을 한 응답에 쓰다 뒤쪽이 대충 처리될 수 있다 | 버림 |
| 2. 해설 검수 호출 D를 새로 둠 | 근거 문서와 직접 대조하고 해설에만 집중한다. 묶음마다 호출 하나, 대략 $0.1 안팎이 는다 | **고름** |
| 3. 문제마다 D를 부름 | 가장 꼼꼼하지만 요금이 다섯 배쯤 된다 | 버림 |

사용자가 2번을 골랐다. 해설을 핵심 가치로 보므로 문서와 직접 대조하는 쪽을 택했다.

## 흐름

```
생성 → 코드 1차 검사(해설 형식) → 파일 저장
     → AI 검수 A(보기만) → B(문서와 풀기) → C(다 푼 뒤: 단서·질문 누설 제안)
     → D(해설 검수, 신규): 문서 + 문제 + 정답 + 해설 + 오답 설명 + B 풀이 + 1차 검사 결과
     → 고친 해설·오답 설명을 코드로 재검사
         통과: 문제에 바로 넣는다. 지적에 옛 글을 남긴다
         실패: 원래 글을 둔다. 고친 안을 제안으로 붙인다(검수함에서 눌러 적용)
     → 지적과 함께 결과 파일을 다시 쓴다 → 들여오기 → 검수함 → 사람이 승인
```

### 1차 코드 검사

`ProblemItemRule`에 해설 형식 검사를 더한다. 경고만 내고 문제를 버리지 않는다.
대상은 A4, B1 시작, B3 걸음 줄 수, B5, C2 길이, C4 길이다.

A4는 해설 마지막 줄의 `(○○편의 '절 이름' 절을 다시 읽어 보라)`에서 편과 절 이름을 뽑는다. 근거 문서에 그 이름의 절(`##`·`###`)이 있는지, 편이 근거 문서의 편과 맞는지 본다. 입문편 절을 함께 넘긴 문제(프롬프트의 "같은 주제 입문편에서 가져온 부분")는 입문편 절도 허용한다.

결과는 D에 힌트로 넘기고, 고친 글의 재검사에 같은 코드를 쓴다.

### D 호출

- 입력: 근거 문서, 문제(지문·보기·표시된 정답), 해설, 오답 설명, B의 풀이, 1차 검사 경고.
- B가 표시된 정답을 고르지 않은 문제는 넘기지 않는다. 정답부터 의심스러운 문제의 해설을 고치면 틀린 정답을 굳힌다. 그 문제는 "정답 의심" 지적이 따로 붙는다.
- 보기는 섞지 않는다. C와 같이 정답을 이미 알려 주는 호출이다.
- 응답(문제마다):
  - 걸린 기준 번호 목록과, 기준마다 걸린 문장을 글자 그대로 인용한 근거
  - 고친 해설 전체(걸린 기준이 A·B·C에 있을 때만)
  - 고친 오답 설명(걸린 보기만, 보기 위치와 함께)
  - D1 의견(있을 때만)
- 고칠 때 지킬 것(프롬프트에 적는다): 정답과 보기는 그대로 둔다. 근거 문서에 없는 사실을 더하지 않는다. 생성 프롬프트 `[해설]`·`[오답 설명]` 절의 꼴을 따른다.
- 인용이 원문에 없으면 그 지적은 버린다. 문서 사실 검수와 같은 방식이다.

### C에서 옮기는 것

C의 해설 어긋남 검사(`explanationIssue`)는 D로 옮긴다. 두 곳에서 같은 지적이 나오지 않게 하려는 것이다. C에는 자료 어긋남(`exhibitIssue`)과 단서·질문 누설 제안만 남긴다.

### 지적의 모양

| 지적 | 등급 | 내용 |
|---|---|---|
| 해설 고침(신규) | 다듬기 | message: "AI가 해설을 고쳤다(기준 A2·B3)". detail: 기준마다 근거 인용, 그 아래 옛 해설. 고쳐 넣었으니 A에 걸렸어도 결함으로 세지 않는다 |
| 오답 설명 고침(신규) | 다듬기 | 보기 위치, 근거, 옛 오답 설명 |
| 해설 고친 안(신규) | A가 걸렸으면 결함, 아니면 다듬기 | 재검사를 통과하지 못해 넣지 않은 경우. 지금의 고친 문장 제안(`Suggestion`)으로 붙인다 |
| 문체 의견(신규) | 의견 | D1. 접어서 보여 준다 |

기존 `EXPLANATION_MISMATCH`는 D가 A1·A2에 걸린 문제를 고치지 못했을 때만 쓴다.

### 검수함

- 해설이 고쳐진 초안에 "AI가 해설을 고침" 표시를 단다.
- 지적을 펼치면 옛 해설과 새 해설을 나란히 본다.
- 승인 막기는 하지 않는다. 지금처럼 경고다.
- 해설이 고쳐진 초안도 일괄 승인에 그대로 둔다(사용자 결정, 2026-11-16). 승인 부담을 지금과 같게 두고, 표시와 옛 글 비교로 확인할 길을 준다.

### 실패했을 때

D 호출이 실패하면 앞의 A·B·C 지적은 살리고, 해설은 고치지 않는다. Actions 요약에 실패를 남긴다. 지금 C 실패 처리와 같다.

## 재기

켜기 전에 `evalReview`(docs/22 §4)로 잰다.

1. 승인된 문제에 해설 결함을 심는다. 기준마다 1~2개로, 틀린 계산(A3), 없는 절 안내(A4), 풀지 않은 용어(B2), 값 없는 예시(B3), 다른 보기를 가리키는 오답 설명(C3) 같은 것이다.
2. 멀쩡한 문제도 섞어 헛경보를 센다.
3. 고친 해설이 원래 정답과 문서 사실을 지켰는지 사람이 읽어 본다.

문턱은 docs/22와 같이 잡는다. 적발률 80% 이상, 헛경보는 멀쩡한 문제 열 개에 두 건 이하다. 측정 1회는 요금이 들어 돌리기 전에 횟수와 비용을 묻는다.

## 만드는 사람에게 맡기는 것

이미 정한 것(설계자 판단): D는 생성과 같은 모델로 부른다. 편은 근거 문서 slug가 `-advanced`로 끝나면 심화편, 아니면 입문편으로 본다. 고친 해설을 넣을 때는 결과 파일의 `problems`와 `reviewFindings`를 함께 다시 쓴다.

- D 응답 스키마의 필드 이름과 순서. 이유를 먼저 쓰고 결론을 나중에 쓰는 지금 관례를 따른다.
- 1차 검사의 정확한 문자열 규칙. 예: "걸음 줄"을 어떻게 셀지.
- D 호출에 사고 과정(thinking)을 켤지. B는 켜고 C는 끈다.
- 검수함에서 옛 글과 새 글을 나란히 보여 주는 화면 모양.
