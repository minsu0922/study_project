# 개념 문서 독자 점검과 나란히 검수 화면 설계

2026-11-20 · 상태: 설계 확정 전

## 왜 하는가

배치 개념 문서는 생성 → 윤문 → 보존 대조 → 사실 검수를 거친다. 이 가운데 "독자가 처음부터 끝까지 막히지 않고 따라오는가"를 보는 단계는 없다.
2026-11-20 DNS 두 편으로 시험해 보니(서브에이전트, 요금 없음) 사람이 바로 고칠 만한 빈틈을 13곳 짚었다.

- 입문편 "14시 00분이 지나면…": 앞에서 13시 50분이라 했는데 14시가 나온 까닭이 빠졌다.
- 심화편 "22시 18분에야 오류가 그쳤다": 연결 20개 × 30초 = 10분인데 본문은 8분이다. 사실 검수가 놓쳤다.
- 심화편 CNAME 비유: 입문편이 "수첩(캐시)"과 "장부(권한 서버)"를 따로 세웠는데 CNAME(장부 한 줄)을 수첩에 빗댔다.

또 사람이 검수할 때 지금 검수함은 마크다운 원문을 `<pre>`로 쌓아 보여 준다. 시험 때 쓴 "원문 옆에 지적을 나란히" 화면이 훨씬 읽기 편했다. 사용자는 이 모양을 관리 화면에서도 원한다.

## 목표

1. 배치가 문서마다 독자 점검을 돌려 결과를 배치 파일과 초안에 남긴다.
2. 관리 콘솔에 문서 하나를 넓게 여는 「나란히 검수」 화면을 만든다. 왼쪽은 렌더링한 본문, 오른쪽은 사실 검수와 독자 점검 지적이다.
3. 독자 점검의 고친 문장 제안을 그 화면에서 수락하면 초안 본문에 반영된다.

## 하지 않을 것

- 독자 점검이 글을 스스로 고치기(자동 보강). 고칠 곳 대부분이 설명을 새로 써 넣는 일이라 모델이 지어낼 위험이 크다. 제안까지만 한다.
- 독자 점검 지적이 승인을 막기. 사용자 결정(①안): 참고로만 보이고 처리하지 않아도 승인된다.
- 이미 승인되어 나간 문서에 독자 점검 돌리기. 이번 범위는 배치가 새로 만드는 초안이다.
- 검수함 목록 화면 바꾸기. 목록은 지금처럼 훑어보는 용도로 두고 버튼 하나만 더한다.

## 실패로 칠 것(동작해도 안 되는 것)

- 제안을 수락했는데 본문의 다른 곳까지 바뀌거나, 수치·소제목·코드 블록이 깨진다.
- 나란히 검수 화면이 승인 전 글을 거르지 않고 innerHTML로 넣어 관리 화면에 스크립트가 돈다.
- 독자 점검이 실패했다고 배치 job이나 문서 저장이 실패한다(사실 검수와 같이 문서는 남아야 한다).

## 정해진 것

### 1. 배치 단계 위치

```
생성(입문·심화) → 윤문 → 보존 대조 → 파일 저장 → reportDraftChecks
  → [사실 검수 입문 · 사실 검수 심화 · 독자 점검 입문 · 독자 점검 심화] 네 호출을 동시에
  → 파일에 factFindings · readerFindings를 붙여 다시 저장
```

- 네 호출을 동시에 보내 순차 단계 수는 그대로다(job 300분 한도, 호출당 최대 45분).
- 독자 점검은 윤문이 채택된 판(윤문이 버려졌으면 원고)을 읽는다. 사실 검수와 같은 판이다.
- 설정 `llm.generation.reader-check-enabled`. 키가 없으면 꺼진 것으로 본다(윤문 `polish-enabled`와 같은 규칙). 처음 커밋은 `false`.
- 독자 점검 호출이 실패하거나 응답을 못 읽으면 그 편의 `readerFindings`는 비워 두고(null) 배치 요약에 한 줄 남긴다. job은 계속한다.

### 2. 독자와 프롬프트

시험 프롬프트(이 문서 부록에 원문을 옮겼다)에 아래 다섯 가지를 더해 `src/main/resources/prompts/document-reader/beginner.txt`, `advanced.txt`로 둔다.

| # | 보완 | 내용 |
|---|---|---|
| 1 | 코스 앞 글을 읽은 독자 | 같은 분야 블록에서 이 주제보다 앞에 오고 **이미 문서가 나온(사용 기록이 있는)** 주제 이름 목록을 user 메시지에 싣는다. "독자는 이 글들을 읽었다. 그 글들이 다룬 기본 용어는 안다." `TopicQueue.laterTopicsInBlock`과 짝인 앞쪽 목록을 쓴다. 문서가 아직 없는 앞 주제를 넣으면 독자가 읽지 않은 글을 읽은 것으로 쳐 진짜 막힘을 놓친다(만든 사람 결정) |
| 2 | 되풀이 예외 넓히기 | 「면접에서 이렇게 물어본다」, 장면 첫머리에서 앞 절 결론을 받아 여는 문장, 「실무에서 어디에 나타나는가」 항목을 예외에 더한다 |
| 3 | 수치가 서로 안 맞음 | 짚을 종류에 "본문 안의 수치·시각끼리 계산이 맞지 않는다"를 더한다. 바깥 사실은 사실 검수의 몫이라 뺀다 |
| 4 | 고친 문장 제안 | 지적마다 `suggestion`을 낸다(아래 형식). 본문에 있는 사실로만 쓰고, 없으면 `need_human`과 물음 한 줄 |
| 5 | 비유 무대 | 비유는 문서가 세운 무대를 기준으로 본다. 심화편은 입문편이 세운 비유가 기준이다 |

- 입문편 독자: 개발을 배운 적 없는 중학생. 심화편 독자: 같은 주제 입문편을 방금 읽은 비전공 취업 준비생. 심화편 호출은 입문편 최종본 전문을 함께 싣는다.
- 고친 문장 제안의 문체는 윤문 프롬프트(`document-polish/system.txt`)의 규칙을 따르라고 적는다(평서문, 60자, 비유 알림말, 건드리지 않는 것).
- 모델은 사실 검수와 같은 모델·같은 호출 설정을 쓴다.

### 3. 응답과 저장 형식

모델 응답(편마다 하나):

```json
{"findings":[{
  "kind":"막힘|되풀이",
  "type":"풀지 않은 말|안 잡히는 문장|건너뛴 단계|비유|그림·표|수치 안 맞음|되풀이",
  "weight":"멈춤|멈칫",
  "section":"소제목",
  "quote":"본문 그대로 80자 이내",
  "earlier":"되풀이면 앞에서 읽은 문장, 아니면 빈 문자열",
  "reason":"독자 입장에서 한 문장",
  "suggestion":{"op":"replace|insert_after|delete|need_human","target":"본문 그대로","text":"새 문장","note":"근거나 확인할 물음 한 문장"}
}]}
```

받는 쪽 코드가 거르는 규칙. 맞춰 볼 때는 사실 검수의 `ClaudeDocumentFactChecker.normalize`처럼 강조·백틱 기호를 걷어 낸 글로 비교한다. 모델 인용에서 강조 기호가 자주 빠지기 때문이다(만든 사람 결정).
- `quote`가 그 편 본문에 없으면 지적을 버린다(사실 검수의 `keepQuotedInDocument`와 같은 생각).
- `suggestion.target`이 걷어 낸 글 기준으로 본문에 정확히 한 번 있어야 하고, 그 자리를 마크다운 원문 위치로 되짚을 수 있어야 한다. 아니면 제안만 지우고 지적은 남긴다(`op`를 `need_human`으로 바꾸고 note에 "제안한 문장을 본문에서 찾지 못했다").

배치 파일: `generated/documents/<날짜>.json`에 `readerFindings` 칸을 더한다. 편을 섞지 않게 `{"beginner":[...], "advanced":[...]}`로 둔다. 칸이 없으면 독자 점검을 안 돌린 파일이다. 파일 읽기는 `JsonMappers.STRICT`라 모르는 칸이 있으면 실패하므로, 로컬 앱 코드를 먼저 배포한 뒤 설정을 켠다(윤문 때와 같은 순서).

초안 표: 새 마이그레이션(V49)으로 `generated_document_draft.reader_findings_json TEXT NULL`을 더한다. NULL = 안 돌림, `[]` = 돌렸는데 지적 없음. 흡수(`DocumentImportService`)가 편에 맞는 목록을 넣는다. 원소마다 처리 기록 `resolution`을 둔다: 없음(미처리) / 수락 / 넘김(이유는 적어도 되고 안 적어도 된다).

### 4. 제안 수락

- 새 API `POST /api/admin/llm-documents/{id}/reader-findings/{index}/accept`, `.../dismiss`(본문 `{note}` 선택). 초안이 PENDING일 때만 받는다.
- 수락: `op`대로 초안 `content_md`를 고친다. replace는 target을 text로, insert_after는 target 뒤에 공백 하나와 text를, delete는 target을 지운다(앞뒤 공백 하나 정리). `need_human`은 수락이 없고 넘김만 있다.
- 고치기 전에 target이 지금 본문에 정확히 한 번 있는지 다시 본다. 다른 지적을 먼저 수락해 문장이 바뀌었으면 "제안한 문장이 본문에서 바뀌었다"로 거절한다.
- target이 소제목 줄, 코드·그림 블록 안, 그림 줄, 「글의 주제」·결론 인용 상자 줄, 표 줄에 걸리면 수락하지 않는다. 윤문 「건드리지 않는 것」과 같은 자리다(만든 사람 결정).
- 고친 뒤 문서 검증기(`reportDraftChecks`가 쓰는 검사)를 돌려, 고치기 전에 없던 막는 오류가 생기면 거절한다.
- 본문을 고치면 사실 검수 「고침」과 똑같이 배치 파일도 고친다(`DocumentFileSync.replaceContent`). DB 초안과 배치 파일이 달라지면 문제 배치가 고치기 전 본문을 근거로 쓴다(만든 사람 결정).
- 처리 기록과 본문 변경은 한 트랜잭션이다. 사실 검수 `resolveFactFinding`과 같은 꼴로 만든다.
- 독자 점검은 승인을 막지 않는다. 남은 지적 수만 화면에 보인다.

### 5. 나란히 검수 화면

새 정적 페이지 `src/main/resources/static/admin/doc-review.html?id={초안 id}`. 관리 콘솔의 다른 화면과 같은 쿠키 게이트·상단 띠를 쓴다. 검수함 문서 카드에 「나란히 검수」 버튼을 더해 새 탭으로 연다.

```
┌ 상단: 제목 · slug · 상태 · 검증기 막는 오류/경고 · [승인] [거절] · [원문 보기] ─────┐
├──────────────── 본문(렌더링) ──────────────┬──── 지적 (붙박이, 따로 스크롤) ─────┤
│ ## 1단계 …                                  │ [사실 검수 3] [독자 점검 11] [처리함] │
│ … ①칠한 문장 … ②칠한 문장 …                 │ ① 사실 · 확신 「…」                   │
│ 그림·mermaid·표                             │    이유 / 바로잡으면 / 출처           │
│                                            │    [고침—문단 고치기] [헛경보]        │
│                                            │ ② 독자 · 막힘 · 건너뛴 단계 · 멈칫    │
│                                            │    까닭 / 앞에서 읽은 문장            │
│                                            │    지금: …  제안: …(빨강·초록)        │
│                                            │    [제안 수락] [넘김]                 │
└────────────────────────────────────────────┴──────────────────────────────────────┘
```

- 본문 렌더링: 사이트 `document.html`과 같은 marked + DOMPurify로 거른 뒤 넣는다. mermaid는 관리 화면의 `renderDiagramPreviews`, 그림 줄은 `/images/docs/` 주소 그대로.
- 「원문 보기」는 지금 검수함처럼 마크다운 원문 `<pre>`를 보여 준다. 검증기가 HTML 태그를 막는 오류로 짚은 초안은 처음부터 원문 보기로 연다(렌더링하면 태그가 눈에서 사라진다).
- 칠하기: 지적의 `quote` 자리를 칠하고 번호를 단다. 색은 사실 검수, 독자 막힘, 독자 되풀이로 나눈다. 번호를 누르면 본문과 지적 카드 사이를 오간다.
- 사실 검수 지적의 「고침」·「헛경보」는 지금 검수함의 동작과 API를 그대로 쓴다. 처리하면 화면을 다시 그린다.
- 좁은 화면(900px 아래)에서는 지적이 본문 아래로 내려간다.

### 6. 기록과 비용

- 배치 요약(Actions step summary)에 편마다 "독자 점검 n건(막힘 a · 되풀이 b · 제안 c)" 한 줄.
- `docs/28-content-flow.md` 4장 흐름도와 `docs/22-ai-review.md` 비용 표에 독자 점검을 더한다. 호출은 문서일마다 편당 하나(입문 1, 심화 1)다.

## 방법 비교(사용자가 고른 것)

| 안 | 내용 | 결정 |
|---|---|---|
| A. 검수함 카드 안에서 두 단 | 화면 이동 없음. 폭이 좁고 목록이 길어짐 | 버림 |
| B. 원문 `<pre>`에 칠하기만 | 지금 안전 규칙 그대로. 표·그림이 기호로 보여 덜 읽힘 | 버림 |
| **C. 따로 여는 넓은 검수 화면** | 렌더링한 본문 + 지적 카드. marked + DOMPurify로 거름 | **채택** |

독자 점검이 고치기까지 하는 안(자동 보강)과 승인을 막는 안은 위 「하지 않을 것」에 적은 이유로 버렸다.

## 만드는 사람에게 맡긴 것

- 칠하기 구현 방식(마크다운에 표지를 넣고 렌더링 뒤 바꾸기, 또는 렌더링한 DOM에서 글자 찾기). 표 칸·코드 블록 안 인용도 칠해지면 좋지만 못 찾은 인용은 카드에 "본문에서 위치를 못 찾음"으로 두면 된다.
- 클래스 이름, 패키지 위치, 테스트 이름. 기존 사실 검수(`ClaudeDocumentFactChecker`, `DraftFactFinding`, `FindingList`)의 꼴을 따른다.
- 앞쪽 주제 목록이 비면(블록의 첫 주제) 그 줄을 싣지 않는다.

## 부록: 시험 프롬프트 원문(보완 전)

2026-11-20 DNS 시험에 쓴 그대로다. 위 「2. 독자와 프롬프트」의 보완 다섯 가지를 이 위에 더한다.

### 입문편

```text
너는 이 글의 독자다. 개발을 배운 적 없는 중학생이다.
글을 처음부터 끝까지 한 번 읽는다. 글 밖의 지식은 없고, 앞에서 읽은 것만 안다.
글을 고치지 마라. 읽다가 걸린 곳만 짚는다.

[짚을 것]
A. 막힘 — 읽기를 멈추게 한 곳
  - 풀지 않은 말: 앞에서 뜻을 알려 주지 않은 전문 용어·영어 약자가 나왔다
  - 안 잡히는 문장: 한 번 읽어 뜻이 안 잡힌다. 주어가 없거나, "이·그"가 무엇인지 모르거나, 꾸밈이 겹쳤다
  - 건너뛴 단계: 앞 문장에서 이 결론이 왜 나오는지 모르겠다
  - 비유: 비유가 무엇을 가리키는지 모르겠다. 또는 앞에서 세운 비유와 다른 무대다
  - 그림·표: 보라고 했는데 무엇을 봐야 할지 모르겠다
B. 되풀이 — 이미 읽은 내용을 새 정보 없이 다시 읽은 곳
```
