# 화면 전면 개편 설계 — 사용자 화면 + 관리 콘솔

작성 2026-09-06. 이 문서는 **구현 전 합의문**이다. 실제로 한 일은 끝난 뒤
`docs/20-...`에 따로 남긴다 — 번호 붙은 docs는 완료된 작업의 기록이라는 규칙을 지킨다.

앞선 개편([18](../../18-problem-list-ui.md), [19](../../19-ui-refresh.md))에서 이어진다.
19가 "토큰 두 벌을 한 벌로" 였다면, 이번은 **그 한 벌 위에 앱을 다시 짓는** 작업이다.

---

## 1. 왜 개편하나

"실제로 서비스를 운영한다고 가정"이 출발점이다. 지금 화면은 기능을 하나씩 붙여 온 결과라
네 군데가 어긋나 있다 — 사용자가 직접 꼽은 것들이다.

| 불만 | 지금 상태 |
| --- | --- |
| 보기(시각적 인상) | 토큰은 정리됐지만 타이포·간격·컴포넌트가 화면마다 제각각 |
| 흐름(정보 구조) | 메뉴 4개에 새 화면이 들어갈 자리가 없다. 화면 안 배치도 화면마다 다른 규칙 |
| 관리자 밀도 | 화면 하나가 최대 940줄. 목록·필터·표를 화면마다 새로 짰다 |
| 모바일 | 반응형 규칙이 부분적. 폰에서 상단 가로바가 넘치고 표가 잘린다 |

없는 화면도 문제다. 실서비스라면 **내 기록·설정·소개(랜딩)** 가 있어야 하는데 셋 다 없다.

## 2. 결정과 근거

브라우저 시안을 놓고 하나씩 골랐다. **뒤집힌 결정과 그 이유까지** 남긴다 —
6개월 뒤에 "왜 이걸 골랐지"를 다시 묻지 않기 위해서다.

| # | 결정 | 고른 것 | 근거 |
| --- | --- | --- | --- |
| D1 | 셸 | 데스크톱 좌측 사이드바 + 폰 하단 탭바 5칸 | 화면 13개가 사이드바에는 이름째로 들어간다. 폰에서 아래쪽이 엄지에 닿는다 |
| D2 | 홈 톤 | 옅은 히어로 + 통계 4칸 + 분야별 진도 6개 | 색이 찬 큰 판(진한 히어로)은 매일 오는 사람에게 매일 같은 광고가 된다 |
| D3 | 플레이어 | **셸 유지** (집중 모드 아님) | 사용자 선택. 풀다가 개념 문서로 바로 넘어갈 수 있는 쪽을 택했다 |
| D4 | 다크 모드 | 남색 어둠(`#0b1120` 계열), 이번에 함께 | 라이트가 이미 slate라 같은 눈금을 아래로 잇기만 하면 된다 |
| D5 | 기술 | 순수 CSS + 공용 레이아웃 JS | 빌드 도구 없이 정적 HTML을 유지하되, 셸 마크업 복붙을 없앤다 |
| D6 | 관리 콘솔 | 다른 방 + 상단 진한 띠 | `admin-common.js`에 이미 있는 판단을 유지 (아래 2.1) |
| D7 | 순서 | 사용자 화면 → 관리 콘솔 | 사용자 화면에서 굳힌 틀을 콘솔에 옮긴다 |
| D8 | 새 화면 | 내 기록 · 설정 · 랜딩 | |
| D9 | 설정 범위 | 브라우저에 저장하는 것만 | 비밀번호 변경 API가 없다. 빈 버튼을 두느니 항목을 뺀다 |
| D10 | 활동 격자 | **넣지 않는다** | 사용자 결정. 스트릭을 뺀 것과 같은 맥락 |

### 2.1 되돌리지 않은 결정 둘

기존 코드 주석이 근거를 남겨 둔 판단이 둘 있었고, 둘 다 그대로 뒀다.

- **콘솔에 학습 메뉴를 넣지 않는다** (`admin-common.js` `renderConsoleNav`)
  — "어느 쪽에 있는지 흐려지고, 검수하다 잘못 눌러 나가기 쉽다."
  사이드바를 공유하는 A안이 더 빨랐지만, 이 판단을 뒤집을 새 근거가 없었다.
- **첫 화면은 광고가 아니라 오늘 할 일** (`index.html`)
  — "매일 오는 사람에게 매일 같은 광고를 보여주지 않는다."
  진한 히어로(시안 B)가 이 결정과 부딪혀 옅은 쪽을 골랐다.

### 2.2 사용자가 내 추천과 다르게 고른 것

**플레이어에서 셸을 유지한다(D3).** 나는 집중 모드를 추천했다 —
폰에서 탭바가 먹는 49px이 보기 하나 값어치이고, "10분 집중"이라는 약속과 맞아서다.
사용자는 풀다가 개념 문서로 넘어가는 쪽을 택했다. 그 대신 두 가지로 손실을 줄인다.

- 문제를 푸는 동안 진행 바를 상단에 얇게 고정해, 탭바가 있어도 "지금 몇 번째"가 늘 보인다.
- 폰에서는 보기 버튼의 세로 여백을 한 단계 줄이고, 문제 지문이 길면
  보기 영역만 안에서 스크롤한다 — 탭바가 문제를 밀어내지 않게.

## 3. 디자인 토큰

`style.css`의 `:root` 한 벌을 **두 벌(라이트/다크)** 로 늘린다. 값의 역할 이름은 그대로 쓴다 —
19에서 정한 `--fill`, `--review`, `--lv1~3` 체계가 이미 자리를 잡았다.

### 3.1 색

| 역할 | 라이트 (지금 유지) | 다크 (신규) |
| --- | --- | --- |
| `--bg` 페이지 바탕 | `#f8fafc` | `#0f172a` |
| `--card` 카드 면 | `#ffffff` | `#1c2740` |
| `--fill` 바탕 위 옅은 면 | `#f1f5f9` | `#273350` |
| `--border` | `#e2e8f0` | `#334155` |
| `--border-strong` | `#cbd5e1` | `#475569` |
| `--text` | `#0f172a` | `#e2e8f0` |
| `--text-2` | `#475569` | `#cbd5e1` |
| `--muted` | `#64748b` | `#94a3b8` |
| `--primary` | `#4f46e5` | `#818cf8` |
| `--primary-dark` | `#4338ca` | `#a5b4fc` |
| `--primary-soft` | `#eef2ff` | `#262052` |
| `--primary-border` (신규) | `#c7d2fe` | `#4338ca` |
| `--review` | `#f59e0b` | `#fbbf24` |
| `--correct` / `--wrong` | `#16a34a` / `#dc2626` | `#34d399` / `#f87171` |
| 난이도 글자 초·중·고 | 지금 값 유지 | `#6ee7b7` / `#fcd34d` / `#fca5a5` |
| 난이도 배경 초·중·고 | 지금 값 유지 | `#052e22` / `#422006` / `#4c1414` |

**다크 바탕이 `#0f172a`인 것은 우연이 아니다** — 라이트의 본문 글자색(`--text`)을 그대로
바탕으로 쓴다. 처음에는 한 단계 어두운 `#0b1120`이었는데 실제로 띄워 보니 무거웠다.
새 값을 지어내는 대신 이미 쓰던 눈금에서 골랐다: 지어낸 값은 나머지 색과 온도가 어긋나기
쉽고, "이 값은 어디서 왔나"에 답할 수 없다.

**색 있는 배경은 아주 어둡게, 그 위 글자는 아주 밝게.** 처음에는 라이트의 배지 색을
어둡게만 한 중간톤(`#7f1d1d` 위에 `#f87171`)을 썼는데 재 보니 **3.62:1**로 AA 미달이었다.
어두운 화면에서 중간톤 위의 중간톤은 둘 다 "회색빛 빨강"이 되어 서로 안 갈린다.
지금 값은 8~10:1이다. 다만 `--lv*-solid`(막대·점에 쓰는 면색)는 중간톤을 유지한다 —
글자가 아니라 면이라 기준이 3:1이고, 너무 밝으면 진도 막대가 눈을 찌른다.

**다크에서 `--primary`가 밝아지는 것이 핵심이다.** `#4f46e5`를 어두운 바탕에 그대로 쓰면
대비가 3:1도 안 나와 버튼 글자가 안 읽힌다. 다크의 주 버튼은 밝은 인디고 바탕 + 어두운 글자다.

**`--primary-border`를 새로 둔다.** 옅은 히어로 판이 `--primary-soft` 바탕 + 이 테두리로 서는데,
지금은 그 자리에 쓸 이름이 없어 컴포넌트마다 `#c7d2fe`를 직접 적게 된다.

**보조 글자 두 개는 다크에서 값이 달라진다.** 라이트의 `--muted`(`#64748b`)를 다크 바탕
(`#0b1120`)에 그대로 쓰면 대비가 **3.96:1** 로 AA에 못 미친다. 다크에서는 `--text-2`를
`#cbd5e1`(12.8:1), `--muted`를 `#94a3b8`(7.4:1)로 올린다. 역할 이름은 같고 값만 다르다.

**대비 검사는 구현 중에 실제로 잰다.** 19에서 스펙의 `#94a3b8`이 2.56:1로 AA 미달이었던 일이
있었다 — 표에 적힌 값이라고 통과했다는 뜻이 아니다. 본문·보조 글자·버튼 글자·배지 글자를
라이트와 다크 양쪽에서 재고, AA(4.5:1, 큰 글자 3:1)에 미달하면 그 자리에서 값을 올린다.

### 3.2 테마 적용 방식

```
:root                                   → 라이트 값 (기본)
@media (prefers-color-scheme: dark)
  :root:not([data-theme="light"])       → 다크 값 (기기 설정 자동)
:root[data-theme="dark"]                → 다크 값 (수동 선택이 이긴다)
```

**자동 감지 블록은 맨 마지막 단계에서 켠다.** 토큰을 선언하는 첫 단계에 함께 넣었다가
한 번 깨졌다 — 기기가 다크인 사람의 화면에서 글자색만 토큰을 따라 밝아지고 카드 배경은
아직 하드코딩된 흰색이라 **흰 글자에 흰 배경**이 됐다.

순서(토큰 먼저, 컴포넌트 나중) 자체는 맞았다. 틀린 것은 자동 감지를 그 순서의 첫 칸에
켠 것이다. 자동 감지는 "아무도 아무것도 안 했는데 화면이 바뀌는" 스위치라, 준비가 덜 된
기간을 사용자가 뒤집어쓴다. `[data-theme="dark"]`는 누군가 명시적으로 고를 때만 켜지고
그 화면(설정)이 아직 없으므로 아무 일도 일어나지 않는다 — 같은 값을 같은 순서로 쌓되
**노출되는 시점만** 다르다.

전환은 3단(자동 · 라이트 · 다크). 고른 값은 `localStorage`에 둔다.

**`data-theme`을 붙이는 코드만 각 HTML의 `<head>`에 인라인으로 넣는다** — 한 줄짜리 예외다.
`shell.js`는 `<body>` 끝에서 실행되므로, 거기서 붙이면 다크를 고른 사람도 첫 그림이
라이트로 한 번 번쩍인다(FOUC). 나머지 테마 코드(전환 UI·저장·기기 설정 감지)는 전부
`shell.js`에 둔다.

### 3.3 타이포·간격

- 글꼴은 지금 그대로(Pretendard Variable, `@import`).
- 크기 눈금을 **6단으로 고정**한다: 11 / 13 / 15 / 17 / 21 / 30px.
  지금은 화면마다 임의값이 섞여 있다. 눈금이 있으면 "이건 왜 16인가"를 매번 정하지 않는다.
- 간격 눈금은 4의 배수 6단: 4 / 8 / 12 / 16 / 24 / 40px.
- 모서리는 19의 결정 유지 — `--radius: 8px`, 큰 표적만 `--radius-lg: 12px`.
- 그림자는 19의 결정 유지 — 카드에 안 쓴다. `--overlay-shadow`만 진짜 떠 있는 것에.

## 4. 셸 (D1)

### 4.1 구조

| 폭 | 모습 |
| --- | --- |
| ~ 767px | 상단 얇은 바(브랜드 + 상황 표시) + **하단 탭바 5칸** |
| 768px ~ | **좌측 사이드바** 고정 폭 208px, 본문 최대 폭 880px |

탭바 5칸: 오늘 · 문제 · 복습 · 문서 · 나.
사이드바: 오늘 / 문제 / 복습(배지) / 개념 문서 — 구분선 — 내 기록 / 설정 — 맨 아래 관리 콘솔(관리자만).

"나" 탭은 폰에서 **내 기록**으로 가고, 그 화면 위쪽에 설정·로그아웃 입구를 둔다.
탭을 여섯으로 늘리지 않는다 — 다섯이 폰 가로폭에서 글자가 안 줄어드는 상한이다.

### 4.2 공용 레이아웃 JS (D5)

지금은 각 HTML이 `<header id="nav">` 하나만 두고 `renderNav()`가 채운다. 사이드바는
마크업이 더 크고 본문을 감싸야 해서 이 방식으로는 부족하다. 새 파일 하나를 둔다.

```
js/shell.js   — 셸 마크업 생성 + 활성 메뉴 표시 + 테마 전환 + 복습 배지
              renderShell({ active, title })
```

`focus` 같은 "셸을 감추는" 옵션은 두지 않는다 — D3에서 플레이어도 셸을 유지하기로 했으므로
셸이 사라지는 화면이 하나도 없다. 쓰지 않을 상태를 미리 만들면 그 상태가 깨져도 아무도 모른다.

각 페이지는 `<body>`에 본문만 쓰고 `renderShell()`을 부른다. HTML 13개에 같은
사이드바 마크업을 복붙하지 않는다 — 화면이 하나 늘 때마다 빠뜨릴 자리가 같이 느는 것을 막는다.

`api.js`의 `renderNav`·`authAreaHtml`·`wireLogout`·`loadReviewBadge`는 `shell.js`로 옮긴다.
`api.js`는 **토큰·HTTP·응답 봉투**만 맡는다 — 지금 한 파일이 인증·통신·화면을 다 하고 있다.

## 5. 화면별 설계

### 5.1 오늘 (`index.html`) — 로그인

위에서 아래로 네 덩이.

1. **옅은 히어로** — `--primary-soft` 바탕 + `--primary-border` 테두리 + 왼쪽 4px 굵은 띠.
   날짜 / "여섯 문제 남았어요" / 안내 한 줄 / 진행 바 / [이어서 풀기] [복습 N개].
   상태에 따라 세 얼굴을 갖는다.

   | 상태 | 색 | 문구 |
   | --- | --- | --- |
   | 할 일 있음 | 인디고 | 여섯 문제 남았어요 |
   | 오늘 몫 끝 | 초록(`--correct`) | 오늘 몫은 끝났어요 ✓ — [더 풀어보기] |
   | 첫날(기록 0) | 인디고 | 첫 문제를 풀어볼까요 — 어떻게 돌아가는지 3줄 안내 |

2. **통계 4칸** — 푼 문제 / 정답률 / 이번 주 / 복습 대기.
3. **분야별 진도 6개** — 2열 그리드. 나머지는 [전체 보기 →] 로 내 기록에.
4. **최근 개념 문서** — 지금 있는 것 유지.

### 5.2 오늘 (`index.html`) — 비로그인 = 랜딩 (신규)

같은 URL에서 갈린다. 지금도 그렇게 되어 있고, 내용만 채운다.

히어로(제목 + 한 줄 + [무료로 시작하기] [가입 없이 한 문제 풀어보기])
→ 3단 설명(매일 10문제 / 잊을 때쯤 다시 / 개념도 같이)
→ **실제 문제 미리보기 한 개**
→ 집계 한 줄("문제 296개 · 개념 문서 24편 · 8개 분야").

"가입 없이 한 문제 풀어보기"는 지금도 되는 동작이다 — 문제 조회는 공개 API이고 채점만
로그인이 필요하다. 한 문제를 풀게 하고 **채점 직전에** 가입을 권한다.

### 5.3 문제 푸는 화면 (`quiz.html`·`daily.html`·`review.html` + `player.js`)

셸을 유지한다(D3). 본문 구성은 셋이 같다.

- 상단: 얇은 진행 바(4px) + 분야·유형·난이도 배지 + N/M
- 문제 지문 17px
- 보기: 카드형 버튼. 왼쪽에 번호 칩(숫자키 힌트와 같은 값), 고르면 인디고 테두리+옅은 바탕

## 7. 서버 변경 (둘, 둘 다 작다)

디자인 작업이지만 화면이 요구하는 데이터가 없어 두 가지가 붙는다.

### 7.1 분야별 전체 문제 수 — 되돌리는 결정이다

`StudySummaryResponse.DomainProgress`는 지금 `(domain, label, solved)`뿐이다.
진도 막대는 분모가 있어야 그려진다.

```java
public record DomainProgress(Domain domain, String label, long solved, long total) {}
```

**이건 기존 판단을 뒤집는 것이다.** 그 DTO의 주석이 분모를 안 주는 이유를 적어 두고 있다.

> 배치가 매일 문제를 더해 분모가 커지기 때문이다. 어제 40%가 오늘 37%가 되면
> 아무것도 잘못하지 않았는데 뒷걸음질친 것처럼 보인다.

걱정은 진짜다. 매일 도는 생성 배치가 분모를 늘리므로 **가만히 있어도 막대가 줄어든다.**
2.1에서 다른 두 판단은 유지했는데 이것만 뒤집는 이유는, 막대 없이는 "8개 분야 중 내가
어디쯤인지"를 한눈에 볼 방법이 없어서다 — 숫자만 늘어놓으면 40개 중 31개와 33개 중 9개가
같은 무게로 읽힌다.

**대신 뒷걸음질이 눈에 덜 띄게 만든다.**

- 화면의 주인공은 **절대값**이다. `31 / 40` 을 크게, 막대는 그 아래 얇게 보조로 둔다.
  퍼센트 숫자는 아예 쓰지 않는다.
- 문제 목록 개편 때 정한 **"게이지 → 절대값"** 과 같은 방향이다. 새로 만드는 규칙이 아니다.
- 뒤집은 이 판단과 그 이유를 DTO 주석에도 남긴다. 지금 주석을 지우지 말고 **이어서 적는다** —
  "왜 그때는 안 줬고 지금은 주는가"가 다음 사람이 읽어야 할 이야기다.

`ProblemListService`에서 분야별 전체 개수를 함께 집계한다. 홈과 내 기록이 같이 쓴다.
승인된 문제만 센다 — 검수 대기 중인 초안이 분모에 들어가면 사용자가 풀 수 없는 문제가
분모에 잡힌다.

### 7.2 공개 집계 엔드포인트

랜딩의 "문제 296개 · 개념 문서 24편 · 8개 분야"를 위해서다. 숫자를 HTML에 글로 박으면
곧 거짓말이 된다.

```
GET /api/stats  (인증 불필요)
→ { problemCount, documentCount, domainCount }
```

승인된 것만 센다. 요청 제한은 `api` 버킷(60/분)을 그대로 탄다.

**둘 다 테스트를 붙인다.** 로직이 바뀌므로 빌드 통과만으로는 완료로 보지 않는다.

## 9. 단계 나누기

19에서 "화면이 변하지 않는 것부터 쌓는다"가 통했다. 같은 방식으로 자른다.
**각 단계마다 앱을 띄워 눈으로 확인하고 커밋한다.**

| 단계 | 한 일 | 화면 변화 |
| --- | --- | --- |
| 1 | 토큰 두 벌(라이트/다크) 선언 + 타이포·간격 눈금. 아직 아무도 안 씀 | 없음 |
| 2 | `shell.js` 신설, `api.js`에서 화면 코드 분리. 기존 상단 바를 그대로 그림 | 없음 |
| 3 | 셸을 사이드바/탭바로 교체 + 반응형 | 큼 |
| 4 | 서버 둘(7.1·7.2) + 테스트 | 없음 |
| 5 | 홈 개편 (히어로 3상태 · 통계 · 진도 6개) | 큼 |
| 6 | 플레이어 3화면 개편 | 큼 |
| 7 | 나머지 기존 화면을 새 토큰·눈금으로 | 중 |
| 8 | 새 화면 셋 (랜딩 · 내 기록 · 설정) | 신규 |
| 9 | 다크 모드 실제 적용 + 전환 UI + 대비 실측 | 큼 |
| 10 | 관리 콘솔 셸 + `admin-table.js` + 화면 7개 이전 | 큼 |

1~9가 사용자 화면(D7), 10이 관리 콘솔. 9를 끝에 두는 이유는 다크가 **모든 화면이
새 토큰만 쓰게 된 뒤라야** 한 번에 맞기 때문이다 — 중간에 하면 옮길 때마다 두 번 고친다.

**구현 계획은 두 개로 나눈다.** 단계 1~9(사용자 화면)가 한 계획, 단계 10(관리 콘솔)이 다른
계획이다. 열 단계를 한 계획에 밀어 넣으면 중간에 방향이 바뀌었을 때 뒤쪽 절반이 통째로
낡는다. 10은 1~9가 끝나고 실제 화면을 본 뒤에 쓴다.
