# ADR-0006: LLM 문제 생성은 초안 테이블 + 사람 검수 + 일일 배치로 구현

- 상태: 채택됨 — **2026-08-11 일부 개정**(배치 실행 주체 변경, 아래 "개정" 절 참고)
- 날짜: 2026-07-18
- 관련 로드맵: B안 (LLM 문제 생성) — [13-llm-problem-generation](../13-llm-problem-generation.md) · [14-llm-batch-automation](../14-llm-batch-automation.md)

## 맥락 (Context)

오늘의 퀴즈(ADR-0005)는 문제 창고(problem)에서 매일 세트를 뽑는다. 창고가 작으면
같은 문제가 반복 출제되어 기능 가치가 떨어진다. Claude API로 문제를 자동 생성해
창고를 채우는 기능(B안)을 만든다. 사용자가 백엔드 개발자라 `BACKEND_FRAMEWORK`
(스프링·백엔드) 도메인도 이때 신설했다(docs/02).

결정할 것은 세 가지다.

1. **생성된 문제를 바로 출제하는가**: LLM은 그럴듯하지만 틀린 문제(환각)를 만들 수 있다.
2. **어디에 저장하는가**: problem에 상태 컬럼을 얹는가, 별도 테이블을 두는가.
3. **언제 생성하는가**: ADR-0005에서 배치를 버렸는데, 여기서도 같은 결론인가.

## 검토한 선택지 (Options)

### 출제 경로
1. **생성 즉시 정식 문제로 등록** — 장점: 검수 노동 0. 단점: 틀린 문제가 그대로
   사용자에게 출제된다. 학습 서비스에서 오답 해설이 틀리는 건 신뢰의 근간이 무너지는
   일이라 탈락.
2. **초안(PENDING) 저장 → 관리자 승인 시 등록** — 장점: 틀린 문제가 사용자에게
   도달할 수 없는 구조. 단점: 검수 노동. 채택.

### 저장 위치
1. **problem에 status 컬럼 추가** — 단점: 퀴즈·복습·오늘의 퀴즈 등 **모든 기존 조회에
   "승인된 것만" 필터가 번져야 하고**, 하나라도 빠뜨리면 미검수 문제가 노출된다.
2. **별도 초안 테이블(generated_problem_draft)** — 기존 조회는 한 줄도 안 바꾼다.
   미검수 문제는 애초에 problem에 없으므로 노출 사고가 구조적으로 불가능. 채택.
   보기는 JSON 문자열로 저장(초안은 채점에 안 쓰이는 임시 데이터라 정규화 이득이 없음).

### 생성 시점
1. **지연 생성** — 오늘의 퀴즈 방식. 그런데 "첫 조회"에 해당하는 사용자 요청이 없다
   (생성은 사용자 기능이 아니다). 해당 없음.
2. **관리자 수동 버튼만** — 장점: 단순. 단점: 잊으면 창고가 안 자란다.
3. **수동 버튼 + `@Scheduled` 일일 배치(기본 꺼짐)** — 채택. ADR-0005가 배치를 버린
   근거는 "꺼져 있으면 그날 **사용자 기능이 죽는다**"였다. 문제 생성은 사용자 대면이
   아니라서 하루 안 돌아도 무해하다 — **실패 비용이 낮은 작업이야말로 배치를 배우기에
   안전한 자리**라 유예했던 배치 학습 소재를 여기서 회수한다.

### 승인 = 등록 경로
- **AdminProblemService.create 재사용** (채택): AI 문제도 손 등록과 같은 검증
  (객관식 정답 1개, OX는 O/X 등 — QUIZ_004)을 통과해야 등록된다. 검증 로직을
  복사하면 한쪽만 수정되는 순간 어긋난다(단일 경로 원칙).

## 결정 (Decision)

**Claude 구조화 출력으로 생성 → 별도 초안 테이블에 PENDING 저장 → 관리자 승인 시
기존 등록 경로(AdminProblemService)로 정식 문제화. 트리거는 수동 버튼 + 일일 배치(기본 꺼짐).**

- 생성 대상은 "가장 부족한 도메인×난이도 칸"을 자동 선택한다(빈 칸 채우기 전략) —
  ADR-0005의 재검토 트리거("문제 풀 고갈")에 대한 선제 대응.
- 구조화 출력(record → JSON 스키마 강제)으로 파싱 실패 자체를 제거한다.
  형식은 스키마가, 내용 규약(정답 1개 등)은 저장 전 정규화 + 승인 시 재검증이 막는다.
- Claude 호출은 트랜잭션 밖에서 한다 — 수십 초짜리 외부 I/O가 DB 커넥션을 물고 있으면
  커넥션 풀이 고갈된다.
- 배치는 `@ConditionalOnProperty`로 기본 꺼짐 — API 비용이 드는 작업이 설정 실수로
  몰래 돌지 않게, 켜는 것을 명시적 선택으로 만든다.

## 결과 (Consequences)

- 긍정적: 문제 창고가 자동으로 자라면서도 품질 게이트(사람 검수)는 유지된다.
  ADR-0005에서 유예한 배치 학습 소재 회수. 초안 이력(모델·거절 사유)이 쌓여
  모델/프롬프트 개선의 근거 데이터가 된다.
- 부정적/트레이드오프: 승인 노동이 남는다(문제당 수십 초). API 비용 발생
  (문제당 수 원 수준). 초안 테이블이라는 관리 대상 추가.
- 재검토 트리거: 승인율이 충분히 높게 유지되면(예: 95%↑) 자동 승인 + 표본 검수로
  완화 검토. 비용이 커지면 모델 하향(Sonnet/Haiku) 후 승인율 비교 — model 컬럼이
  그 비교의 재료다.

## 개정 (2026-08-11) — 배치 실행 주체를 앱에서 GitHub Actions로

**무엇이 바뀌었나**: 일일 배치를 앱 내부 `@Scheduled`에서 GitHub Actions로 옮겼다.
Actions가 매일 문제를 만들어 `generated/YYYY-MM-DD.json`으로 저장소에 커밋하고,
앱은 기동할 때 그 파일을 검수 대기 초안으로 흡수한다(V7 `imported_draft_file`).
상세 설계는 [14-llm-batch-automation](../14-llm-batch-automation.md).

**왜 바꿨나**: 배치를 켠 다음 날 확인해 보니 초안이 0건이었다. 원인은 명확했다 —
이 앱은 개인 PC에서 도는 앱이고, 06시에 PC나 앱이 꺼져 있으면 앱 안의 알람은 울리지 않는다.

여기서 중요한 건 **원래 결정의 논리가 틀린 게 아니라는 점**이다. "문제 생성은 사용자
대면이 아니라 하루 안 돌아도 무해하다"는 판단은 지금도 유효하다. 틀린 것은 그 판단이
딛고 있던 **숨은 가정** — "배치가 하루쯤 건너뛸 수 있다"였다. 실제로는 "거의 매번 안 돈다"에
가까웠고, 이건 유예가 아니라 기능 부재다. **결정을 검증할 때는 결론만이 아니라 그 결론이
전제한 실행 환경까지 확인해야 한다**는 교훈으로 남긴다.

**무엇을 잃었나**: "가장 부족한 칸 자동 선택"이 배치 경로에서 사라졌다(러너에 DB가 없다).
날짜 기반 24일 순환으로 대체했다. 적응력을 잃었지만, 집계 방식이 실제로 겪었던 버그
(검수를 미루면 매일 같은 칸만 뽑힘)가 순환에서는 정의상 발생할 수 없다는 이득이 있다.
관리자 수동 생성은 DB가 옆에 있으므로 기존 집계 선택을 그대로 쓴다.

**함께 정리한 것**: 주간 감시 워크플로(`llm-e2e.yml`)를 폐지했다. 그 워크플로의 존재
이유는 "배치가 조용히 실패하면 아무도 모른다"였는데, Actions job은 실패 시 소유자에게
메일을 보내므로 **매일 도는 생성 배치 자신이 더 촘촘한 감시기**가 됐다. 감시 대상이
스스로 감시 기능을 갖게 되면 별도 감시기는 중복 비용이다.

**재검토 트리거**: 앱을 상시 서버에 배포하게 되면(로드맵), 앱 내부 스케줄러로 되돌리는
편이 단순하다 — 그때는 파일 왕복과 흡수 로직이 불필요한 복잡성이 된다.

## 면접 대본 요약

"LLM으로 콘텐츠를 생성할 때 세 가지를 결정했습니다. 첫째, 생성물을 바로 서비스에
넣지 않고 별도 초안 테이블에 격리한 뒤 사람 승인을 거치게 했습니다 — 기존 테이블에
상태 컬럼을 얹으면 모든 조회에 필터가 번지고 하나만 빠져도 미검수 콘텐츠가 노출되는데,
테이블을 분리하면 그 사고가 구조적으로 불가능해집니다. 둘째, 승인 시 관리자 수동 등록과
같은 서비스 경로를 재사용해 검증 규칙이 한 곳에만 존재하게 했습니다. 셋째, 앞서 오늘의
퀴즈에서는 '꺼져 있으면 사용자 기능이 죽는다'는 이유로 배치를 버렸지만, 문제 생성은
실패해도 무해한 작업이라 배치를 채택했습니다 — 같은 도구라도 실패 비용에 따라 결론이
달라진다는 걸 한 프로젝트 안에서 대비해 본 사례입니다.

다만 그 배치를 앱 안의 `@Scheduled`로 둔 건 나중에 개정했습니다. 개인 PC에서 도는 앱이라
예약 시각에 컴퓨터가 꺼져 있으면 아예 실행되지 않는다는 걸 실측으로 발견해서,
GitHub Actions로 옮기고 결과를 저장소에 커밋한 뒤 앱이 기동할 때 흡수하는 구조로
바꿨습니다. **판단이 틀렸다기보다 그 판단이 전제한 실행 환경을 확인하지 않았던 것**이고,
그래서 ADR을 지우지 않고 개정 이력으로 남겼습니다."
