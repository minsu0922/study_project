# ADR-0005: 오늘의 퀴즈는 세트 저장 + 지연 생성(lazy)으로 구현

- 상태: 채택됨
- 날짜: 2026-07-15
- 관련 로드맵: 로드맵 6 (오늘의 퀴즈 · 데일리 세트) — [12-daily-quiz](../12-daily-quiz.md)

## 맥락 (Context)

"매일 문제를 풀고 싶다"는 요구에서 출발했다. 매일 뭘 풀지 고르는 결정 비용이
습관을 막으므로, 시스템이 매일 개인화된 세트(복습 4 + 취약 3 + 새 문제 3)를
차려 주는 기능을 만든다.

결정할 것은 두 가지다.

1. **세트를 저장하는가**: 진행률("3/10")이 의미 있으려면 오늘 세트는 하루 동안
   고정이어야 한다. 기존 퀴즈 API는 `ORDER BY RAND()`라 매번 결과가 다르다.
2. **언제 만드는가**: "매일"이라는 주기를 무엇으로 실행하는가.
   제약 조건 — 이 앱은 로컬 PC에서 돌므로 **자정에 꺼져 있을 수 있다**.

## 검토한 선택지 (Options)

### 세트 고정 방법
1. **저장 테이블(daily_quiz + daily_quiz_item)** — 뽑은 결과를 DB에 남긴다.
   장점: 어느 기기·어느 시점에도 같은 세트, 진행률·스트릭·source별 분석의 재료가 됨.
   단점: 테이블 2개와 쓰기 경로 추가.
2. **결정적(seed 고정) 랜덤** — user_id+날짜를 시드로 매번 같은 결과를 재계산.
   장점: 저장 없음. 단점: 하루 중 재료가 변하면(복습 승급, 새 문제 추가) 세트가
   슬며시 바뀐다. "몇 개 풀었는지"도 결국 어딘가 저장해야 해서 이점이 사라짐.
3. **localStorage에 세트 보관** — 서버 저장 없음.
   단점: 기기 간 불일치, 지우면 증발, 서버가 완료/스트릭을 알 수 없음. 탈락.

### 생성 시점
1. **`@Scheduled` 자정 배치** — 매일 0시 전 사용자 세트 생성.
   장점: 접속 시점 비용 0, "배치" 학습 소재. 단점: **앱이 꺼져 있으면 그날 세트가
   없다**(로컬 PC 치명적), 안 올 사용자 몫까지 만드는 낭비, 실패 시 복구 로직 필요.
2. **지연 생성(lazy)** — 그날 첫 `GET /api/me/daily-quiz` 때 없으면 만든다.
   장점: 앱 가동 시간과 무관하게 항상 동작, 필요한 만큼만 생성, 별도 스케줄러 없음.
   단점: 첫 조회가 살짝 느림(생성 비용 포함), 동시 첫 조회 경합 처리 필요.
3. **Spring Batch** — 이 규모(사용자 소수 × 10행)에 청크·재시작 프레임워크는 과잉. 탈락.

## 결정 (Decision)

**세트는 테이블에 저장하고, 그날 첫 조회 때 지연 생성한다.**

- 저장: 세트 고정은 이 기능의 전제 조건이고, 재계산(2안)은 재료가 변하는 순간 깨진다.
  저장한 순간부터 진행률·완료·스트릭·배합 분석이 전부 공짜로 따라온다.
- 지연 생성: 결정적 근거는 실행 환경이다 — 로컬 PC에서 자정 배치는 "꺼져 있으면 그날
  기능이 죽는" 단일 실패점이다. 지연 생성은 스케줄러라는 부품 자체를 없앤다.
  "없으면 만들어서 반환"은 멱등이라 클라이언트도 단순해진다.
- 동시 첫 조회(탭 2개) 경합은 코드가 아니라 **UNIQUE(user_id, quiz_date)** 가 막는다 —
  review_item(ADR-0004)과 같은 패턴의 재적용.

## 결과 (Consequences)

- 긍정적: 스케줄러 없이 "매일" 기능이 성립. 세트가 학습 기록(어느 칸 문제를 잘 맞히나)으로
  축적됨. 채점 경로는 기존 submit 하나를 유지(사다리·세트 반영 모두 트랜잭션 합류).
- 부정적/트레이드오프: "배치 작업"이라는 학습 소재는 이번에 못 얻는다(B안·LLM 생성으로 유예).
  그날 첫 조회에 생성 비용이 실린다(수십 ms 수준 예상, 문제 될 규모 아님).
- 재검토 트리거: 사용자가 늘어 첫 조회 생성 비용이 관측되면 배치 사전 생성 병행 검토.
  문제 풀 고갈로 GENERAL 채움이 잦아지면 B안(LLM 문제 생성) 논의 시작.

## 면접 대본 요약

"매일 개인화 문제 세트 기능에서 두 가지를 결정했습니다. 첫째, 세트를 저장했습니다 —
진행률이 의미 있으려면 세트가 하루 동안 고정이어야 하는데, 시드 고정 재계산은 복습
상태 같은 재료가 하루 중 변하면 깨지기 때문입니다. 둘째, 자정 배치 대신 지연 생성을
택했습니다 — 실행 환경이 상시 가동 서버가 아니라서 자정 배치는 단일 실패점이 되고,
'첫 조회 때 없으면 생성'은 스케줄러라는 부품 자체를 제거하면서 멱등 API로 클라이언트도
단순해집니다. 동시 생성 경합은 코드가 아니라 DB UNIQUE 제약으로 막았는데, 경합 방지를
애플리케이션 로직에 맡기지 않는다는 원칙을 복습 기능에 이어 재적용한 것입니다."
