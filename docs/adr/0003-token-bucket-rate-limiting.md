# ADR-0003: 요청 제한은 토큰 버킷을 Redis Lua로 직접 구현

- 상태: 채택됨
- 날짜: 2026-07-06
- 관련 로드맵: 로드맵 3 (요청 제한 + 표준 에러 응답 확장)
- 관련 문서: [09-rate-limiting](../09-rate-limiting.md)

## 맥락 (Context)
로그인 무차별 대입과 API 폭주를 막기 위한 요청 제한이 필요하다. 결정할 것이 세 층위:
(1) 어떤 **알고리즘**으로 셀 것인가, (2) 카운터를 **어디에** 둘 것인가, (3) **라이브러리 vs 직접 구현**.

## 검토한 선택지 (Options)

### 알고리즘
1. **고정 윈도우 카운터** — "매 분 0초에 카운터 리셋". 구현 최단순. 단, 경계 문제: 0:59에 60번 + 1:01에 60번 = 2초간 120번 통과.
2. **슬라이딩 윈도우 로그** — 요청 타임스탬프를 전부 저장(ZSET). 정확하지만 요청당 메모리·연산 비용이 크다.
3. **토큰 버킷** — 버킷 크기(버스트)와 충전 속도(평균)를 분리해 제어. 저장은 키당 숫자 2개(tokens, ts). 경계 문제 없음.

### 카운터 위치
1. **앱 메모리(예: Caffeine)** — 가장 빠르지만 서버가 늘어나면 한도가 서버 수만큼 뻥튀기. 재시작 시 리셋.
2. **RDB** — 매 요청 UPDATE는 "DB를 지키려는 장치가 DB를 죽이는" 자충수.
3. **Redis** — 메모리 속도 + 서버 간 공유 + TTL로 청소 공짜. 이미 로드맵 2에서 도입해 추가 인프라 없음.

### 구현
1. **Bucket4j(+Redis)** — 검증된 라이브러리. 다양한 백엔드·정책 지원. 단, 내부가 블랙박스가 되고 의존성 추가.
2. **직접 구현(Lua 스크립트)** — 핵심이 Lua 40줄. 원자성 확보 방법(스크립트 원자 실행)을 직접 다루게 됨.

## 결정 (Decision)
**토큰 버킷 + Redis + Lua 직접 구현.**

- 토큰 버킷: 버스트(페이지당 API 동시 호출)와 평균 속도를 독립 제어할 수 있는 유일한 후보. 실무 표준이기도 하다.
- Redis: 이미 있는 인프라이고, "요청 횟수"는 자주 쓰고 금방 버리는 데이터라 Redis의 결이 정확히 맞는다.
- 직접 구현: 이 프로젝트의 목적이 원리 체득이다. "왜 GET/SET 두 번이면 안 되고 Lua여야 하는가"(check-then-act 경쟁 상태)를
  직접 겪는 것이 Bucket4j 설정법을 배우는 것보다 남는 게 많다. 실무 대규모라면 Bucket4j가 합리적 선택.

부속 결정:
- **fail-open**: Redis 장애 시 전부 통과 + 경고 로그. 캐시·refresh 토큰과 동일 철학(보조 장치 장애 ≠ 서비스 장애).
- **시각은 Redis TIME**: 앱 서버 다중화 시 clock skew 제거 — 기준 시계를 하나로.
- **키 정책**: 인증 경로는 IP(로그인 전이라 신원 불명), 그 외는 사용자 id(NAT 공유 IP의 공정성 + IP 변경 회피 차단).

## 결과 (Consequences)
- 긍정적: 의존성 무추가. 429 + Retry-After가 기존 공통 봉투 체계에 자연스럽게 확장(COMMON_429). 버킷 상태를 redis-cli로 직접 관찰 가능(학습 효과).
- 트레이드오프: 모든 API 요청에 Redis 왕복 1회 추가(로컬 실측 ~수 ms). Redis 장애 시 요청마다 타임아웃(2초) 비용 — 장애가 길어지면 전 API가 2초씩 느려진다(개선 후보: 연속 실패 시 일정 시간 제한을 끄는 회로 차단기).
- 재검토 트리거: 엔드포인트별 세밀한 정책이 필요해지는 시점(@RateLimit 애너테이션 방식 또는 Bucket4j 전환 검토). 다중 인스턴스 배포 시 X-Forwarded-For 신뢰 구성 필수.

## 면접 대본 요약
"요청 제한을 토큰 버킷으로 직접 구현했습니다. 고정 윈도우는 경계에서 한도 2배가 뚫리는 문제가 있어 버스트와 평균 속도를 분리 제어하는 토큰 버킷을 골랐고, 카운터는 서버가 늘어도 한도가 공유되도록 Redis에 뒀습니다. 읽고-계산하고-쓰는 판정을 GET/SET로 나누면 동시 요청이 같은 토큰을 두 번 쓰는 경쟁 상태가 생겨서, Lua 스크립트로 묶어 Redis가 원자적으로 실행하게 했습니다. 제한기 장애가 서비스 장애가 되지 않도록 fail-open으로 두되 경고 로그로 관측 가능하게 했고, 키는 로그인 전 경로만 IP, 나머지는 사용자 id로 세서 NAT 뒤 사용자들이 억울하게 묶이지 않게 했습니다."
