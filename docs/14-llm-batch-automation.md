# 14. LLM 일일 생성 배치 자동화 (GitHub Actions)

> 결정 배경: [ADR-0006](adr/0006-llm-problem-generation.md)(개정) · 관련: [13-llm-problem-generation](13-llm-problem-generation.md)(생성·검수 본체) · [11-flyway-migrations](11-flyway-migrations.md)(V7)
>
> 📖 **설정·실행·점검 방법은 [16-llm-pipeline-operations](16-llm-pipeline-operations.md)**로 옮겼다.
> 이 문서는 "왜 Actions로 옮겼나"와 그 과정의 판단을 남긴다.
>
> 📖 **생성 품질을 어떻게 지키는지는 [17-prompt-quality-and-eval](17-prompt-quality-and-eval.md)**.
> 배치에 붙은 관문 둘이 그 문서에서 나왔다 — 생성 **전**의 `hasMaterialFor`
> (오늘 난이도가 캘 절이 근거 문서에 있는지)와, 생성 **직후**의 품질 경고 6종이다.

## 쉽게 말하면

문제를 매일 자동으로 만들어 두는 기능인데, 만드는 곳이 **내 PC가 아니라 GitHub**이다. 🏭☁️

원래는 앱 안에 알람시계(`@Scheduled`)를 넣어 매일 06시에 문제를 만들게 했다. 그런데
그 알람은 **앱이 켜져 있을 때만 울린다.** 새벽 6시에 PC가 꺼져 있으면 그날 문제는
영영 만들어지지 않는다 — 실제로 배치를 켠 다음 날 확인해 보니 초안이 0건이었다.

그래서 "매일 정해진 시각에 무언가를 한다"는 일을 **항상 켜져 있는 곳**으로 옮겼다.

```
   [GitHub Actions]  매일 06:17, 내 PC와 무관하게 실행
          ↓  문제를 만들어 저장소에 커밋
   [저장소 generated/2026-08-12.json]   ← 택배함
          ↓  내가 앱을 켤 때
   [내 PC의 검수 대기함]  → 관리자 화면에서 승인/거절 (기존과 동일)
```

**택배함 비유**가 정확하다. 택배기사(Actions)는 내가 집에 없어도 매일 물건을 택배함에
넣어 두고, 나는 집에 돌아왔을 때 한 번에 꺼내 온다. 일주일 만에 켜면 7일 치가 한꺼번에
들어온다 — **밀린 것이 사라지지 않는다**는 점이 예전 방식과의 결정적 차이다.

## 왜 옮겼나 — 가정이 틀렸다는 것을 실측으로 발견

ADR-0006에서 배치를 채택할 때의 논리는 이랬다.

> "문제 생성은 사용자 대면이 아니라서 하루 안 돌아도 무해하다. 실패해도 무해한 작업이야말로
> 배치를 배우기에 안전한 자리다."

이 판단 자체는 지금도 맞다. **틀린 것은 그 뒤에 숨어 있던 가정**이었다 — "배치가 하루쯤
건너뛸 수 있다"와 "배치가 **한 번도 안 돈다**"는 전혀 다른 이야기인데, 개인 PC에서 도는 앱의
`@Scheduled`는 후자에 가까웠다. PC를 새벽에 켜 두는 습관이 없으면 성공 확률이 0에 수렴한다.

| | 앱 내부 `@Scheduled` | GitHub Actions |
|---|---|---|
| 실행 주체 | 내 PC의 앱 프로세스 | GitHub의 상시 인프라 |
| PC가 꺼져 있으면 | **그날 치 영구 소멸** | 정상 실행, 결과는 저장소에 보관 |
| 실패했을 때 | 로그 한 줄(조용히 죽음) | job 실패 → **소유자에게 메일** |
| DB 접근 | 가능(같은 PC) | 불가능 → 설계 변경 필요 |
| 비용 | 0 | 0 (공개 저장소는 러너 무료) |

## 기술적 흐름

### 1) 클라우드 쪽 — 매일 06:17에 벌어지는 일

`.github/workflows/llm-daily.yml`이 `DraftGeneratorCli`(Gradle 태스크 `generateDrafts`)를 실행한다.

1. **오늘의 칸 결정** — `GenerationSchedule.cellFor(날짜, 후보도메인)`
2. **중복 회피 목록 구성** — `generated/` 안의 이전 파일들 + `_existing-questions.json`
3. **Claude 호출** — `ClaudeProblemGenerator`(기존 코드 그대로 재사용)
4. **JSON 파일로 저장** — `generated/YYYY-MM-DD.json`
5. **커밋 & 푸시** — `github-actions[bot]` 이름으로

**Spring을 띄우지 않는다.** 이 프로그램에 필요한 건 Claude 호출뿐이라 DB도 웹서버도 없어도
된다. Spring을 띄우면 `ddl-auto: validate`가 MySQL 연결을 요구해서 러너에 DB 컨테이너를
붙여야 하는데, "생성만 하는 작업에 DB를 왜 띄우나"가 된다.

> 이 경로는 새로 검증할 것도 없었다. 폐지한 `ClaudeProblemGeneratorE2ETest`가 이미 매주
> 같은 방식(Spring 없이 생성기만 직접 생성)으로 실제 API를 호출해 왔기 때문이다.
> **기존에 만들어 둔 것이 새 설계의 디딤돌이 된 사례.**

### 2) 날짜 순환 — DB 없이 "무엇을 만들지" 정하기

이 설계 변경에서 **유일하게 잃은 것**이다. 기존에는 `GROUP BY` 집계로 "가장 부족한 칸"을
찾았는데, 러너에는 DB가 없다. 대신 날짜만으로 결정되는 순환으로 바꿨다.

- **잃은 것과 얻은 것**: 적응력(검수 상황에 반응)을 잃고 예측 가능성을 얻었다. 그런데
  집계 방식이 실제로 겪었던 버그 — *검수를 미루면 그 칸의 문제 수가 늘지 않아 매일 같은 칸만
  뽑힘* — 은 **순환에서는 정의상 발생할 수 없다.**
- 관리자 화면의 수동 생성은 **여전히 집계 기반 자동 선택**을 쓴다(옆에 DB가 있으므로).
  두 경로가 다른 전략을 쓰는 것은 **가진 정보가 다르기 때문**이지 일관성 결함이 아니다.

#### 처음 규칙 — 24칸 순환 (지금은 폴백)

```
8개 도메인 × 3개 난이도 = 24칸
순번 = (에포크일) % 24
도메인 = 후보[순번 % 8]          ← 안쪽 축: 매일 바뀜
난이도 = 난이도[(순번 / 8) % 3]  ← 바깥 축: 8일마다 한 단계
```

**도메인을 안쪽 축에 둔 이유**: 난이도를 안쪽에 두면 같은 분야가 사흘 연속 나온다.
검수하는 사람이 지루하면 검수를 미루고, 미루면 이 기능 전체가 멈춘다.

#### 지금 규칙 — 4일 주기 (`GenerationSchedule.planFor`)

문제들이 서로 남남이라 **지식이 파편으로 쌓인다**는 진단이 나와, 개념 문서 한 편을 중심으로
나흘을 묶는 방식으로 바꿨다(2026-08-12, docs/15 2단계).

```
0일차  개념 문서 1편
1·2·3일차  ↑ 그 문서를 근거로 초급 → 중급 → 고급 문제
→ 다음 분야로 (후보 8개 × 4일 = 32일에 한 바퀴)
```

**위의 "도메인을 안쪽 축에" 원칙을 스스로 뒤집은 것**이다. 이제 같은 분야가 사흘 연속 나온다 —
문서 한 편으로 세 난이도를 뽑는다는 목표와 근본적으로 맞바꿀 수 없는 부분이다. 대신 얻은 것이
더 크다고 판단했다: 문제에 근거 문서가 생겨 환각이 줄고, 학습자는 막혔을 때 돌아가 읽을 곳이 생긴다.

**24칸 순환은 지우지 않고 폴백으로 남겼다.** 문서 생성이 실패했거나 검수에서 거절된 주기에는
근거가 없는데, 그때 "이번 주기의 난이도"를 그대로 쓰면 주기가 헛도는 동안 같은 분야만 계속
나온다. 폴백에서는 옛 규칙으로 돌아가 분야를 매일 바꾸는 편이 낫다 — 최소한 다양성은 확보된다.

> 계산식과 오늘이 며칠차인지 세는 법은 [16-llm-pipeline-operations §2](16-llm-pipeline-operations.md#2-4일-주기--오늘-무엇이-나오는가).

#### 재료 검사 — 난이도 하나, 유형 하나

문서를 근거로 삼기 전에 **두 가지를 미리 본다.** 둘 다 API를 부르기 전이라 막히면 요금이 0이다.

| 축 | 무엇을 보나 | 없으면 |
|---|---|---|
| 난이도 | 그 난이도가 캘 절이 있는가 (`SOURCE_SECTIONS`) | 폴백 — 모델 지식으로 그날 치를 만든다 |
| 유형 | 짝짓기라면 표가 4행 이상 있는가 (`TypeMaterialRule`) | 폴백 |

문서를 `--document-date`로 **지목한** 실행에서는 폴백하지 않고 그 자리에서 실패한다. 사람이
문서를 콕 집어 부른 것이라, 근거 없는 문제를 대신 만들어 주는 것은 요청과 다른 일을 하는 것이다.

유형 검사가 짝짓기에만 있는 이유는 **셀 수 있는 것이 표뿐이어서다.** 순서 배열에 필요한
"인과로 이어진 단계"는 표처럼 셀 수 없고, 절차가 없는 주제에 절을 강요하면 모델이 절을 지어낸다.
그건 재료를 보장하는 것이 아니라 *재료가 있는 척*을 보장하는 것이라 그만두었다 — 순서 배열은
사람이 문서를 보고 고른다.

표 4행은 **필요조건이지 충분조건이 아니다.** 행이 넷 있어도 설명이 서로 배타적이지 않으면 문제가
성립하지 않는데, 그건 뜻을 읽어야 아는 것이라 코드로 잴 수 없다. 이 검사가 막는 것은 "재료가
아예 없는 문서에 요금을 쓰는 것" 하나뿐이고, 나머지는 `ProblemItemRule`의 짝짓기 검사와 검수자가 잡는다.

> 2026-09-01 실측: 문서 10편 중 8편 통과(7~21행), 표가 없는 옛 문서 2편 차단.
> 같은 날 프롬프트도 고쳤다 — 짝짓기 재료로 `## 바탕이 되는 개념`만 지목하고 있었는데
> 그 절에 표가 있는 문서는 10편 중 1편뿐이었다. 이제 `### 용어 한눈에`도 함께 가리킨다.

### 3) 로컬 쪽 — 앱을 켤 때 벌어지는 일

`DraftImportRunner`(ApplicationRunner)가 `generated/`를 훑어 아직 안 가져온 파일을 찾고,
`DraftImportService`가 파일 하나씩 초안으로 들여온다.

- **파일 하나 = 트랜잭션 하나.** 초안 저장과 "들여오기 완료" 기록은 함께 성공하거나 함께
  실패해야 한다(갈라지면 중복 들여오기 또는 그날 문제 증발). 반대로 여러 파일을 한 트랜잭션으로
  묶지는 않는다 — 3일 치 중 하루가 깨졌다고 나머지를 롤백하면 손해다.
- **스캔과 들여오기를 다른 빈으로 나눈 이유**: 같은 클래스 안에서 자기 `@Transactional` 메서드를
  호출하면 스프링 프록시를 거치지 않아 **트랜잭션이 조용히 무시된다.** 흔히 놓치는 함정이라
  구조적으로 막았다.
- **파일을 신뢰하지 않는다.** 커밋된 JSON은 사람이 손으로 고칠 수 있으므로, 들여올 때
  `LlmProblemService.saveDrafts`의 규약 검증(객관식 정답 정확히 1개 등)을 반드시 거친다.
  **관리자 버튼으로 만든 문제와 완전히 같은 문을 통과한다** — 승인 시
  `AdminProblemService.create`를 재사용한 것과 같은 단일 경로 원칙이다.
- 한 파일이 깨져도 나머지는 들어오고, **부팅 자체는 실패시키지 않는다.** 문제 생성은 부가
  기능인데 이것 때문에 앱이 안 뜨면 퀴즈 풀이 같은 본 기능까지 죽는다.

### 4) 들여오기 이력 테이블 (V7)

`imported_draft_file` — 파일명이 PK다.

- **파일명이 곧 그 배치의 신원**이라 자연키를 PK로 썼다. 대리키 + UNIQUE 조합도 가능하지만,
  그러면 이 테이블의 유일한 목적(중복 방지)이 PK가 아닌 부가 제약에 의존한다.
  자연키 PK면 애플리케이션 검사가 빠져나가도 INSERT가 실패한다(이중 안전장치).
- **초안이 0건이어도 기록을 남긴다.** 모델이 규약을 다 어겨 한 문제도 못 건진 파일을
  매 부팅마다 다시 읽고 다시 버리는 낭비를 막기 위해서다. (그래서 초안 테이블에
  `source_file` 컬럼을 얹는 대안을 버렸다 — 0건인 파일은 흔적이 안 남는다.)

## 보안

### 개선된 점 — 키가 내 PC에서 사라졌다

기존 구조로 배치를 살리려면 `ANTHROPIC_API_KEY`를 **PC에 영구 등록**해야 했다
(사용자 환경변수 = 레지스트리 `HKCU\Environment`에 **평문** 저장, 내 계정으로 도는
아무 프로그램이나 읽을 수 있음). 지금은 키가 GitHub 암호화 시크릿에만 있고, 실행 순간에만
임시 러너로 풀린 뒤 러너와 함께 폐기된다.

### 적용한 대응

| 위험 | 대응 | 위치 |
|---|---|---|
| 서드파티 액션 탈취 → 같은 job의 키 유출 | **액션을 커밋 SHA로 고정**(태그는 가변) | `llm-daily.yml` uses 절 |
| 수동 입력값으로 셸 명령 조작(스크립트 인젝션) | 입력을 명령에 직접 박지 않고 **환경변수로 전달** | `llm-daily.yml` 생성 스텝 |
| 워크플로 권한 과다 | `permissions: contents: write`만 명시 | `llm-daily.yml` 상단 |
| LLM 텍스트가 화면에서 실행(저장형 XSS) | 지문 출력 시 `escapeHtml` — **기존에 이미 적용됨** | `player.js` |
| 포크 PR이 시크릿 탈취 | 트리거가 `schedule`/`workflow_dispatch`뿐이라 기본 브랜치에서만 실행. `pull_request_target`은 **절대 쓰지 않는다** | `llm-daily.yml` on 절 |

### 구조적으로 안전한 이유

Actions가 커밋하는 건 **데이터 파일이지 코드가 아니다.** 실행되지 않고, 내가 승인 버튼을
누르기 전까지 정식 문제가 되지도 않는다. 즉 자동화가 손댈 수 있는 최대 범위가
**"검수 대기함에 종이 한 장 넣기"**로 물리적으로 제한된다. 이건 우연이 아니라 ADR-0006에서
초안을 별도 테이블로 격리해 둔 덕분이다 — **좋은 경계는 나중에 다른 문제까지 막아 준다.**

## 운영 메모 (알고 있어야 할 한계)

- **예약 시각은 보장이 아니라 최선노력.** GitHub의 `schedule`은 혼잡하면 밀린다. 특히
  정시(`:00`)가 가장 붐벼서 일부러 `:17`을 골랐다. 몇십 분 밀려도 무해한 작업이라 감수한다.
  **실측: 48~50분 지연**(2026-08-12 07:05 시작 / 08-13 07:05 시작, 예약은 06:17).
  두 번 모두 비슷하게 밀린 걸 보면 이 정도가 이 시간대의 평상값이다 — cron은 건드리지 않는다.
- **cron은 UTC.** `17 21 * * *` = 한국시간 06:17. 날짜 계산은 CLI가 `Asia/Seoul`로 하므로
  워크플로와 파일명이 어긋나지 않는다.
- **60일 무활동 시 예약이 자동 해제된다**(공개 저장소 정책). 봇의 매일 커밋이 이 타이머를
  리셋해 주는지는 확인되지 않았다 — **두 달쯤 뒤 Actions 탭에서 한 번 확인할 것.**
- **`GITHUB_TOKEN`으로 만든 커밋은 다른 워크플로를 트리거하지 않는다.** 무한 루프가 원천
  차단되는 좋은 성질이고, 덕분에 데이터 파일 커밋으로 `ci-cd.yml`이 헛돌지 않는다.
- **`_existing-questions.json`은 스냅샷이라 시간이 지나면 낡는다.** 다만 승인된 문제는
  원래 `generated/*.json`에서 온 것이라 이미 회피 목록에 있으므로, 낡음의 영향은 제한적이다.
  이 파일은 **앱을 켤 때마다 `ExistingQuestionsExporter`가 자동으로 갱신**한다(분야별 최근 50건).
  손으로 관리하던 시절에는 갱신을 잊으면 조용히 낡았는데, 그 구멍을 메운 것이다 — 대신
  **커밋은 여전히 사람이 해야** 다음 배치에 반영된다.

## 설정

```yaml
llm:
  generation:
    model: claude-opus-5   # CLI도 이 값을 읽는다(설정의 단일 출처)
    batch-enabled: true    # 중단 스위치 (아래 참고)
    batch-type: auto       # 무엇을 만들지 — auto | problem | document (아래 참고)
    batch-count: 5
    batch-domains: NETWORK,OS,DATABASE,...   # 이 순서가 곧 날짜 순환 순서
  import:
    enabled: true          # 들여오기만 따로 끌 수 있다
    dir: generated         # Actions가 커밋하는 위치와 반드시 같아야 한다
```

`batch-cron`은 제거했다 — 예약 시각은 이제 워크플로의 `schedule`이 정한다.

> 각 값의 의미와 우선순위는 [16-llm-pipeline-operations §3](16-llm-pipeline-operations.md#3-설정--applicationyml).

## 배치를 멈추는 방법

멈출 수 있는 지점이 **네 군데**이고, 목적이 다르다.

| 무엇을 멈추나 | 방법 | 언제 쓰나 |
|---|---|---|
| 생성 (요금이 나가는 쪽) | Actions 탭 → "Disable workflow" | **급할 때.** 버튼 한 번, 즉시 반영 |
| 생성 | `llm.generation.batch-enabled: false` | **오래 꺼둘 때.** 이유가 커밋 이력에 남는다 |
| 문서 또는 문제 **한쪽만** | `llm.generation.batch-type: problem`\|`document` | 한쪽만 보고 싶을 때 |
| 들여오기 (파일 → 검수함) | `llm.import.enabled: false` | 파일은 쌓되 검수함은 비워 두고 싶을 때 |
| 진행 중인 1회 | Actions에서 Cancel workflow | 이미 API를 호출했다면 요금은 나간다 |

### batch-type — "전부 아니면 전무"가 아닌 스위치

`batch-enabled`만 있던 시절에는 **한쪽만 끄는 방법이 없었다.** 있는 건 전부 중단과,
수동 실행에서 그 한 번만 유효한 `type` 입력뿐이었다.

- `document`를 "매일 문서"가 아니라 **"문서일에만"**으로 정한 이유: 매일 만들면 요금이 네 배가
  된다. 이 스위치는 "한쪽만 보고 싶다"는 도구이지 주기를 바꾸는 도구가 아니다.
- `problem`에는 부작용이 있다. 문서를 안 만들면 근거로 삼을 문서가 안 생겨 **배치가 계속
  폴백으로 돈다** — 문제들이 서로 남남이던 2단계 이전으로 돌아간다.
- **모르는 값(오타)은 `auto`로 본다.** 오타 하나로 배치가 통째로 멈추는 것보다 평소대로 도는
  편이 낫다 — 이 프로젝트가 겪은 사고는 "안 도는 걸 몇 주 뒤에 알아차린" 쪽이었다.
- `application.yml`의 **키 이름이 CLI가 읽는 이름과 같은지도 테스트로 묶었다**
  (`DraftGeneratorCliTest.configKeyMatchesWhatCliReads`). 어긋나면 값이 영영 전달되지 않는데
  배치는 오류 없이 `auto`로 돌아서, 설정한 사람은 한참 뒤에야 알아차린다.

**왜 설정 스위치를 따로 두는가.** GitHub의 Disable 버튼이 더 빠른데도 굳이 둔 이유는
**발견 가능성** 때문이다. 버튼은 GitHub 화면 깊숙한 곳에 있어서, 몇 주 뒤 "왜 요즘 문제가
안 들어오지?" 할 때 원인을 찾기 어렵다. 설정 파일에 적혀 있으면 코드만 보고도 알 수 있고,
**언제 왜 껐는지가 커밋 메시지에 남는다.** 반대로 급한 정지에는 커밋·푸시가 필요한 설정보다
버튼이 낫다 — 그래서 둘 다 둔다.

`batch-enabled: false`일 때 CLI는 API를 부르지 않고 **종료 코드 0으로 정상 종료**한다.
실패로 죽이면 매일 알림 메일이 오고, 그러면 진짜 사고 알림까지 무시하게 된다
("의도된 중단"은 실패가 아니다).

### force — 꺼 둔 채로 한 번만 돌리기

수동 실행(workflow_dispatch)의 `force` 입력을 켜면 `batch-enabled=false`여도 이번 한 번만
생성한다. **이 구멍이 필요한 이유**: 스위치가 절대적이면, 꺼 둔 상태에서 문제 하나가 급할 때
"설정을 true로 커밋 → 실행 → 다시 false로 커밋"을 해야 한다. 되돌리기를 잊으면
**끈 줄 알았던 배치가 계속 돈다** — 스위치를 둔 목적이 무너진다. force는 저장소 설정을
건드리지 않으므로 "한 번만 예외"가 영구 변경으로 새지 않는다.

예약 실행은 `inputs.force`가 비어 있어 항상 꺼진 채로 넘어간다 —
**예약이 스스로 중단 스위치를 무시하는 일은 구조적으로 불가능하다.**

## 거절 사례 되먹이기 (검수 → 생성 루프)

검수자가 거절한 문제와 그 사유를 다음 생성 프롬프트에 넣어, 같은 실수를 반복하지 않게 한다.

```
[검수자가 거절]  →  generated_problem_draft.reject_reason
       ↓
 ┌──────────────────────┬─────────────────────────────────┐
 │ 관리자 수동 생성        │ 일일 배치(GitHub Actions)         │
 │ DB 직접 조회            │ RejectionNotesExporter           │
 │ → 거절 즉시 반영        │  → generated/_rejection-notes.json │
 │                       │  → (사용자가 커밋) → DraftGeneratorCli │
 └──────────────────────┴─────────────────────────────────┘
       ↓ 두 경로가 같은 RejectionNote 타입으로 합류
  ClaudeProblemGenerator가 프롬프트 문장으로 조립 (조립은 한 곳에서만)
```

프롬프트에는 이렇게 들어간다.

```
[과거 거절 사례] 아래는 검수자가 실제로 거절한 문제와 그 사유다. 같은 실수를 반복하지 마라:
- "다음 중 옳지 않은 것은?" → 거절 사유: 부정형 문제라 검수 비용이 크다
```

**왜 값어치가 있나.** `SYSTEM_PROMPT`의 금지 규칙이 "일반론"이라면 이건 **"판례"**다.
우리 검수자가 실제로 무엇을 탈락시켰는지는 **이 서비스에만 있는 데이터**라, 아무리 좋은
범용 프롬프트로도 얻을 수 없는 신호다. 사람이 검수할수록 다음 생성이 좋아지는 루프가 된다.

### 설계 메모

- **사유만이 아니라 지문도 함께 넣는다.** "부정형 금지"만 던지면 모델은 그것이 어떤 문제를
  두고 한 말인지 모른다. 짝지어 주면 구체적 사례가 되어 신호가 훨씬 강해진다.
- **도메인으로 거르지 않는다.** 거절 사유는 대개 분야를 가리지 않는 출제 품질 문제라,
  네트워크 문제를 만들 때도 운영체제 문제의 거절 이유가 그대로 교훈이 된다. 도메인별로
  나누면 표본이 잘게 쪼개져 대부분의 칸에서 0건이 되어 기능이 무력해진다.
- **사유가 없는 거절은 제외한다.** 사유는 선택 입력이라 NULL일 수 있는데, 이유 없이 지문만
  주면 "왜인지 모르지만 나쁘다"는 말이 되어 도움이 안 된다.
- **최근 20건까지.** 회피 목록(50)보다 적은 이유는 목적이 다르기 때문 — 회피 목록은 빠지면
  중복이 나지만, 거절 사례는 **패턴을 보여주는 것**이라 20건이면 반복되는 실수가 충분히 드러난다.
- **이력이 없으면 블록 자체를 넣지 않는다.** 빈 제목만 남으면 모델이 "사례가 없다"를
  "기준이 없다"로 읽을 수 있고 토큰도 낭비다.

### 스냅샷 파일과 커밋

배치 쪽은 DB를 볼 수 없으므로 `_rejection-notes.json`을 거쳐야 한다. **앱을 켤 때마다**
최신 사례로 갱신되고, 갱신되면 로그로 알려 준다.

```
거절 사유 스냅샷 갱신: generated\_rejection-notes.json (3건) — 커밋하면 다음 배치부터 반영됩니다
```

- **내용이 같으면 파일을 다시 쓰지 않는다.** 매 부팅마다 "내보낸 시각"만 바뀐 파일을 쓰면
  앱을 켤 때마다 git이 변경으로 인식해서, **정작 진짜 새 거절이 생긴 날을 알아볼 수 없다.**
  그래서 시각은 날짜 단위로만 기록하고 비교는 사례 목록으로만 한다.
- **앱이 직접 `git push`를 하지 않는 이유**: 애플리케이션이 자기 소스 저장소에 쓰기를 시작하면
  권한·인증·충돌 처리가 줄줄이 따라온다. 하루 한 줄 커밋을 아끼자고 앱에 git 클라이언트를
  심는 것은 손해다.

## 앞으로 — 문제 품질을 더 올리려면

현재 프롬프트(`ClaudeProblemGenerator.SYSTEM_PROMPT`)는 이미 오답 보기 조건·해설 요구·금지
사항을 담고 있고, 거기에 위의 거절 사례 되먹이기가 더해졌다. 남은 수단을 **가성비 순**으로:

1. **좋은 문제 예시(few-shot) 주입** — 승인된 문제 2~3개를 프롬프트에 실물로 보여 준다.
   추상적 기준보다 실물 예시가 훨씬 강한 신호다(난이도 규칙에서 이미 확인한 효과).
   거절 사례가 "이러지 마라"라면 이건 "이렇게 해라"로, 짝을 이루면 효과가 커진다.
2. **생성량을 늘리고 골라 쓰기** — 5개를 만들어 5개를 다 검수하는 대신 8개를 만들어
   좋은 5개만 승인한다. 비용은 오르지만 승인율이 아니라 **최종 품질**이 올라간다.
3. **자기 검증 한 번 더**(2단계 생성) — 만든 문제를 모델에게 다시 "사실 오류·중복 정답이
   있는지" 검토시킨다. 비용이 두 배 가까이 오르므로 승인율이 낮을 때만.
4. **thinking effort 상향** — 마지막 수단. 사고 토큰이 전부 **출력** 요금이라 비용이 크게
   뛴다(입력의 5배 단가). 위를 다 해 보고도 아쉬울 때.

**측정 없이 바꾸지 않는다**가 원칙이다. 바꾸기 전 승인율을 먼저 기록해 둔다 —
**관리자 대시보드 → "AI 초안 승인율"**에서 모델별로 볼 수 있다.

> 이 표는 한동안 **없었다.** `model` 컬럼을 "모델별 승인율 비교용"으로 기록해 두고도 정작
> 볼 수단을 만들지 않아, 재료만 모으고 저울이 없는 상태로 지냈다(2026-08-13 최종 점검에서 발견).
> **측정하겠다고 적어 두는 것과 측정할 수 있는 것은 다르다.**

## 면접 대본 요약

"일일 배치를 앱 안의 `@Scheduled`로 만들었는데, 개인 PC에서 도는 앱이라 예약 시각에
컴퓨터가 꺼져 있으면 배치가 아예 실행되지 않는다는 걸 실제로 겪었습니다. 초안이 0건인 걸
보고 원인을 찾았죠. 프로덕션이라면 k8s CronJob이나 Cloud Scheduler를 썼겠지만, 이 작업은
사용자 대면이 아니고, 하루 밀려도 무해하고, 멱등하고, 결과물이 저장소 콘텐츠라서 —
상시 서버 없이 GitHub Actions로 옮기고 결과를 저장소에 커밋한 뒤 앱이 기동할 때 들여오는
구조로 바꿨습니다. 클라우드에는 DB가 없어서 '가장 부족한 칸 선택'을 날짜 기반 순환으로
바꿔야 했는데, 적응력을 잃는 대신 '매일 같은 칸만 뽑히는' 기존 버그가 원천 불가능해지는
이득이 있었습니다. 부수 효과로 실패 시 메일 알림이 생겨서 별도로 두고 있던 주간 감시
테스트를 없앨 수 있었고요. **설계 문서에 적어 둔 판단이 틀린 게 아니라, 그 판단이 딛고 선
가정이 틀렸다는 걸 실측으로 발견한 사례**입니다."
