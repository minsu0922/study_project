# CS 지식베이스 & 문제풀이 플랫폼 (csquiz) — 프로젝트 요약

> `docs/` 폴더의 설계 문서 16개 + ADR 6개를 이력서/포트폴리오 제출용으로 한 파일에 압축.
> 원본 문서가 더 상세하니, 면접에서 깊게 파고들 질문이 나오면 해당 번호 문서를 참고.
> 최종 갱신 2026-08-13.

---

## 1. 한 줄 소개

**백엔드 CS 개념(인덱스, 캐싱, 인증, 요청 제한, 스키마 관리 등)을 하나씩 실제로 구현하고
성능을 직접 측정하며 검증한 학습형 포트폴리오 프로젝트.**
단순히 "만들었다"가 아니라 매 기술 선택마다 대안을 비교하고, 왜 그 선택을 했는지를
ADR(Architecture Decision Record)로 남겼고, 핵심 주장(인덱스 효과 등)은 실측 데이터로 뒷받침했다.

- **기간**: 2026-06 ~ 2026-08 (MVP → 로드맵 1~7 전부 완료 + AI 생성 파이프라인 3단계)
- **형태**: 1인 개발, 백엔드 중심(Spring Boot) + 정적 HTML/JS 프론트엔드
- **기술 스택**: Java 21 · Spring Boot 3.4.1 · MySQL 8(InnoDB) · Spring Data JPA + QueryDSL ·
  Spring Security(JWT) · Redis 7 · Flyway · Docker Compose · JUnit5 + Testcontainers ·
  GitHub Actions(CI/CD) · Claude API(LLM 문제 생성)

## 2. 이력서에 바로 쓸 수 있는 요약 문장 (예시)

- CS 개념 학습을 위해 Spring Boot 기반 문제풀이 플랫폼을 설계·개발하고, 모든 기술적 의사결정을
  ADR로 문서화(6건)하여 트레이드오프 근거를 남김.
- 제출 이력 50만 건 규모의 부하 테스트를 진행해 복합 인덱스 적용 시 API 응답 시간을
  **1.8초 → 16ms(약 100배)**로 단축, 실행계획(EXPLAIN ANALYZE) 기반으로 성능 개선을 실증.
- QueryDSL DTO 프로젝션 도입으로 목록 조회 API의 N+1 쿼리를 **10회 → 2회**로 구조적으로 고정하고,
  불필요한 대용량 컬럼(LONGTEXT) 전송을 제거.
- Claude API 기반 콘텐츠 생성 파이프라인을 구축(초안 격리 → 사람 검수 → 정식 등록)하고,
  실행 주체를 앱 내부 스케줄러에서 **GitHub Actions로 이전** — 개인 환경 의존으로 배치가
  실행되지 않던 문제를 실측으로 발견하고 구조를 재설계.
- 자체 점검으로 **커버리지가 25%로 떨어져 있던 스케줄링 결함**을 발견·수정하고,
  구현이 아닌 **불변 성질을 검증하는 회귀 테스트**를 추가해 재발을 차단.
- Redis Lua 스크립트로 토큰 버킷 알고리즘을 직접 구현해 요청 제한(rate limiting) 기능을 추가,
  로그인 무차별 대입 공격을 분당 5회로 제한하면서도 fail-open 정책으로 가용성을 보존.
- 에빙하우스 망각곡선 기반 간격 반복 복습 추천 기능을 설계해 별도 상태 테이블(`ReviewItem`)로
  분리, DB UNIQUE 제약으로 동시성 경합을 코드 없이 방지.
- Claude API 구조화 출력(Structured Output)을 활용한 LLM 문제 자동 생성 파이프라인을 구축,
  초안 격리 테이블 + 관리자 승인 게이트로 AI 환각(hallucination) 리스크를 구조적으로 차단.
- GitHub Actions로 빌드·테스트·Docker 이미지 배포(GHCR)를 자동화하는 CI/CD 파이프라인 구축,
  CI 환경에서만 재현되는 마이그레이션 FK 위반·요청 제한 오탐 버그 2건을 발견해 수정.

## 4. 데이터 모델 핵심

- **User / Document / Tag / Problem / Choice / Submission**을 뼈대로, `DocumentTag`·`ProblemTag`
  M:N 연결 테이블로 태그 검색을 지원.
- 오답노트는 별도 테이블 없이 `Submission` 조회 기반(파생 뷰)으로 시작 — 불필요한 사전 설계를
  피하고, 복습 기능처럼 "고유 상태"가 필요해지는 시점에만 테이블을 분리(ADR-0002 → ADR-0004).
- 문제 타입별 채점 로직: 객관식(Choice.is_correct) / OX(대소문자 무시 비교) / 단답형(`|` 구분
  복수 정답, trim+lowercase 비교) / 서술형(MVP 미지원).
- 모든 FK에 명시적 인덱스, 참조 무결성은 CASCADE/RESTRICT를 데이터 성격(이력 vs 상태)에 따라 구분.

## 5. 인증/보안

- JWT access 토큰만 발급(MVP), subject는 이메일이 아닌 사용자 id(불변값), role 클레임으로
  DB 조회 없이 권한 판단.
- BCrypt로 비밀번호 해시, Stateless 세션(SessionCreationPolicy.STATELESS) + CSRF 비활성화
  (쿠키 기반 세션이 아니므로 CSRF 표면 자체가 없음).
- 인증/인가 실패(필터 단계)도 `@RestControllerAdvice`가 못 잡는 지점이라 별도
  EntryPoint/AccessDeniedHandler로 동일한 공통 응답 포맷을 유지.

## 6. 공통 응답 & 에러 처리

- 모든 API 응답을 `{success, data, error}` 고정 포맷(envelope)으로 통일.
- 에러 코드는 `{도메인}_{3자리}` 체계(`AUTH_001`, `QUIZ_002` 등)로 클라이언트가 코드 기반 분기 가능.
- `@RestControllerAdvice` 하나로 검증 오류/비즈니스 예외/시스템 예외를 전부 흡수.

## 7. 성능 실측 (로드맵 1)

- 제출 50만 건 + 문제 10만 건 규모로 부하를 만들어 실측:
  - 오답노트 조회: 복합 인덱스(`user_id, is_correct, submitted_at`) 유무에 따라
    **API 응답 12~17ms ↔ 1,081~1,769ms**, 읽은 행 수 5행 ↔ 50만 행.
  - 부수 발견: 해당 인덱스가 FK 제약의 기반 인덱스를 겸하고 있어 단순 DROP이 거부됨
    → 인덱스는 조회 성능뿐 아니라 제약조건의 기반이라는 것을 실습으로 확인.
  - `ORDER BY RAND()` 방식은 10만 건에서 15배 느려짐을 확인, 다만 현재 규모(수백 문제)에선
    과최적화라 판단해 개선을 보류(측정 기반 의사결정).
- 문서 목록 API의 N+1 쿼리를 QueryDSL DTO 프로젝션으로 해결: **10쿼리 → 2쿼리(설정과 무관하게
  고정)**, 목록에 불필요한 LONGTEXT 본문 전송도 함께 제거.

## 8. 요청 제한(Rate Limiting)

- 토큰 버킷 알고리즘을 Redis + Lua 스크립트로 직접 구현(라이브러리 미사용) — 고정 윈도우의
  경계 문제(순간 2배 통과)를 피하고, 원자성(check-then-act 경쟁 상태 방지)을 직접 다룸.
- 로그인/회원가입: IP 기준 분당 5회. 그 외 API: 사용자 id 기준 분당 60회(NAT 공유·IP 우회 문제
  동시 해결).
- Redis 장애 시 fail-open(전부 통과 + 경고 로그) — 보조 장치의 장애가 서비스 전체 장애로
  번지지 않게 하는 설계 철학을 캐싱·rate limiting에 일관되게 적용.

## 9. 복습 추천(간격 반복)

- 에빙하우스 망각곡선 기반, Leitner 방식의 고정 간격 사다리(`1일 → 3일 → 7일 → 14일 → 30일 → 졸업`).
- `ReviewItem` 테이블 분리 근거: "다음 복습일·복습 단계"가 이력에서 파생 불가능한 고유 상태가
  되는 시점을 ADR-0002에서 미리 트리거로 적어두고 그대로 실행.
- SM-2(Anki 방식) 대신 고정 간격을 택한 이유: SM-2의 핵심 입력(자가 평가)이 우리 시스템엔
  없고(채점이 정오 2값뿐), 입력 해상도에 맞지 않는 알고리즘은 복잡도만 늘리기 때문(ADR-0004).
- 채점 API(`POST /api/quiz/submit`) 하나로 오답노트·복습 상태·오늘의 퀴즈 진행률을 모두 갱신
  — 쓰기 경로를 하나로 유지해 정합성 관리 지점을 최소화.

## 10. 오늘의 퀴즈(데일리 세트, 습관 형성)

- 복습(4) + 취약 도메인(3) + 신규(3) 배합으로 매일 개인화된 10문제 세트를 제공.
- 세트를 DB에 저장 + "그날 첫 조회 시 지연 생성"하는 방식 채택 — 로컬 PC 환경(항상 켜져
  있지 않음)에서 자정 배치보다 안정적이라는 실행 환경 제약을 근거로 선택(ADR-0005).
- 동시 접속 경합은 애플리케이션 코드가 아니라 DB `UNIQUE(user_id, quiz_date)` 제약으로 차단.
- 스트릭(연속 학습일)은 저장하지 않고 조회 시점에 계산 — "시간이 흐르면 바뀌는 값은 저장하지
  않는다"는 설계 원칙을 일관되게 적용.

## 11. LLM 문제 자동 생성 (B안)

- Claude API의 구조화 출력(JSON 스키마 강제)으로 파싱 실패 가능성을 원천 제거.
- 생성된 문제는 바로 출제되지 않고 별도 초안 테이블(`generated_problem_draft`)에 PENDING으로
  격리 → 관리자 승인 시에만 정식 문제로 등록 — AI 환각으로 인한 오답 노출을 구조적으로 차단.
- "가장 비어 있는 도메인×난이도 칸"을 자동 선택해 생성(빈 칸 채우기 전략), 프롬프트에 기존
  문제 목록을 실물로 포함시켜 중복 생성 방지.
- Claude 호출을 DB 트랜잭션 밖에서 수행 — 외부 API 지연이 커넥션 풀을 점유하지 않도록 설계.

## 11-2. 생성 배치를 앱에서 GitHub Actions로 이전

- 일일 생성 배치를 앱 내부 `@Scheduled`로 만들었으나, **개인 PC에서 도는 앱이라 예약 시각에
  컴퓨터가 꺼져 있으면 배치가 한 번도 실행되지 않는다**는 것을 초안 0건으로 확인.
  "하루쯤 건너뛴다"와 "한 번도 안 돈다"는 다른 문제였고, **설계 판단이 딛고 선 가정이
  틀렸다는 것을 실측으로 발견**한 사례.
- 실행 주체를 GitHub Actions로 옮기고, 결과를 저장소에 커밋 → 로컬 앱 기동 시 흡수하는
  구조로 전환. 부수 효과로 **실패 시 메일 알림**이 생겨 별도 감시 워크플로를 폐기.
- 클라우드 러너에는 DB가 없어 "가장 부족한 칸 선택(GROUP BY 집계)"을 **날짜 기반 결정적
  순환**으로 대체. 적응력을 잃는 대신 "검수를 미루면 매일 같은 칸만 뽑히는" 기존 버그가
  정의상 발생 불가능해지는 이득.
- DB에만 있는 정보(기존 지문·거절 사유·거절된 문서)는 **스냅샷 파일**로 내보내 저장소를
  경유시킴. 앱에 git 클라이언트를 심지 않기 위한 선택이며, 파일이 오래되면 배치가
  Actions 요약 화면에 경고한다.

## 11-3. 개념 문서 생성 → 그 문서를 근거로 한 출제

- "문제들이 단발성 지식이라 깊이 있는 이해로 이어지지 않는다"는 진단에서 출발.
  **4일 주기**로 재구성: 0일차에 개념 문서 1편, 1~3일차에 그 문서를 근거로 초급·중급·고급 문제.
- 문제에 근거 문서를 `document_slug`로 **느슨하게 연결**(FK 아님) — 문제 초안이 문서 승인보다
  먼저 존재할 수 있기 때문. 오답 화면에서 "이 개념 문서 읽기" 링크로 이어진다.
- LLM이 쓴 문서는 3,000자가 넘어 사람이 형식 결함을 놓치므로 **자동 검증**을 붙임(필수 절 누락,
  코드블록 밖 HTML 태그, slug 형식). **코드블록 안은 예외 처리** — 없었다면 XSS·SQL 인젝션 같은
  보안 주제 문서가 매번 반려됐을 것.
- 검수 실수를 되돌릴 수 있게 **복구(restore)** 기능 추가. 되돌릴 수 없으면 거절 버튼을 누르는
  것 자체가 부담이 되어 검수가 밀린다.

## 11-4. 스스로 발견해 고친 결함 (자동화 최종 점검, 2026-08-13)

- **개념 문서의 분야 선택만 옛 규칙을 쓰고 있었다.** 문서일은 에포크일이 4의 배수인 날인데
  옛 규칙은 분야를 8로 나눈 나머지로 골라서, **후보 8개 중 2개만 무한 반복**되고 나머지 6개
  분야는 문서를 영영 못 받는 상태였다. 문제까지 문서 분야를 따라가므로 기능 전체의 커버리지가
  25%로 떨어져 있었다.
- **규칙에는 테스트가 촘촘했지만 그것을 쓰는 쪽은 아무도 보지 않았다.** 게다가 분야를 맞춰 주는
  안전장치가 매일 발동하며 결과를 그럴듯하게 만들어 **증상까지 가려 주고 있었다.**
  → 안전장치가 상시 발동하면 그건 본선이 고장 났다는 신호라는 교훈.
- 수정은 한 줄이지만 판단을 이름 있는 함수로 분리하고, 구현을 모방하는 대신 **"한 바퀴(32일)에
  모든 분야가 한 번씩"이라는 성질**을 검사하는 테스트를 붙였다(옛 규칙으로 되돌려 실패하는 것까지 확인).

## 12. Flyway (DB 스키마 버전 관리)

- 모든 스키마 변경을 `V__` 파일로 순서대로 누적(수정 금지, 새 파일로만 정정), 뷰 등 멱등한
  대상은 `R__`로 분리.
- `ddl-auto=validate` + Flyway 조합 — JPA는 엔티티-테이블 일치만 검증하고, 스키마의 주인은
  Flyway가 맡는 역할 분리.
- **콘텐츠 시드를 마이그레이션에서 제거**(V2·V3 삭제): 문제·문서를 INSERT로 하드코딩했더니
  ① 수정 경로가 관리자 화면과 마이그레이션 둘로 갈리고 ② 시드 간 FK 순서 사고로
  `out-of-order` 설정까지 켜야 했으며(Flyway의 전제를 스스로 무너뜨림) ③ 삭제한 문제가
  배치 스냅샷에 유령으로 남았다. **구조는 마이그레이션, 콘텐츠는 애플리케이션**으로 정리.

## 13. CI/CD (로드맵 5)

- GitHub Actions로 빌드 → 테스트 → GHCR(GitHub Container Registry) 이미지 push 파이프라인 구축.
- CI 환경에서만 재현되는 버그 2건을 발견·수정: 빈 DB에서의 V3 마이그레이션 FK 위반,
  요청 제한(rate limit) 관련 429 오탐(로컬에서는 재현 안 됨 — CI 특유의 타이밍/환경 차이로 발견).

## 14. 테스트

- JUnit5 + Testcontainers로 JWT 발급, 인증 서비스, HTTP 인증 흐름 등 통합 테스트 작성.
- 테스트가 실제 버그를 잡은 사례: LLM 초안 승인 API의 "이미 처리됨" 검사 순서 결함,
  RefreshTokenStore의 Redis 장애 미처리.

## 15. 설계 전반에 걸친 일관된 원칙 (면접에서 강조 포인트)

1. **파생 가능한 값은 저장하지 않는다** — "미복습 여부", "스트릭", "복습 완료 여부(due)" 등은
   컬럼이 아니라 조회 시점 계산. 배치로 매일 갱신해야 하는 상태를 애초에 만들지 않음.
2. **동시성 경합은 애플리케이션 코드가 아니라 DB 제약(UNIQUE)으로 방지** — ReviewItem,
   DailyQuiz 양쪽에 동일 패턴 재적용.
3. **보조 장치의 장애가 서비스 전체 장애가 되지 않게(fail-open)** — 캐시, refresh 토큰,
   rate limiting에 일관되게 적용.
4. **데이터에 "고유 상태"가 생기는 시점에만 테이블을 분리** — 오답노트(조회 기반) →
   복습(ReviewItem 분리)로의 전환을 ADR에 미리 트리거로 남기고 실제로 그 시점에 이행.
5. **측정 후 결정** — 인덱스 효과, RAND() 성능 저하를 실측하고, "현재 규모에선 과최적화"라는
   판단도 근거를 남김(추측이 아니라 데이터 기반 의사결정).
6. **쓰기 경로는 하나로 유지** — 퀴즈 제출 API 하나가 채점·오답노트·복습 상태·데일리 세트
   진행률을 전부 갱신, 동기화 코드 불필요.
