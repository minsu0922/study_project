# 09. 요청 제한 (Rate Limiting) — 로드맵 3

서버에 "일정 시간 동안 보낼 수 있는 요청 횟수"의 상한을 둔다.
왜 토큰 버킷 + Redis Lua로 직접 구현했는지의 결정 배경은 [ADR-0003](adr/0003-token-bucket-rate-limiting.md).

## 왜 필요한가

| 위협 | 시나리오 | 방어 |
|---|---|---|
| 무차별 대입(brute force) | 로그인 API에 비밀번호를 초당 수천 번 대입 | 로그인 IP당 분당 5회 → 사실상 불가능 |
| 폭주/스크래핑 | 버그 있는 클라이언트·크롤러가 요청을 쏟아냄 | 사용자당 분당 60회 상한 |
| 공유지의 비극 | 한 명의 폭주로 DB가 밀려 **모두가** 느려짐 | 입구(필터)에서 차단, DB 도달 전 |

## 정책 (application.yml `ratelimit.*`)

| 정책 | 대상 | 키 | 한도 | 이유 |
|---|---|---|---|---|
| `auth` | POST /api/auth/login·signup·refresh | IP | 분당 5회 (버스트 5) | 자격 증명을 "맞혀 볼 수 있는" 공격 표면. 사람 손 속도면 충분 |
| `api` | 그 외 /api/** 전부 | 사용자 id (비로그인은 IP) | 분당 60회 (버스트 60) | 정상 사용은 안 막고 폭주만 거르는 널널한 상한 |

- **정적 파일(HTML/CSS/JS)·Swagger는 제외** — 여기서 걸리면 "페이지 자체가 안 열리는" 과잉 차단.
- **로그인 사용자는 IP가 아니라 사용자 id로 센다**: 회사·학교는 수백 명이 IP 하나를 공유하고(NAT),
  반대로 공격자는 IP를 바꿔가며 한도를 회피할 수 있다. id 기준이 양쪽 문제를 모두 푼다.
- **로그아웃은 auth 정책에 안 넣었다**: 맞혀서 얻을 게 없는 경로라 일반 api 정책으로 충분.

## 동작 방식 — 토큰 버킷 (scripts/rate-limit.lua)

사용자마다 양동이(버킷)가 있고 요청 1번 = 토큰 1개 소모. 토큰은 시간에 비례해 다시 차되
최대치(capacity)를 넘지 않는다. 빈 버킷에 온 요청은 거부.

- **버스트 허용**: 페이지 하나가 API 5~6개를 동시에 부르는 정상 패턴을 안 막는다.
  (이게 고정 윈도우 카운터 대비 토큰 버킷의 장점 — 평균 속도만 제한)
- **lazy refill**: 배경 스케줄러 없이, 요청이 왔을 때 "흐른 시간만큼" 몰아서 충전.
- **원자성**: 읽기→계산→쓰기를 Lua 스크립트로 묶어 Redis가 원자적으로 실행 — 동시 요청 경쟁 상태 차단.
- **시각은 Redis TIME**: 앱 서버가 여러 대여도 시계 기준이 하나(clock skew 제거).
- **키 TTL**: "빈 버킷이 가득 차는 시간"만큼만 보관 — 그 뒤엔 새 버킷과 구별 불가이므로 지워도 같다.

키 구조: `rl:{정책}:{user:id|ip:주소}` → 해시 `{tokens, ts}`.

## 거부 응답 (docs/04 확장)

```
HTTP/1.1 429 Too Many Requests
Retry-After: 12

{"success":false,"data":null,"error":{"code":"COMMON_429","message":"요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."}}
```

- **429** = "너무 많이 요청함"의 표준 상태 코드(RFC 6585). **Retry-After** 헤더로
  "몇 초 뒤에 다시 오면 되는지"까지 알려 준다 — 잘 만든 클라이언트는 이걸 보고 백오프한다.
- 필터 단계라 @RestControllerAdvice가 못 잡으므로, JwtAuthenticationEntryPoint와 같은 방식으로
  공통 봉투 JSON을 필터에서 직접 쓴다.

## 장애 정책: fail-open

Redis가 죽으면 **전부 통과**시키고 경고 로그만 남긴다. 제한기(보조 장치)의 장애가
서비스 전체 정지(fail-close)로 번지는 건 주객전도 — 캐시·refresh 토큰과 동일한 철학.
트레이드오프: 장애 동안은 무제한이 된다. 로그로 알아차리고 복구하는 게 전제.

## 필터 위치

```
요청 → JwtAuthenticationFilter(토큰 해석) → RateLimitFilter(제한 판정) → ... → 컨트롤러
```

JWT 필터 **뒤**에 둔 이유: 사용자 id로 세려면 토큰이 먼저 해석돼 있어야 한다.
대가로 제한 전에 JWT 검증 비용을 치르지만 HMAC 검증은 메모리 연산이라 무시할 수준.

## 알려진 한계 (배포 전 점검 목록)

- **X-Forwarded-For 신뢰 문제**: 프록시 없이 직접 노출되면 클라이언트가 이 헤더를 위조해
  IP 제한을 회피할 수 있다. 실 배포에서는 "신뢰하는 프록시(nginx 등)가 덮어쓴 값만 믿는" 구성이 전제.
- **회원가입 IP 제한의 부작용**: 같은 학원/학교에서 단체 가입하면 분당 5회에 걸릴 수 있다.
  문제가 되면 signup만 별도 정책으로 분리.
- **WSL 개발 환경**: WSL2 NAT가 유휴 TCP 연결을 조용히 끊어 Redis 명령이 타임아웃(→ fail-open)될
  수 있다. 트래픽이 이어지면 정상 동작. (로드맵 2의 keepalive/2s 타임아웃 이슈와 동일 뿌리)
