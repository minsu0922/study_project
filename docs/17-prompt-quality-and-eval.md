# 17. 프롬프트 품질 개선과 평가 하네스

> 2026-08-16 ~ 08-17 작업. 시작은 "초급 문제가 초급 같지 않다"는 한 줄이었고,
> 끝은 프롬프트를 고칠 때마다 **숫자로 확인하는 구조**를 갖추는 것이었다.

---

## 쉽게 말하면

문제를 만드는 지시문(프롬프트)에 규칙을 잔뜩 적어 뒀는데, **적은 대로 나오지 않았다.**

원인은 대개 "규칙이 없어서"가 아니라 **규칙끼리 싸워서**였다. 그리고 규칙을 지켰는지
아무도 세지 않아서, 어긋나도 며칠 뒤 눈으로 알아챌 때까지 몰랐다.

그래서 세 가지를 했다.

| 한 일 | 왜 |
|---|---|
| 싸우는 규칙을 갈라 놓기 | 규칙이 충돌하면 어느 쪽이 이길지는 그날 운이다 |
| 셀 수 있는 규칙은 코드로 세기 | 검사하지 않는 규칙은 없는 규칙이다 |
| 고친 뒤 바로 재 보는 도구 만들기 | 하루에 한 번 5개 보고 튜닝하면 수렴하지 않는다 |

---

## 1. 출발점 — 초급이 왜 어려웠나

2026-08-16 초급 5문제를 실제로 세어 봤다.

- 4개가 `~했다`로 시작하는 **배경 서술**을 달고 있었다
- 1개는 `READ COMMITTED`와 `REPEATABLE READ`를 **나란히 놓고 비교**시켰다 (중급의 일)
- 지문 길이 45 / 97 / 124 / 145 / 149자 — 45자짜리 하나만 상황 없는 정의 문제였다

**초급 규칙이 약해서가 아니었다. 다른 규칙 셋이 초급 규칙을 덮어쓰고 있었다.**

| 덮어쓴 규칙 | 어디 있었나 | 왜 초급을 밀어 올렸나 |
|---|---|---|
| "문서가 설명한 원리를 **다른 상황에 적용**하게 만들어야 한다" | 근거 문서 블록 (모든 난이도) | 이 문장이 **중급의 정의 그 자체**다 |
| "**명백히 틀린 보기 금지**" | `typeRule` (모든 난이도) | 초급 오답 = 다른 개념의 정의, 중급 오답 = 원리 오적용과 정면 충돌 |
| "한 절에서 두 문제를 뽑지 마라" | 배치 내 중복 규칙 | 초급이 캘 절은 `## 무엇인가` 하나뿐인데 5개를 요구받으니, **규칙을 지키려고** 다른 절로 넘어갔다 |

세 번째가 특히 중요하다. **모델이 규칙을 어긴 게 아니라 지킨 결과**가 나빴다.

---

## 2. 난이도를 다시 정의했다

"얼마나 어려운가"가 아니라 **무엇을 묻는가**로 갈랐다.

| | 초급 | 중급 | 고급 |
|---|---|---|---|
| 묻는 것 | 용어가 무엇인가 | 원리를 처음 보는 상황에 적용 | 여러 대응 중 무엇을 고를까 |
| 지문 | 상황 없음, 120자 이내 | 상황이 한 문단 | 상황 + **이미 시도한 것** |
| 오답 | 서로 다른 개념의 정의 | 원리를 잘못 적용한 판단 | **조건이 달랐다면 옳았을 대응** |
| 푸는 사람 | 문서를 읽은 사람 | 원리를 이해한 사람 | 겪어 보고 대가를 아는 사람 |

### 중급과 고급은 지문으로 구분되지 않았다

08-13(중급)과 08-14(고급)의 지문은 형태가 **똑같았다** — "상황 서술 → 원인과 대응으로
가장 적절한 것은?". 실제로 갈린 곳은 **오답**이었다.

| | 중급 오답 (08-13) | 고급 오답 (08-14) |
|---|---|---|
| 실제 예 | "캐시 서버와 앱 서버의 **시각이 어긋나** TTL 계산이 밀렸다" | "TTL에 임의 값을 더해 만료를 흩뿌리고 잠금을 건다" |
| 성격 | 명백히 틀림 | **stampede였다면 정답**인 대응 |

그래서 모델이 스스로 판정할 수 있는 기준을 줬다.

> 고급인데 **명백히 틀린 보기가 하나라도 있으면** 그 문제는 고급이 아니다.
> 중급인데 **네 보기가 전부 그럴듯하면** 그건 고급이다.

"더 어렵게 내라"는 지킬 수도 확인할 수도 없지만, 이건 **세어 볼 수 있다.**

### 예시를 통 문항으로 바꿨다

지문 한 줄짜리 예시로는 **오답 설계가 전달되지 않는다.** 난이도를 실제로 가르는 게
오답인데 말이다. 그래서 보기 넷 + "왜 이 난이도인가"까지 붙였다(`difficultyExample`).

**승인된 기존 문제를 예시로 쓰지 않았다.** 그것들이 지금 고치려는 바로 그 기준으로
만들어진 것들이라, 예시로 주면 어긋난 기준을 굳힌다.

> **이 저장소가 두 번 확인한 것: 예시가 규칙을 이긴다.**
> 문서 프롬프트의 "핵심 용어를 하이픈 목록으로" 규칙이, 바로 아래 예시에 하이픈이
> 없다는 이유로 무시됐다(커밋 `bafb2e9`가 고치려다 실패). 반대로 난이도 예시를
> 통 문항으로 바꾸자 형태가 바로 달라졌다.

## 3. 셀 수 있는 규칙은 검증기로 옮겼다

프롬프트에 적어 둔 숫자가 지켜지지 않는다는 것을 실측했다.

> "해설은 400~700자로 쓴다"고 적어 뒀는데 2026-08-13 배치는 **5개가 전부 359~395자**였고,
> 세는 곳이 없어 아무도 몰랐다.

### 규칙의 성격에 따라 처리할 곳이 다르다

| 규칙의 성격 | 어디서 | 예 |
|---|---|---|
| **셀 수 있다** | 코드 검증 — 프롬프트에도 적되, 검증이 없으면 없는 규칙 | 해설 400자, 용어 6개, 하이픈 목록 |
| **판단이 필요하다** | 사람이 볼 표본을 뽑아 준다 | "오답 넷이 다 그럴듯한가" |
| **취향·방향** | 프롬프트 + 실물 예시 | 문체, 주제 선택 |

### 문제 쪽 — `ProblemItemRule`

| 검사 | 기준 | 근거가 된 실물 |
|---|---|---|
| 해설 분량 | 400~700자 | 08-13 **5개 전부** 미달 |
| 초급 지문 길이 | 120자 | 08-16 지문 중 45자 하나만 상황 없음 |
| 지문의 근거 문서 지칭 | "문서가 든 것은?" 류 | 08-16 4번 |
| 해설의 보기 번호 지칭 | "두 번째 보기는" | **사람 눈으로는 못 잡는다** (아래 참고) |
| 정답이 최장 + 편차 1.5배 | 둘이 **겹칠 때만** | 22개 중 **18개(82%)** |
| 마크다운(백틱·별표) | 화면이 평문 출력 | 실물 2건 |

전부 **경고**이고 `defectOf`(버리는 판정)에는 넣지 않았다. 해설이 350자인 문제를 버리면
멀쩡한 문제를 요금까지 내고 잃는다.

### 문서 쪽 — `DocumentDraftValidator`

| 검사 | 근거 |
|---|---|
| `### 왜 이렇게 설계됐는가` 정확히 1개 | 08-15 문서에 `###`로 0개, **굵은 글씨로 3개** |
| `## 무엇인가`의 용어가 하이픈 목록인가 | 홑줄바꿈은 문단을 안 끊어 화면에서 뭉친다 |
| 본론 섹션 2개 이상 | 필수 절 목록으로는 본론의 부재를 못 잡는다 |
| `## 언제 깨지는가` 항목 5개 이상 | 고급 재료. 형식이 미지정이라 세 형식 모두 인정 |

**문서 검증을 생성 직후로 앞당겼다.** 원래는 승인 화면에서만 돌았는데, 문서는 만든 날
바로 승인되지 않고 그 사이 **사흘 치 문제가 만들어진다.**

### 문턱은 실측으로 정했다

보기 길이 비율을 예로 들면:

| 문턱 | 실물 22개 중 경고 |
|---|---|
| 1.4 | 8건 (36%) — 시끄러움 |
| **1.5** | **5건 (23%)** ← 채택 |
| 1.6 | 3건 (14%) — 놓침 |

**정답 최장과 비율 초과가 겹칠 때만** 울린다. 정답이 우연히 최장인 건 넷 중 하나꼴로 늘
생기므로, 그것만으로 울리면 4분의 1이 헛울린다.

> **오탐이 미탐보다 비싸다.** 헛울리는 경고는 사람이 경고 **전체**를 안 보게 만든다.
> 이 저장소가 이미 겪은 실패 방식이라, 새 검사를 넣을 때마다 실물에 돌려 오탐률을 봤다.

## 4. 평가 하네스 — 피드백 루프를 하루에서 몇 분으로

### 왜 필요했나

```
전:  프롬프트 수정 → 커밋 → 하루 대기 → 문제 5개 확인 → 추측 → 다시 수정
```

**하루에 한 번, 표본 5개로 튜닝**하고 있었다. 게다가 매일 분야가 바뀌므로 어제와 오늘의
차이가 프롬프트 때문인지 주제 때문인지 갈라낼 수가 없다.

### 무엇을 하나

`PromptEvalCli` — 근거 문서를 **고정**하고 세 난이도를 한 번에 뽑아 채점한다.

```powershell
$env:ANTHROPIC_API_KEY = "sk-ant-api03-..."   # 그 창에서만
.\gradlew.bat evalPrompt -PevalArgs="--count=3 --label=before"
# (프롬프트 수정)
.\gradlew.bat evalPrompt -PevalArgs="--count=3 --label=after"
```

`eval/` 아래 파일 **둘**이 생긴다.

| 파일 | 담는 것 |
|---|---|
| `YYYYMMDD-HHMMSS-라벨.md` | 채점 보고서 (표 + 경고 + 난이도별 표본 1문항) |
| `YYYYMMDD-HHMMSS-라벨.json` | **생성 원본 전부** — 전수 검토용 |

### 재는 것과 안 재는 것

**재는 것:** 요청→응답→유효 개수, 지문·해설 길이(최소/평균/최대), 품질 경고,
그리고 **배경 서술이 붙은 문항 수**.

마지막 것이 초급 상한의 핵심 지표다. "상황 없이 한두 문장"은 셀 수 없어서, 한국어 배경
서술이 거의 예외 없이 `~다.`로 끝난다는 점을 이용했다. 08-16 초급 5문제로 맞춰 보니
**눈으로 읽은 판정과 정확히 일치**했다.

**안 재는 것:** 오답이 "조건이 달랐다면 옳았을 대응"인지. 셀 방법이 없으므로 판정을
흉내 내는 대신 난이도마다 문항 하나를 보기까지 통째로 찍어 사람이 본다.

> 기계가 못 재는 것을 재는 척하면, **숫자는 좋아졌는데 물건은 나빠진 상태**를 못 알아챈다.

### 설계 판단 셋

| 판단 | 이유 |
|---|---|
| 회피 목록·거절 사례를 **비운다** | 날마다 자라는 입력을 넣으면 같은 프롬프트로도 다음 주에 다른 결과가 나온다 |
| 배치 중단 스위치를 **안 본다** | 배치를 꺼 둔 채 프롬프트를 고치는 상황이 바로 이 도구가 필요한 때다 |
| `check`/`build`에 **안 엮는다** | 실제 API를 부르므로 엮으면 요금이 조용히 샌다 |

채점 기준은 `ProblemItemRule`을 그대로 쓴다. 따로 적으면 "하네스는 통과인데 배치는 경고"가 된다.

### 원본을 남기는 이유 — 하루 만에 값을 했다

보고서는 난이도마다 한 문항만 찍는다. 08-17 감사에서 **9문항 중 6개가 사라져** 전수
검토가 막혔고, 그래서 원본 JSON을 함께 저장하게 했다.

바로 그날, 검증기 오탐을 고친 뒤 **API를 다시 부르지 않고** 저장된 원본으로 재채점해
확인했다. 요금 0원.

## 5. 실측 결과

네 번 돌렸다(약 3,400원).

| 지표 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 초급 지문 (평균) | 45~149 (**112**) | 34~42 (**38**) |
| 초급 배경 서술 | **4/5** | **0/3** |
| 중급 지문 | 93~183 (141) | 186~225 (204) |
| 고급 지문 | 149~172 (161) | 217~232 (226) |
| 해설 기준 밖 | 08-13 **5개 전부** | **0개** |
| 해설의 보기 번호 지칭 | 중급 **3/3** | **0/3** |
| 정답이 최장 | **18/22 (82%)** | 2/9 (22%) |

**세 난이도의 지문 길이 범위가 겹치지 않는다** — 초급 최대 42 < 중급 최소 186 < 고급
최소 217. 이전에는 112 → 141 → 161로 서로 파묻혀 있었다.

### 고친 것 중 효과가 확실했던 것

| 수정 | 결과 |
|---|---|
| 근거 문서 블록의 "다른 상황에 적용" 제거 | 초급 배경 서술 4/5 → 0/3 |
| 해설의 보기 인용 규칙 | 중급 3/3 → 0/3 |
| 오답 규칙을 난이도별로 가름 | 고급에서 "READ COMMITTED로 내린다"류 오답 소멸 |
| `[금지]`의 정답 용어 규칙 완화 | "MVCC에 대한 설명으로 옳은 것은?" 형태 허용 (34자) |

### 안 먹힌 것 — 보기 길이 편향

프롬프트에 1.5배를 박았는데 82% → 22%로, **표본 대비 거의 안 줄었다**(이전 실물 기준
23%였다). 정답 위치 편향과 같은 결론이다.

| | 정답 위치 편향 | 보기 길이 편향 |
|---|---|---|
| 증상 | 정답이 4번에 한 번도 없음 | 정답이 넷 중 가장 김 |
| 프롬프트로 고쳐지나 | ❌ | ❌ |
| 코드로 고칠 수 있나 | ✅ 내보낼 때 섞는다 | ❌ **길이는 섞을 수 없다** |

그래서 검증기가 세고 검수자가 정답에서 한 줄 덜어내는 것으로 간다.

## 6. 사람 눈으로는 못 잡는 결함

이번 작업에서 가장 값어치 있었던 검사는 **해설의 보기 번호 지칭**이다.

```
"…따라서 두 번째 보기는 MVCC를 락 기반과 혼동한 것이다"
```

정답 위치 편향을 고치면서 **내보낼 때 보기를 섞기로** 했는데(`QuizProblemItem`),
그 결정에 짝이 되는 제약이 빠져 있었다. 순서로 가리키면 섞인 뒤 엉뚱한 보기를 가리킨다.

**검수자는 섞이기 전 화면을 보므로 번호가 맞아 보인다. 학습자만 어긋난 해설을 읽는다.**

평가 실행에서 중급 3문제가 **전부** 이 형태로 나왔다. 검증기가 없었으면 9개 중 3개가
그대로 나갔을 것이다.

### 원인은 반쪽짜리 규칙이었다

`[해설]` 절이 "나머지 보기가 왜 틀렸는지 짚어라"라고 시키면서 **가리키는 방법**은 안
알려 줬다. 모델은 지시를 지키려고 순서로 가리켰다. **규칙끼리 싸운 게 아니라 규칙이
절반만 있었다.**

고친 문구:

```
단, 보기를 가리킬 때는 <순서가 아니라 내용>으로 가리켜라.
(X) 두 번째 보기는 MVCC를 락 기반과 혼동한 것이다
(O) "MVCC도 읽기에 공유 락을 건다"는 보기는 MVCC를 락 기반과 혼동한 것이다
```

## 7. 화면 쪽 버그 하나

해설 22개 중 **17개**가 줄바꿈·하이픈 목록을 쓰는데, 문제 화면은 `escapeHtml`로 **평문**을
넣고 `.explain`에 `white-space: pre-wrap`이 없었다. 한 줄로 뭉쳐 나왔다.

문서 화면에서 이미 겪은 그 버그가 다른 화면에서 재발한 것이다.

**프롬프트로 목록을 금지하는 대신 CSS로 살렸다** — 해설은 "정답 근거 + 오답 셋"이라
본래 목록이 어울리는 내용이고, 금지하면 해설이 오히려 나빠진다.

```css
.feedback .explain { white-space: pre-wrap; word-break: break-word; }
```

검증기가 막는 것은 **살릴 수 없는 것**(백틱·별표)뿐이다.

## 8. 관련 코드

| 클래스 | 하는 일 |
|---|---|
| `ClaudeProblemGenerator.SOURCE_SECTIONS` | 난이도별로 문서에서 캘 절 — **절 이름의 단일 출처** |
| `ClaudeProblemGenerator.difficultyExample` | 난이도별 통 예시 (보기 + 판정 근거) |
| `DraftGeneratorCli.hasMaterialFor` | 오늘 난이도가 캘 절이 문서에 있는지 — 없으면 폴백 |
| `ProblemItemRule.qualityWarningsOf` | 문제 품질 경고 6종 |
| `SourceQuoteRule.warningOf` | 근거 인용이 문서에서 왔는지 + **남의 난이도 절을 캤는지** |
| `DocumentDraftValidator` | 문서 형식 검사 (기존 5 + 신규 4) |
| `PromptEvalCli` | 평가 하네스 (`evalPrompt` 태스크) |

`SourceQuoteRule`은 나머지와 달리 **근거 문서를 손에 들고 있어야** 판정한다. 그래서 배치와
평가 CLI만 부르고, 들여오기(`LlmProblemService`)는 부르지 않는다 — 파일만 받는 쪽에는 대조할
원본이 없다. 판정 방향을 "지목 절 안인가"가 아니라 "남의 절을 캤는가"로 뒤집은 이유는
클래스 주석에 있다(중급은 설계 근거를 본론에서 캐도 정상이라, 전자로 재면 매번 헛울린다).

테스트는 규칙이 **조용히 사라지는 것**을 막는 데 집중했다. 프롬프트에서 한 줄이 빠져도
예외가 안 나고 문제는 멀쩡히 생성되므로, 증상이 며칠 뒤 품질로만 나타난다.

## 9. 남은 것

| 항목 | 상태 |
|---|---|
| 보기 길이 편향 | 검증기가 세는 것으로 간다. 프롬프트로는 안 줄었다 |

| 자기 검토(self-critique) 호출 | 평가 하네스로 재 보고 부족하면 넣는다. 미리 넣으면 효과를 모른 채 요금만 2배 |

## 10. 면접 대본 요약

> **"LLM이 만든 콘텐츠 품질을 어떻게 보장했나요?"**
>
> 규칙을 세 종류로 나눴습니다. **셀 수 있는 건 검증기로** 막고, **판단이 필요한 건**
> 사람이 볼 표본을 뽑아 주고, 프롬프트는 방향만 잡게 했습니다.
>
> 프롬프트를 고칠 때는 **평가 하네스로 회귀 측정**을 했습니다. 근거 문서를 고정하고 세
> 난이도를 한 번에 뽑아 채점하니, 하루 걸리던 확인이 몇 분으로 줄었습니다.
>
> 실제로 프롬프트로 안 고쳐지는 것들이 있었습니다. **정답 위치 편향은 내보낼 때 섞어서**
> 코드로 해결했고, **보기 길이 편향은 섞을 수가 없어서** 검증기가 세고 사람이 판단하게
> 뒀습니다. "프롬프트에 적어 두고 지켜지길 바라는" 상태를 없애는 게 핵심이었습니다.
