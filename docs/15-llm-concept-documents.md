## 쉽게 말하면

지금까지는 AI가 **문제**만 만들었다. 그런데 문제를 매일 5개씩 받아 풀어 보니 문제가 생겼다.

> "문제들이 단발성 지식들이고, 깊이 있는 이해로 이어지기가 어려운 것 같다."

오늘은 TCP, 내일은 인덱스, 모레는 캐시. 서로 남남인 문제들이라 **지식이 파편으로 쌓인다.**
시험 문제집만 풀고 교과서는 안 읽는 것과 같다. 📚

그래서 **교과서를 먼저 쓰게 했다.**

```
[1일차]  AI가 "캐시 전략" 개념 문서를 쓴다        ← 교과서
[2·3·4일차]  그 문서를 근거로 초급/중급/고급 문제  ← 문제집
```

문서 하나를 중심으로 사흘이 묶이니, 문제를 풀다 막히면 **돌아가 읽을 곳이 생긴다.**

## 전체 구조 — 문제와 똑같은 길을 간다

```
[GitHub Actions]  매일, 내 PC와 무관하게 실행
      ↓  문서를 만들어 저장소에 커밋
[generated/documents/2026-08-12.json]        ← 택배함 (문서용 칸)
      ↓  내가 앱을 켤 때 (DraftImportRunner)
[generated_document_draft 테이블 = 검수 대기함]
      ↓  관리자 화면 "AI 문서" 탭에서 승인
[document 테이블 = 사이트에 보이는 정식 문서]
```

문제 흐름(docs/14)과 **한 칸도 다르지 않다.** 일부러 그렇게 맞췄다 — 들여오기 규칙(이미 가져온
파일은 건너뛰기, 오래된 순, 한 파일 실패가 나머지를 막지 않기)이 두 벌이 되면 언젠가 한쪽만
고쳐져 "문서만 중복 들여오는" 버그가 난다. 그래서 러너는 하나이고, 파일을 읽어 해석하는
부분만 서비스 둘로 갈라져 있다.

## 왜 폴더를 나눴나 — 그리고 그것이 만든 지뢰

문서 파일을 `generated/documents/` **하위 폴더**에 둔다. 접두사(`doc-2026-08-12.json`)로
구분하는 대안도 있었지만, 그러면 기존 문제 들여오기 코드가 그 파일까지 읽으려다 파싱에 실패한다
(형식이 다르므로). 폴더로 나누면 `Files.list()`가 하위 디렉터리를 `.json` 필터에서 자연스럽게
걸러 주므로 **기존 코드를 한 줄도 안 고치고** 분리된다.

그런데 이 선택이 지뢰를 하나 만들었다.

```
generated/2026-08-12.json            ← 문제
generated/documents/2026-08-12.json  ← 문서   같은 이름!
```

"이 파일은 처리했다"고 도장을 찍는 표(`imported_draft_file`)의 열쇠가 **파일명 하나뿐**이다.
그대로 두면 문제 파일을 먼저 들여온 순간 도장이 찍히고, 문서 파일은 "이미 처리함"으로
**예외도 로그도 없이 건너뛰어진다.** 이 프로젝트가 가장 경계하는 조용한 실패다.

→ 문서의 열쇠에는 폴더를 붙인다(`documents/2026-08-12.json`).
구분자를 `/`로 못 박은 이유는 `Path`를 그대로 문자열로 만들면 윈도우에서 `documents\...`가 되어
**같은 파일이 OS마다 다른 열쇠**가 되기 때문이다(CI는 리눅스).

문제 쪽 열쇠에 폴더를 붙이지 **않는** 것도 의도적이다 — 규칙을 바꾸는 순간 이미 들여온 파일이
전부 "처음 보는 파일"이 되어 초안이 통째로 복제된다.

## 자동 검증 — 사람은 내용만 보게 한다

LLM이 쓴 문서는 3,000자가 넘고 문장이 매끄러워서, 검수자가 죽 읽다 보면 **형식 결함**을
그냥 지나친다. 내용의 옳고 그름은 사람만 판단할 수 있지만 형식은 기계가 훨씬 잘 본다.

검증 규칙은 **전부 실물에서 나왔다**(2026-08-11·12 생성분 2편을 읽고 도출).

| 항목 | 판정 | 왜 |
|---|---|---|
| `title` 필드 ↔ 본문 `# H1` 불일치 | 경고 | 2편에서 실제로 어긋났다("XSS와 CSRF" vs "CSRF와 XSS"). 어느 쪽이 맞는지는 사람만 정한다 |
| 필수 절 누락 | **차단** | 목록은 생성 프롬프트의 `REQUIRED_SECTIONS`를 공유한다 |
| 코드블록 **밖**의 HTML 태그 | **차단** | 문서 화면이 `innerHTML`로 렌더링하므로 그 자리의 태그는 진짜 실행된다 |
| slug 형식 위반 | **차단** | 승인 경로는 `@Valid`를 안 타므로 여기서 안 보면 그냥 통과한다 |
| 본문 3,500자 초과 | 경고 | ↓ |
| 본문 5,000자 초과 | **차단** | 여기까지 오면 "잘 썼다"가 아니라 지시를 무시한 것 |

### 코드블록 예외가 없었다면 보안 문서를 영영 못 썼다

2026-08-12 문서(XSS와 CSRF)의 본문에는 `<script>`와 `<form action=...>`이 **정상적으로**
들어 있다. 공격 예시니까 당연하다. 코드블록 안이면 marked가 글자로 이스케이프하므로 실행되지 않는다.

`<`만 보고 막는 검증기를 만들었다면 XSS·SQL 인젝션 같은 주제의 문서가 **매번 반려**됐을 것이고,
한참 뒤에야 "왜 보안 문서만 안 올라가지?"를 알았을 것이다.

태그 정규식에도 함정이 있었다. `<[a-zA-Z][^>]*>`로 쓰면 본문의 부등호를 태그로 오인한다 —
`if (a<b) return c>d`에서 `<b) return c>`가 통째로 걸린다. 그래서 태그 이름 뒤에
**공백·`/`·`>` 중 하나**를 요구하도록 했다.

### 분량은 왜 차단하지 않나

프롬프트에 "2,500~3,500자, 상한을 넘기지 마라"라고 적었는데도 실측은 이랬다.

| | 지시 | 실제 | 초과 |
|---|---|---|---|
| 1편 (캐시 전략) | 2,000자 | 2,645자 | +32% |
| 2편 (XSS·CSRF) | 3,500자 | 4,578자 | +31% |

**프롬프트 문구로는 못 잡는다**는 것이 두 편으로 확인됐다. 이걸 차단으로 두면 잘 쓴 문서가
매일 승인 불가로 쌓인다. 억지로 줄이면 용어 설명과 면접 질문부터 잘려 나가는데, 그 두 절이
분량을 올린 목적이었다. 그래서 화면에 숫자만 띄우고 판단은 사람에게 맡긴다.

## 검증에 걸린 문서도 일단 들여온다

문제 들여오기(docs/13)와 **일부러 다르게** 만든 지점이다. 문제는 규약을 어긴 항목을 저장 단계에서
버리는데, 문서는 다 받아 둔다.

1. 문서는 하루 한 편이라 버리면 그날 결과가 **0건**이 된다. 5개 중 1개를 버리는 것과는 손실의 크기가 다르다.
2. 걸린 문서도 **왜 걸렸는지 보는 것 자체가 정보**다 — 프롬프트를 어떻게 고칠지는 걸린 실물을 봐야 안다.
3. 검증 규칙은 실물 두 편을 보고 만든 초기 버전이다. 규칙이 틀렸을 때 저장 단계에서 버렸으면 **되돌릴 원본이 없다**.

대신 승인 시점에 차단 항목을 막으므로, 잘못된 문서가 정식으로 올라가는 일은 없다.

## 승인은 기존 등록 경로를 재사용한다

```java
// LlmDocumentService.approve
DocumentDetailResponse created = adminDocumentService.create(new AdminDocumentRequest(...));
draft.approve(created.id());
```

문제 승인이 `AdminProblemService.create`를 재사용하는 것과 같은 **단일 경로 원칙**이다.
문서 등록에는 slug 중복 검사, 태그 find-or-create, 캐시 무효화가 딸려 있는데, 여기서 직접
저장하면 그 셋을 다시 구현해야 하고 언젠가 한쪽만 고쳐진다 — 예를 들어 나중에 문서 등록에
검색 색인 갱신이 추가되면 **AI가 승인한 문서만 검색에 안 잡히는** 버그가 된다.

slug 중복(DOC_002)을 여기서 따로 검사하지 않는 것도 같은 이유다. 같은 주제를 다시 뽑으면
slug도 같아지므로 실제로 자주 생기는데, `AdminDocumentService`가 이미 409를 던진다.

## 검수 화면 — 왜 마크다운을 렌더링하지 않나

관리자 화면은 본문을 렌더링하지 않고 **원문 그대로** `<pre>`에 보여 준다.

- 검수자가 봐야 하는 것은 "최종 화면"이 아니라 **"저장될 내용"**이다. 렌더링하면 검증기가
  지적한 HTML 태그가 눈앞에서 사라져(브라우저가 실행해 버려) 확인할 수가 없다.
- 승인 전 문서는 아직 검증을 통과하지 않은 글이다. 그걸 `innerHTML`로 넣는 순간
  **관리자 페이지가 XSS 표적**이 된다 — 우리가 막으려는 바로 그 문제다.

"생성 요청" 버튼도 두지 않았다. 문서 생성은 한 편에 1~2분·$0.2가 드는 작업이라 화면에 버튼이
있으면 실수로 누르기 쉽고, 누른 뒤에는 응답이 올 때까지 화면이 멈춰 있어야 한다.
필요하면 워크플로를 수동 실행하는 쪽이 주제·날짜까지 지정할 수 있어 오히려 낫다.

## 클라우드는 DB를 못 본다 — 스냅샷 파일

`generated/_existing-documents.json`에 정식 문서 + **검수 대기 초안**의 제목과 태그를 내보낸다.
앱을 켤 때마다 `ExistingDocumentsExporter`가 갱신하고, 사용자가 커밋하면 다음 배치부터 반영된다.

```json
{
  "titles": ["캐시 전략 — 무엇을 어디에 저장하고, 어떻게 깨지는가", "..."],
  "tags": ["auth", "cache", "http", "performance", "security", "system-design"],
  "rejectedSlugs": []
}
```

| 필드 | 배치가 쓰는 곳 |
|---|---|
| `titles` | 같은 주제를 또 만들지 않게 하는 회피 목록 |
| `tags` | 기존 태그를 재사용하게 해 태그 난립을 막는다 |
| `rejectedSlugs` | **이 문서로는 문제를 만들지 마라**(2단계에서 추가) |

검수 대기 초안까지 넣는 것이 핵심이다. 승인을 며칠 미루는 동안 정식 문서 목록에는 그 주제가
없으므로, 초안을 빼면 배치가 **대기함에 이미 있는 주제를 또 만든다.**

`rejectedSlugs`가 필요한 이유는 다르다. 검수자가 "이건 아니다"라고 판단한 문서로 사흘간 문제를
만들면 **그 사흘이 통째로 낭비**다. 거절 여부는 로컬 DB에만 있으므로 이 목록으로 실어 보낸다.
반대로 **아직 검수 안 한 문서는 그냥 쓴다** — 미승인은 부정 신호가 아니라 "아직 안 봤다"일 뿐인데,
승인을 며칠 미뤘다고 그 주기를 날리면 사람의 검수 속도에 배치가 인질로 잡힌다.

> 옛 파일에는 `rejectedSlugs` 필드가 없다. CLI가 읽는 지점에서 전부 빈 목록으로 정규화해
> 호출부가 null을 신경 쓰지 않게 했다(`DraftGeneratorCli.readExistingDocuments`).

**내용이 같으면 파일을 다시 쓰지 않는다**가 이 클래스의 규칙이다(`RejectionNotesExporter`와 동일).
매 부팅마다 "내보낸 시각"만 바뀐 파일을 새로 쓰면 앱을 켤 때마다 git이 변경으로 인식해서
진짜 바뀐 날을 알아볼 수 없게 된다.

## 데이터 모델 (V8)

| 컬럼 | 비고 |
|---|---|
| `domain` `title` `slug` `content_md` | `document` 테이블과 1:1 — 승인 시 그대로 이관 |
| `tags_json` | `["security","auth"]`. 정규화하지 않는 이유는 V6의 `choices_json`과 같다. 게다가 초안의 태그는 아직 없는 태그일 수 있어, 정규화하면 **승인도 안 한 문서 때문에 tag 테이블이 오염된다** |
| `status` `model` `reject_reason` | 문제 초안과 동일 |
| `approved_document_id` | FK 아님 — 이력이라 문서를 지웠다고 함께 사라지면 안 된다 |

`slug`에 UNIQUE를 걸지 않았다. 초안 단계에서 막으면 같은 주제를 다시 뽑아 비교해 보는 것
자체가 불가능해진다. 진짜 유일성은 `document.slug`가 지킨다.

**검증 결과는 컬럼으로 저장하지 않는다.** 조회할 때마다 다시 계산한다 — 규칙은 실물을 보며
계속 손볼 것이라, 저장해 두면 이미 들여온 초안이 옛 규칙으로 굳어 규칙을 고쳐도 화면이 안 바뀐다.

### 거절 복구 — 왜 필요했나

거절은 되돌릴 수 없는 판단이 아니다. 실수로 눌렀을 수도 있고, 나중에 "고쳐서 쓰면 되겠다"로
생각이 바뀌기도 한다. 그런데 되돌릴 방법이 없으면 **거절 버튼을 누르는 것 자체가 무서워져**
검수가 밀린다 — 이 기능 전체가 멈추는 경로다.

```java
public void restore() {
    if (this.status != DraftStatus.REJECTED) {
        throw new BusinessException(ErrorCode.LLM_002, "거절된 초안만 검수 대기로 되돌릴 수 있습니다. ...");
    }
    this.status = DraftStatus.PENDING;
    this.reviewedAt = null;   // rejectReason은 일부러 남긴다
}
```

- **`REJECTED`만 되돌린다.** 승인된 것까지 되돌리면 이미 정식 문서가 만들어진 뒤라
  "초안은 대기 상태인데 문서는 공개돼 있는" 어긋난 상태가 된다.
- **거절 사유를 지우지 않는다.** `PENDING`인데 `rejectReason`이 남아 있으면 그것이 곧
  **"되살린 초안"**이라는 표시다 — 컬럼을 새로 만들지 않고 상태 조합으로 해결했다.
  검수자에게도 "지난번엔 이래서 거절했었지"라는 정보가 그대로 보인다.

문제 초안(`/api/admin/llm-problems/{id}/restore`)도 같은 규칙이다.

### 2단계가 실제로 동작한 증거 (2026-08-13)

예약 배치가 만든 파일의 머리말에 근거 문서가 찍혔다.

```json
"domain": "SYSTEM_DESIGN", "difficulty": "INTERMEDIATE",
"documentSlug": "caching-strategies-and-failures"
```

해설이 문서 내용을 직접 가리킨다 — *"문서가 '갱신이 아니라 삭제'를 권하는 이유가 이것이며"*.
문서를 무시하고 모델이 아는 대로 냈다면 나올 수 없는 문장이라, **프롬프트에 실린 문서를 실제로
읽었다는 확인**이 된다.

### 잡은 버그 — 문서 분야가 옛 규칙을 쓰고 있었다 (2026-08-13)

2단계에서 문제 쪽만 `planFor`로 옮기고 **문서 쪽은 옛 `cellFor`를 그대로 뒀다.** 두 규칙이
어긋나는 방식이 하필 최악이었다.

```
문서일   = 에포크일 mod 4 == 0     → 4의 배수인 날
cellFor = 분야[에포크일 mod 8]     → 4의 배수를 8로 나눈 나머지는 0 아니면 4
⇒ 후보 8개 중 두 개만 무한 반복 (NETWORK ↔ SYSTEM_DESIGN)
```

나머지 여섯 분야는 개념 문서를 **영원히 못 받는다.** 게다가 문제일에는
`alignDomainWithDocument`가 분야를 문서 쪽으로 맞추므로 **문제까지 그 두 분야에 갇힌다** —
이 한 줄이 기능 전체의 커버리지를 25%로 떨어뜨리고 있었다.

**세 겹으로 숨어 있었다.**

1. `planFor`에는 테스트가 촘촘했지만 **그것을 쓰는 쪽**은 아무도 보지 않았다.
   규칙이 옳아도 배선이 틀리면 소용이 없다.
2. 정렬 장치가 매일 "분야를 맞췄습니다" 로그를 남기며 결과를 그럴듯하게 만들어 줘서
   **증상마저 가려졌다.** 옛 문서를 위한 임시 그물이 상시 발동 중이었던 것이다.
3. 첫 실행일에는 티가 안 났다 — 8/13 배치를 확인하면서 `SYSTEM_DESIGN`을
   "근거 문서에 맞춰 정렬된 것"으로 읽고 **정상이라고 판단했다.**

**교훈**: 안전장치가 자주 발동하면 그건 안전장치가 잘 도는 게 아니라 **본선이 고장 났다는
신호**다. 정렬 로그가 매일 찍히는 것을 이상하게 여겼어야 했다.

수정은 한 줄이지만, 판단을 `DraftGeneratorCli.documentDomain`이라는 **이름 있는 함수로 꺼내**
테스트를 걸었다. 구현을 베끼는 대신 *"한 바퀴(32일)에 모든 분야가 한 번씩"*이라는 **성질**을
검사하므로, 어떤 방식으로 다시 짜든 이 성질이 깨지면 실패한다.
