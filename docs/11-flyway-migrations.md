# 11. Flyway — DB 스키마 형상 관리

> 2026-07-14 대화에서 정리한 학습 노트. 관련 파일: `src/main/resources/db/migration/`

## Flyway가 뭔가 (아무것도 모르는 사람용)

코드는 git으로 버전 관리하면서, **DB 구조(테이블·컬럼·인덱스)는 왜 버전 관리를 안 하지?**
— 이 질문에 대한 답이 Flyway다.

DB는 코드처럼 "새 버전으로 통째로 교체"할 수 없다. 안에 **데이터가 쌓여 있기** 때문이다.
그래서 "처음부터 지금까지 어떤 변경을 어떤 순서로 적용했는지"를 SQL 파일로 쌓아 두고,
그 기록을 순서대로 재생하는 방식을 쓴다. **공사 일지** 비유:

- 건물(DB)은 부수고 다시 지을 수 없다 → "1일차 기둥, 2일차 벽, 3일차 창문" 일지를 남긴다
- 새 땅(새 개발 PC, 운영 서버)에서는 일지를 1일차부터 따라 하면 똑같은 건물이 나온다

스프링 부트는 앱 시작 때 Flyway를 자동 실행한다(의존성만 넣으면 됨).

## 동작 원리 — "동기화"가 아니라 "재생"

- DB 안에 `flyway_schema_history` 장부 테이블이 있다. "V1 실행함, V2 실행함…"을 기록.
- 앱이 뜰 때: 장부에 **없는 새 파일만** 번호 순서로 실행. 장부에 있는 파일은 건너뜀.
- 파일을 고쳐서 DB에 반영시키는 구조가 **아니다**. 기존 파일 수정은 금지(아래 체크섬).

### 체크섬 — "일지 조작 감지"

적용할 때 파일의 지문(체크섬)을 장부에 기록하고, 매 시작마다 "파일이 그때 그대로인가"
검사한다. **빈 줄 하나만 달라져도** 지문이 바뀌어 앱이 시동을 거부한다.
(실화: V4에 빈 줄 하나가 끼어들어가 있어서 git checkout으로 되돌렸다 — 2026-07-14)

**주석도 파일의 일부다.** 2026-08-21에 또 밟았다 — V13을 적용한 뒤 `-- 기준 문서:` 한 줄의
문서 번호를 고쳤더니 다음 기동이 `Migration checksum mismatch for migration version 13`으로
죽었다. 이 저장소의 마이그레이션은 주석이 본문보다 긴데, 그 주석이 전부 지문에 들어간다.
바꿀 일이 생기면 **파일이 아니라 딴 데(문서·커밋 메시지)에 적는다.**

#### 어긋났을 때 되돌리는 법

로컬 개발 DB면 밀고 처음부터 재생하는 게 제일 깔끔하다. 그럴 수 없을 때
(2026-08-21이 그랬다 — 문제 33건과 제출 이력이 들어 있었다) 셋 중 하나다.

1. **파일을 원래대로 되돌린다.** git이 있으니 가장 싸다. 고친 내용을 포기해도 될 때.
2. **DDL이 정말 그대로인지 확인하고 장부의 지문을 갱신한다.** 이 프로젝트에는 Flyway
   Gradle 플러그인이 없어서 `flywayRepair`를 쓸 수 없다. 대신 직접 계산해 넣는다 —
   Flyway의 체크섬은 **줄 단위 CRC32 누적**이다(줄바꿈 문자는 빼고, UTF-8, 32비트 부호 있는 정수):

   ```python
   import zlib
   crc = 0
   for line in open(path, encoding='utf-8').read().splitlines():
       crc = zlib.crc32(line.encode('utf-8'), crc)
   print(crc - 2**32 if crc >= 2**31 else crc)
   ```

   **먼저 옛 파일로 계산해 장부의 값과 같은지 확인하고**(같으면 계산법이 맞다는 뜻),
   그다음 새 값을 넣는다. 이 확인을 건너뛰면 틀린 값을 박아 넣고도 모른다.

   ```sql
   UPDATE flyway_schema_history SET checksum = <새 값>
    WHERE version = '13' AND checksum = <옛 값>;
   ```
3. **정정하는 새 파일을 추가한다.** DDL까지 바뀌었다면 이것뿐이다.

2번은 **DDL이 한 글자도 안 바뀐 경우에만** 쓴다. 조금이라도 바뀌었으면 장부와 실제 스키마가
어긋난 채로 검증만 통과하는, 가장 나쁜 상태가 된다.

## 규칙 요약

1. **새 변경 = 새 파일.** 컬럼 하나 추가도 `V5__add_xxx.sql`을 새로 만든다.
2. **이미 적용된 V__ 파일은 절대 수정 금지.**
3. 실수를 되돌릴 때도 파일을 고치지 말고 **정정하는 새 파일**을 추가한다.
   (로컬 개발 DB는 그냥 밀고 처음부터 재생하는 게 제일 깔끔)

## V__ vs R__

| | `V__` (Versioned) | `R__` (Repeatable) |
|---|---|---|
| 이름 | `V5__add_column.sql` (번호) | `R__domain_stats_view.sql` (번호 없음) |
| 실행 | 번호순으로 딱 한 번 | **내용이 바뀔 때마다** 재실행 |
| 수정 | 금지 | 수정하는 게 사용법 |
| 순서 | 먼저 | 모든 V__ 이후 |
| 용도 | 테이블·인덱스·데이터 이관 | 뷰·프로시저·트리거 등 "지우고 다시 만들어도 되는 것" |

R__의 조건은 **멱등성**(몇 번 실행해도 결과가 같음) — `CREATE OR REPLACE VIEW`처럼
"있으면 교체" 문법을 써야 한다. 이 프로젝트의 실물: `R__domain_stats_view.sql`
(도메인별 정답률 뷰. 왜 뷰인지·대안은 뭔지 파일 주석 참고).

## 마이그레이션에 뭐가 들어가나

- **본론은 구조(DDL)**: CREATE/ALTER TABLE, CREATE INDEX. 모든 표는 어떤 V파일에서 태어난다.
- **이관(backfill)은 들어간다**: 구조 변경에 딸린 기존 데이터 옮기기.
  `V4`가 그 예 — 기존 `submission`에서 "최근 제출이 오답인" 조합을 찾아 복습 항목으로 만든다.
  이건 **구조 변경의 일부**다. 표만 만들고 데이터를 안 옮기면 기능을 켠 날 이전 오답이 전부 증발한다.
- **절대 안 들어가는 것**: 운영 중 사람이 만드는 데이터(회원가입, 제출 기록),
  그리고 **콘텐츠**(문제·문서). 이유는 바로 아래.

## 콘텐츠 시드를 걷어낸 이야기 (2026-08-12)

원래 `V2`·`V3`에 문제 24개와 문서 몇 편이 **INSERT로 하드코딩**돼 있었다. "개업 때 초기 재고"
라는 명분이었는데, 실제로 겪은 일들이 그 명분이 틀렸다고 말해 주었다.

**① 콘텐츠는 계속 바뀌는데 마이그레이션은 못 고친다**

문제 하나를 고치려면 `V10__fix_problem_7.sql`을 새로 만들어야 한다. 관리자 화면에는
수정 버튼이 있는데, **같은 데이터를 고치는 방법이 두 개**가 되고 둘은 서로를 모른다.

**② FK 순서 사고**

`V3`가 문서를 넣으면서 태그를 참조했는데 그 태그는 `V2`에 없었다. FK 위반으로 CI가 깨졌고,
급하게 `V2_1__seed_base_document_tag.sql`을 끼워 넣었다. 번호를 중간에 넣으려니
`out-of-order: true` 설정까지 켜야 했다 — **"장부는 순서대로 재생한다"는 Flyway의 전제를
스스로 무너뜨린 것**이다. 시드가 없었으면 애초에 생기지 않을 문제였다.

**③ 지운 문제가 스냅샷에 유령으로 남았다**

시드를 지우고 보니 배치의 중복 회피 목록(`_existing-questions.json`)에 **이미 삭제된 문제 24건**이
그대로 있었다. 없는 문제를 피하라고 하면 그 주제로 새 문제를 영영 못 만든다.

**결론**: 구조는 마이그레이션, 콘텐츠는 애플리케이션. 지금은 문제·문서가 전부
**관리자 화면 또는 AI 생성 → 검수 승인**으로만 들어온다. 들어오는 문이 하나면 규칙도 하나다.

> **테스트에 준 영향**: 시드에 기대던 테스트 3개가 깨졌다(`DailyQuizFlowIntegrationTest`).
> 클래스 주석에 *"시드 데이터 전제: 문제 풀이 이미 있으므로"*라고 **적혀 있었는데도** 놓쳤다.
> 지금은 각 테스트가 자기 데이터를 직접 만든다 — 원래 그게 맞다.
> 남의 데이터에 기대는 테스트는 그 데이터가 바뀌는 날 이유도 모르고 깨진다.

## 실무에서는

- 자바/스프링 진영 사실상 표준급. 경쟁자는 Liquibase(XML/YAML, 기능 많음 ↔ Flyway는 순수 SQL로 단순).
- 같은 패턴이 모든 생태계에 있다: Django migrations, Rails Active Record,
  Alembic(Python), Prisma Migrate(Node), golang-migrate(Go).
- 규모가 커지면 앱 시작 시 자동 실행 대신 **배포 파이프라인의 별도 단계**로 분리
  (서버 여러 대가 동시에 뜨며 경쟁하는 것 방지).
- 초대형 테이블 ALTER는 서비스가 멈출 수 있어 gh-ost, pt-online-schema-change 같은
  무중단 도구를 조합한다.
- "귀찮지 않나?" — 그 SQL은 어차피 누군가 짜서 실행해야 한다. Flyway는 추가 노동이
  아니라 **어차피 하는 노동을 기록이 남는 곳으로 옮긴 것**. ddl-auto=update를 운영에서
  안 쓰는 이유(예측 불가, 데이터 유실 위험)와 함께 면접 단골 주제.
