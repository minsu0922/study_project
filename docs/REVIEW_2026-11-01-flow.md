| 다른 AI | 흐름도 문서만 봤다. 코드와 운영 로그는 안 봤다고 스스로 밝혔다 | [프로젝트_콘텐츠_흐름도_분석](프로젝트_콘텐츠_흐름도_분석.md) |

## 2. 다른 AI의 지적을 코드와 대조한 결과

| 지적 | 그 AI의 순위 | 대조 결과 | 근거 |
|---|---|---|---|
| 승인 뒤 고친 문서가 배치 파일에 안 닿는다 | P0 | 맞다 | 문서 관리는 `document` 표만 고친다. 문제 배치는 `generated/documents/*.json`만 읽는다 |
| 생성 입구마다 AI 검수가 다르다 | P0 | 맞다 | `LlmProblemService.generate`·`generateFromDocument`는 DB 초안으로 바로 저장하고 검수를 부르지 않는다 |
| 코드 실행 격리 수준을 확인하라 | P0 | 일부만 있다 | `CodeRunner`가 메모리 `-Xmx64m`, 시간 초과 시 강제 종료를 건다. 실행 단계는 API 키 없는 일회용 러너에서 돌고 커밋은 깨끗한 러너가 따로 한다. 네트워크·파일 접근 차단은 없다 |
| 현황 파일 커밋을 사람이 한다 | P1 | 맞다 | `SnapshotExporter`는 파일만 쓴다. 14일 넘게 안 바뀌면 경고만 남긴다 |
| 파일 존재만으로 재실행을 막는다 | P1 | 반쯤 해결돼 있다 | 지적을 덧붙일 때 임시 파일에 쓰고 옮겨 반쪽 파일이 남지 않는다. 다시 돌릴 때는 `--suffix`를 쓴다. 실행 상태 기록은 없다 |
| JSON 파일에 형식 버전이 없다 | P1 | 맞다 | 버전 칸이 없다. `JsonMappers.STRICT`가 모르는 칸이 오면 읽기를 실패시키는 방식으로만 막는다. **2026-11-03 `formatVersion`을 넣었다([14](14-llm-batch-automation.md) "형식 버전")** |
| 주제 대기열 양방향 동기화 | P1 | 맞다 | `TopicQueueSyncRunner`(@Order 5) → `TopicQueueExporter`(@Order 50) 순서에 기댄다. 이 순서 때문에 사용 기록을 잃은 일이 있었다 |
| 거절 사유를 유형으로 나눠라 | P2 | 맞다 | `RejectionNote`는 질문과 사유 글 두 칸뿐이다. **2026-11-03 문제 거절에 유형 8가지를 넣었다([14](14-llm-batch-automation.md) "거절 사례 되먹이기")** |
| 근거 없이 만든 문제를 따로 표시하라 | 제안 | 판단이 갈린다 | 근거가 없으면 옛 순환 규칙으로 만드는 대체 경로는 "그날 생성을 통째로 날리지 않으려고" 일부러 넣었다. 이 경로를 없앨지는 정책 문제다 |
| 코드 문제 검수 흐름을 문서로 남겨라 | P2 | 맞다 | [24 코드 문제](24-java-code-problems.md)에 생성 규칙은 있지만 검수함에서 처리하는 법은 흐름도에 없다. **2026-11-03 24 5장 "검수함에서 처리하기"로 썼다.** 쓰다가 코드 문제도 직접 고치기로 보기 글을 고칠 수 있던 것을 찾아 막았다 |
| 검수 우선순위를 두라 | 제안 | 일부 있다 | 검수함 위쪽에 AI 지적 요약 표가 있다. 위험도 순 정렬은 없다 |

## 3. Claude Code만 짚은 것

| 지적 | 근거 | 벌어지는 일 |
|---|---|---|
| 문서 검수 전에 그 문서로 문제가 나간다 | 문제 배치는 승인 여부를 모른다. `_existing-documents.json`의 거절 목록에 있을 때만 근거에서 뺀다 | 틀린 문서로 사흘 치 문제가 만들어진다. 나중에 문서를 고쳐도 이미 만든 문제는 그대로다 |
| 같은 일을 하는 코드가 두 벌이다 | 문제·문서 AI 지적 처리(`LlmProblemService.resolveAiFinding`·`LlmDocumentService.resolveFactFinding`), 들여오기(`DraftImportService`·`DocumentImportService`), 거절 사례 읽기(앱은 DB, 배치는 파일). **2026-11-03 정정: 거절 사례는 두 벌이 아니었다(9장)** | 한쪽만 고치고 다른 쪽을 잊기 쉽다 |

다른 AI는 코드를 안 봐서 두 번째 지적은 볼 수 없었다.

## 5. 순위 1·2 처리 (2026-11-01)

| 항목 | 내용 |
|---|---|
| 정한 것 | 원문 문서 파일(`generated/documents/*.json`)이 늘 최신본을 따른다. 승인 전에는 초안, 승인 뒤에는 정식 문서다. 배치 코드는 바꾸지 않았다 |
| 고르지 않은 안 | 승인본을 `generated/approved/<slug>.json`에 따로 내보내고 배치가 그쪽을 먼저 읽는 안. 모델 원본 파일은 남지만 배치 코드와 파일이 하나씩 더 는다 |
| 바뀐 동작 | 문서 관리에서 고치거나 되돌리면 커밋 직후 그 편을 맞춘다. 앱이 뜰 때 정식 문서 전체와 대조해 다른 편을 맞춘다 |

## 6. 순위 3 처리 (2026-11-02)

| 항목 | 내용 |
|---|---|
| 정한 것 | C안. 관리 콘솔 버튼 하나로 `generated/_*.json`과 `generated/documents/*.json`만 커밋해 원격 `main`에 push한다. 설계는 [29-generated-publish](29-generated-publish.md) |
| 고르지 않은 안 | A. 파일을 쓸 때마다 앱이 자동 push. 사람이 모르는 사이에 작업 폴더를 rebase한다. B. GitHub API로 파일만 올림. 토큰을 새로 받아 두어야 하고 로컬이 원격과 어긋난다 |
| 바뀐 동작 | 보낼 변경이 있으면 상단 띠에 "보낼 변경 N" 칩이 뜬다. 배치 현황 화면에서 파일 목록을 보고 "배치로 보내기"를 누른다 |
| 사용자 작업 보호 | main이 아니거나, git 작업이 진행 중이거나, 사람이 안 올린 커밋이 있거나, 원격이 바꾼 파일을 사람도 고치고 있으면 멈춘다. rebase 충돌이면 누르기 전으로 되돌린다 |
| 설계와 달라진 것 | `rebase --autostash`는 되돌릴 때 스테이지를 풀어서 쓰지 않았다. 앱이 `stash push`와 `stash pop --index`를 직접 한다 |
| 확인 | 임시 원격·복제본으로 보내기 테스트 14개, API 테스트 2개, 배지 테스트 1개. 8081을 임시 복제본에 물려 화면에서 눌러 보고 임시 원격에 커밋이 들어간 것을 봤다. 진짜 원격에는 누르지 않았다 |
| 남는 것 | 누르는 것을 잊을 수 있다. 칩이 그 신호다. 앱과 배치가 함께 쓰는 `_topics.json`은 충돌할 수 있다(순위 5) |

## 7. 순위 4 처리 (2026-11-02)

| 항목 | 내용 |
|---|---|
| 정한 것 | "문서로 문제 생성"에만 배치와 같은 검수기(`ClaudeProblemReviewer`)를 붙인다. 객관식만, 생성 직후 같은 요청에서 돌린다. 생성 화면의 "AI 검수도 돌리기" 체크박스로 끌 수 있고 처음부터 켜 둔다 |
| 고르지 않은 안 | 근거 없는 "문제 생성"에도 검수 붙이기. 검수기가 근거 문서와 대조하는 구조라 문서 없이 쓰려면 프롬프트를 새로 써야 하고, 얼마나 잡는지 잰 적이 없다. 저장 뒤 따로 검수하기. 기다림은 줄지만 "검수 중" 상태와 실패 처리가 새로 필요하다 |
| 바뀐 동작 | 지적은 배치처럼 질문 글자로 초안에 짝지어 적는다(`DraftAiFinding.groupByQuestion`, 배치 들여오기와 같은 함수). 검수가 실패하면 초안은 지적 없이 저장하고, 생성 화면이 "AI 검수를 돌리지 못했습니다"라고 알린다 |
| 남는 것 | 근거 없는 "문제 생성"은 여전히 검수가 없다. 화면에 그 이유를 적었다. 배치가 함께 싣는 "근거 문단에 사실 지적"(`SOURCE_FLAGGED`)은 이 경로에 없다. 문서 초안의 사실 지적을 읽어 오지 않기 때문이다 |
| 확인 | 서비스 테스트 4개(검수·끄기·객관식 아님·검수 실패). 8081에서 체크박스가 근거·유형에 맞게 잠기는 것과 요청 칸이 묶이는 것을 봤다. 실제 Claude 호출은 요금이 들어 돌리지 않았다 |

## 8. 순위 5 처리 (2026-11-03)

| 항목 | 내용 |
|---|---|
| 정한 것 | 쓰는 쪽마다 파일을 나눈다. 대기열 파일(`_topics.json`·`_code-topics.json`)은 앱만, 사용 기록 파일(`_topic-usage.json`·`_code-topic-usage.json`)은 배치만 쓴다 |
| 고르지 않은 안 | "배치로 보내기"가 충돌을 자동으로 합치는 안. 보내기 코드가 대기열 내용을 알아야 해서 둘이 엮인다. 코드를 두고 절차만 문서로 적는 안 |
| 바뀐 동작 | 배치는 두 파일을 합쳐 다음 주제를 고르고, 쓴 주제의 사용일·횟수를 사용 기록 파일에만 적는다. 앱은 기동할 때 사용 기록 파일을 DB에 읽는다. 번호 없이 손으로 적은 줄은 분야와 주제 글자로 짝짓는다 |
| 초기화 | 사용 기록 파일은 앱이 지울 수 없어서, 관리 화면에서 초기화하면 초기화한 날을 DB(`topic_queue.usage_reset_at`, V46)와 대기열 파일(`usageResetAt`)에 남긴다. 앱과 배치는 그날까지의 기록을 무시한다 |
| 옮기지 않은 것 | 지금 대기열 파일에 있는 사용일은 그대로 둔다. 배치가 두 파일 중 늦은 날짜를 쓰므로 기록을 잃지 않는다 |
| 확인 | 배치 쪽 테스트 6개(사용 기록 파일에만 씀, 편수, 안내문, 글자로 짝짓기, 초기화, 깨진 파일), 앱 쪽 테스트 4개(번호로 반영, 글자로 반영·지운 줄 무시, 초기화, 초기화 날 내보내기) |
| 남는 것 | 사람이 손으로 문서를 써 넣을 때도 사용일은 사용 기록 파일에 찍는다 |

## 10. 처리 뒤 코드 검토 (2026-11-03)

| 지적 | 처리 |
|---|---|
| 코드 문제 워크플로가 커밋 단계로 `_code-topic-usage.json`을 넘기지 않아 매주 같은 주제가 걸린다 | 넘기는 파일 목록에 더했다. 순위 5에서 생긴 구멍이다 |
| 보내기 중 rebase가 시간을 넘기면 도중 상태로 남고 사람 작업이 stash에 갇힌다 | rebase를 되돌리고 stash를 꺼낸다. 커밋은 남겨 다음에 push만 한다 |
| 배지의 `git status`가 보내기와 겹치면 `index.lock` 때문에 보내기가 실패하거나 거짓 충돌이 뜬다 | git 명령에 `GIT_OPTIONAL_LOCKS=0`을 준다. 조회가 잠금을 잡지 않는다 |
