# 12. 오늘의 퀴즈 (데일리 세트) — 로드맵 6

> 결정 기록: [ADR-0005](adr/0005-daily-quiz-set.md) (세트 저장 + 지연 생성)
> 선행 문서: [10-review-recommendation](10-review-recommendation.md) — 복습 사다리가 세트의 재료가 된다.

## 쉽게 말하면

매일 접속하면 **나에게 맞는 문제 10개가 자동으로 차려져 있는** 기능이다.
급식에 비유하면 — 메뉴(문제)는 이미 주방에 있고, 매일 아침 영양사가
"오늘의 식단"을 짜 주는 것. 새 문제를 만드는 게 아니라 **고르는** 기능이다.

진짜 목적은 문제 추천 자체가 아니라 **습관 형성**이다. 매일 공부하려면
"오늘은 뭘 풀지, 몇 개나, 복습도 해야 하나"를 스스로 정해야 하는데,
이 **선택하는 수고가 매일 하는 습관의 가장 큰 적**이다. 오늘의 퀴즈는
그 결정을 시스템이 대신해서, 사용자는 "출석해서 풀기"만 하면 되게 만든다.

- 홈 화면: **"오늘의 퀴즈 10문제 (3/10 완료)"** 카드 → [이어서 풀기]
- 다 풀면: "오늘 완료! 🔥 연속 5일째" (스트릭 표시)

## 세트 배합 레시피

무작위 10개면 기존 퀴즈 페이지와 다를 게 없다. 이 기능의 핵심 가치는 **배합**이다.

| 구성 | 목표 개수 | 뽑는 기준 | 왜 |
|---|---|---|---|
| 복습(REVIEW) | 4 | 사다리에서 오늘이 예정일인 것, 오래 밀린 순 | 잊기 직전에 다시 봐야 기억이 굳는다 (docs/10) |
| 취약(WEAK) | 3 | 내 정답률이 낮은 도메인의 문제, 무작위 | 약점은 방치하면 영영 약점 |
| 새 문제(NEW) | 3 | 한 번도 안 푼 문제, 무작위 | 복습만 하면 진도가 안 나간다 |

### 배합 세부 규칙

- **중복 제거**: 복습으로 뽑힌 문제는 취약/새 문제 후보에서 제외한다. 같은 칸을 두 번 채우지 않는다.
- **취약 도메인 판정**: 사용자별 도메인 정답률 하위 도메인에서 뽑는다. 단,
  **제출 5회 미만인 도메인은 판정에서 제외** — 2문제 풀고 1개 틀렸다고 "취약"이라
  단정하는 건 통계가 아니라 소음이다(표본이 작으면 신뢰하지 않는다).
  ⚠️ 기존 `domain_stats` 뷰(R__)는 **전체 사용자** 집계라 여기 못 쓴다 —
  사용자별(user_id 조건) 집계 쿼리가 따로 필요하다.
- **부족분 채우기(fallback)**: 각 칸이 목표를 못 채우면 아래 순서로 메꾼다.
  1. 복습이 4개 미만 → 부족분만큼 새 문제를 더 뽑는다 (밀린 복습이 없다 = 여유가 있다 = 진도)
  2. 취약 판정 불가(데이터 부족) → 새 문제로 채운다
  3. 새 문제도 바닥나면(문제 풀을 다 풀었으면) → 이미 푼 문제 중 무작위(GENERAL)
  4. 그래도 10개가 안 되면 → **작은 세트를 허용**한다. 문제 수를 맞추려고
     같은 문제를 두 번 넣는 것보다 "오늘은 7개"가 정직하다.
- **ESSAY 제외**: 자동 채점 불가 유형은 퀴즈 API와 동일하게 세트에 못 들어온다.

### 설계 포인트: 세트는 하루 동안 "고정"이다

오늘 세트가 정해지면 새로고침해도, 다른 기기로 접속해도 **같은 10문제**여야 한다.
그래야 "3/10 완료"라는 진행률이 의미를 가진다. 기존 퀴즈 API(`ORDER BY RAND()`)는
매번 다른 문제를 주므로 재사용할 수 없고, **뽑은 결과를 저장하는 테이블이 필요**해진다.
이것이 이 기능의 데이터 모델이 존재하는 이유다(ADR-0005).

### 설계 포인트: 어제 세트는 리셋된다 (밀림 누적 없음)

어제 세트를 다 안 풀었어도 오늘은 새 세트만 보인다. 밀린 숙제가 쌓이는 구조는
부담감 때문에 오히려 접속을 꺼리게 만든다(습관 형성이라는 목적에 역행).
잃는 것도 없다 — 복습 예정은 어차피 사다리(`review_item`)가 따로 관리하고 있어서,
어제 못 푼 복습 문제는 오늘 세트의 복습 칸에 다시 뽑힌다. 어제 행은 지우지 않고
그대로 남는다(스트릭 계산과 학습 기록의 재료).

### 설계 포인트: 복습 페이지와의 관계 = "요약판 ↔ 상세판"

오늘의 퀴즈에 복습 문제가 포함되므로 기존 복습 페이지와 겹쳐 보이지만, 역할이 다르다.

- **오늘의 퀴즈**: 오늘 할 일의 요약판. 복습 중 가장 급한 4개만 담는다.
- **복습 페이지**: 전체 현황판. 밀린 복습이 4개보다 많으면 여기서 마저 푼다. 졸업 현황도 여기.

채점 경로가 `QuizService.submit()` 하나뿐이므로(docs/10의 설계), 오늘의 퀴즈에서
복습 문제를 풀어도 **사다리 승급/리셋이 자동으로 반영**된다. 별도 동기화 코드가 필요 없다 —
쓰기 경로를 하나로 유지한 설계가 여기서 보상을 준다.

## 세트 생성 시점 — 지연 생성 (lazy)

"매일"을 실행하는 방법 세 가지 중 **지연 생성**을 택했다(상세 비교는 ADR-0005).

| 방식 | 내용 | 판단 |
|---|---|---|
| `@Scheduled` 자정 배치 | 매일 0시에 전 사용자 세트 미리 생성 | 앱이 꺼져 있으면(로컬 PC) 그날 세트가 없다. 안 올 사용자 것까지 만드는 낭비 |
| **지연 생성 (채택)** | 그날 첫 조회 때 "오늘 세트 없으면 만들어서" 반환 | 앱 가동 시간과 무관하게 항상 동작. 온 사람 것만 만든다 |
| 클라이언트 계산 | 저장 없이 매번 조합 | 세트 고정 불가(새로고침마다 바뀜) → 진행률 무의미. 탈락 |

- "하루"의 기준: **서버 날짜(LocalDate, KST)**. 자정에 바뀐다.
- 동시 첫 조회(탭 2개)로 세트가 2개 생기는 경합은 **UNIQUE(user_id, quiz_date)**가 막는다 —
  review_item의 UNIQUE 제약과 같은 패턴(경합 방지는 코드가 아니라 DB 제약의 몫).

## 데이터 모델

세트(머리) + 항목(줄) 2테이블. 사용자 × 날짜당 세트 1개.

### `daily_quiz` — 세트

| 컬럼 | 타입 | 제약 | 비고 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | |
| user_id | BIGINT | FK → user(id), NOT NULL | |
| quiz_date | DATE | NOT NULL | 이 세트가 속한 날 |
| completed_at | DATETIME(6) | NULL | 모든 항목을 푼 시각. NULL = 미완료 |
| created_at | DATETIME(6) | NOT NULL | |
| | | UNIQUE(user_id, quiz_date) | 하루 1세트 보장 + 동시 생성 경합 방지 |

### `daily_quiz_item` — 세트 안의 문제 한 줄

| 컬럼 | 타입 | 제약 | 비고 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | |
| daily_quiz_id | BIGINT | FK → daily_quiz(id) CASCADE, NOT NULL | 세트가 지워지면 같이 |
| problem_id | BIGINT | FK → problem(id), NOT NULL | |
| seq | INT | NOT NULL | 세트 안 표시 순서 (1..N) |
| source | VARCHAR(10) | NOT NULL | enum `REVIEW` / `WEAK` / `NEW` / `GENERAL` — 어느 칸으로 뽑혔나 |
| submission_id | BIGINT | FK → submission(id), NULL | 이 세트에서 푼 제출. NULL = 아직 안 풂 |
| | | UNIQUE(daily_quiz_id, problem_id) | 세트 안 중복 문제 금지 |

- **풀었는지를 boolean이 아니라 `submission_id`로 저장하는 이유**: "풀었음" 플래그만 남기면
  맞았는지·뭐라고 답했는지를 또 조회해야 한다. 제출 이력을 가리키면 정답 여부·제출 시각이
  전부 따라온다(진실의 원천은 여전히 submission — 여기는 연결만).
- **`source`를 저장하는 이유**: 조회 시점엔 재계산이 불가능한 값이다(그날의 사다리 상태·
  정답률 스냅숏으로 뽑았으므로). 또한 "복습 문제를 잘 맞히나, 새 문제를 잘 맞히나" 같은
  나중 분석의 재료가 된다.
- **완료(completed_at)는 저장한다**: "시간이 흐르면 저절로 바뀌는 값은 저장하지 않는다"(docs/10)
  원칙과 충돌하지 않는다 — 완료는 시간이 아니라 **제출이라는 사건**으로 확정되는 값이고,
  스트릭 계산이 매번 항목 전체를 세지 않도록 세트에 도장을 찍어 두는 것이다.

## 스트릭 (연속 일수)

- 정의: **오늘(또는 어제)부터 거슬러 올라가며 연속으로 완료(completed_at NOT NULL)된 날 수.**
  오늘 아직 미완료여도 어제까지 이어져 있으면 스트릭은 살아 있다(오늘 풀면 +1).
- **저장하지 않고 조회 시점에 계산**한다(파생값 원칙 재적용) — `daily_quiz`에서 최근 완료
  날짜들을 내림차순으로 읽어 연속성이 끊길 때까지 센다. 하루 1행이라 1년 치가 365행,
  계산 비용은 무시할 수준. 저장하면 자정마다 "끊김"을 갱신할 배치가 필요해진다.
- MVP 범위: 숫자 표시까지만. 배지·보상·최고 기록 같은 게임화는 하지 않는다.

## API (초안)

기존 응답 봉투(docs/04)·인증(JWT) 규칙을 그대로 따른다.

### `GET /api/me/daily-quiz` — 오늘 세트 조회 (없으면 생성)

지연 생성의 입구. 오늘 세트가 있으면 그대로, 없으면 만들어서 돌려준다(멱등).

```json
{
  "success": true,
  "data": {
    "quizDate": "2026-07-15",
    "completed": false,
    "streak": 4,
    "progress": { "total": 10, "solved": 3 },
    "items": [
      {
        "seq": 1,
        "source": "REVIEW",
        "solved": true,
        "correct": false,
        "problem": { "...": "QuizProblemItem과 동일(정답·해설 미포함)" }
      }
    ]
  }
}
```

- `problem`은 퀴즈 API의 `QuizProblemItem`을 재사용한다(정답 미포함 원칙 동일).
- `correct`는 푼 항목에만 존재(미풀이면 null) — 이어서 풀 때 "앞에서 뭘 틀렸는지" 표시용.

### 제출 — 기존 `POST /api/quiz/submit` 재사용 (새 API 없음)

채점 경로는 계속 하나다. submit이 채점·이력 저장·사다리 반영을 마친 뒤,
**오늘 세트에 이 문제가 미풀이 상태로 있으면 `submission_id`를 연결**하고,
마지막 항목이었으면 `completed_at`을 찍는다. ReviewService.onSubmission과 같은
패턴(같은 트랜잭션 합류, `Propagation.MANDATORY`)으로 붙인다 —
"채점은 됐는데 세트 진행률만 안 바뀐" 어중간한 상태를 금지.

- 세트에 없는 문제의 제출은 세트와 무관하게 지금처럼 동작한다(일반 퀴즈/복습 페이지 풀이).
- 세트 항목을 세트 밖(일반 퀴즈 등)에서 우연히 풀어도 연결한다 — 사용자 입장에서
  "아까 풀었는데 왜 미완료지?"가 더 이상하다. 판정 기준은 "오늘 세트에 있고 아직 미풀이"뿐.

## UI

- **홈(index.html)**: 로그인 상태면 "오늘의 퀴즈" 카드가 최상단 —
  미시작("시작하기") / 진행 중("3/10 · 이어서 풀기") / 완료("오늘 완료 🔥 N일째") 3상태.
- **플레이어**: 기존 단계형 플레이어(player.js) 재사용, 데일리 모드로 진입만 다르게.
  다 풀면 완료 화면(정답률 요약 + 스트릭).
- **내비게이션**: 복습 배지처럼 과하게 늘리지 않는다 — 홈 카드가 입구다.

## 하지 않는 것 (MVP 경계)

- 밀린 세트 누적/이월 (위 리셋 정책)
- 알림·푸시 ("들어오면 보인다"까지만 — 들어오게 만드는 건 스트릭의 몫)
- 배합 비율의 사용자 설정·개인화 학습 (상수 4/3/3으로 시작, 값 튜닝은 상수 수정으로 끝)
- LLM 문제 자동 생성 (B안 — 별도 로드맵. 이 기능의 "문제 풀 공급"이 아쉬워질 때 재논의)

## 재검토 트리거

- 문제 풀이 부족해 GENERAL 채움이 자주 발생하면 → B안(문제 생성) 논의 시작.
- 사용자가 늘어 "그날 첫 조회"가 몰리는 시간대에 생성 비용이 보이면 → 배치 사전 생성 재검토.
- 배합 효과를 측정하고 싶어지면 → source별 정답률 분석 (item에 source를 남겨 둔 이유).
