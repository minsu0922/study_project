# 웹 접근성 점검 (2026-09-07)

국내 웹 접근성 인증(WA)의 심사 기준인 **KWCAG 2.2** 24개 항목을 기준으로 사용자 화면
11개를 점검했다. 관리 콘솔은 내부 도구라 인증 범위에서 빼고 봤다.

점검 방법은 **브라우저에서 직접 재는 것**이다. 체크리스트를 눈으로 훑는 방식은
"있어 보이는데 실제로는 안 되는" 것을 놓친다 — 실제로 이번에 걸린 것 중 셋이 그런
종류였다(글자 대비는 12:1인데 안 읽히던 것, 버튼처럼 보이는데 키보드로 못 가는 것,
`role`이 없어 스크린리더에게는 다른 물건인 것).

---

처음 점검했을 때는 **떨어지는 상태**였다. 필수 항목 넷이 걸렸고, 같은 날 전부 고쳤다.

| 보완 권고 | 4 | 2 |
| 통과 | 나머지 | 나머지 |

고친 내용은 아래 각 항목에 "고침" 문단으로 붙여 두었다. 남은 권고 둘은 3장에 있다.

대비(명도 4.5:1, 비텍스트 3:1)는 **이번 주에 두 번 손봐서** 지금은 통과한다.
그 과정 자체가 이 문서의 교훈 하나를 만들었다 — 아래 5장.

## 2. 위반 — 고쳐야 통과한다

### 2.1 키보드로 개념 문서를 열 수 없다 (6.1.1 키보드 사용 보장)

`documents.html`의 문서 카드 10개가 이렇게 생겼다.

```html
<div class="card clickable" onclick="location.href='/document.html?slug=...'">
```

`div`에 `onclick`만 있고 `tabindex`도 `role`도 없다. **마우스 없이는 문서를 하나도
열 수 없다.** 키보드 사용 보장은 인증의 필수 항목이고, 예외 없이 불합격 사유다.

카드 안에 제목 링크(`<a>`)가 이미 있다는 점이 함정이다. 탭으로 그 링크에는 갈 수 있어서
"되는 것처럼" 보인다. 그러나 카드 전체가 누를 수 있게 생겼는데 키보드에게는 카드가
존재하지 않는다 — 보이는 것과 조작할 수 있는 것이 어긋난다.

고치는 방향은 `tabindex`를 붙이는 것이 아니라 **카드 자체를 `<a>`로 만드는 것**이다.
`div`에 `tabindex="0"`과 `role="link"`와 키 처리를 붙이면 브라우저가 공짜로 주는 것
(초점·엔터·새 탭으로 열기·주소 복사)을 전부 손으로 다시 만들게 된다.

**고침.** 카드를 `<a>`로 바꾸고 제목의 안쪽 `<a>`를 없앴다(링크 안에 링크는 넣을 수
없다). CSS에서 `display:block`과 색·밑줄을 되돌려야 했다 — `<a>`는 기본이 inline이라
카드가 글자처럼 접히고, 전역 링크 색이 카드 전체를 남보라로 만든다.

### 2.2 반복 영역 건너뛰기 링크가 없다 (5.1.2)

11개 화면 전부에 없다. 스크린리더나 키보드 사용자는 화면을 옮길 때마다 메뉴 7개를
지나야 본문에 닿는다.

`main`·`nav`·`header` 랜드마크는 제대로 있어서 스크린리더 사용자는 우회할 수단이
있지만, **키보드만 쓰는 사용자에게는 랜드마크가 아무 도움이 안 된다.** 심사도 링크의
존재를 본다.

**고침.** 셸이 그린다 — 화면마다 손으로 넣으면 새 화면에서 반드시 빠뜨린다.
닿을 자리(`main`의 id와 `tabindex="-1"`)도 셸이 챙긴다. `tabindex="-1"`이 없으면
브라우저에 따라 **스크롤만 내려가고 초점은 메뉴에 남아**, 다음 탭이 본문이 아니라
메뉴의 그다음 항목으로 간다.

### 2.3 보기를 골라도 무엇을 골랐는지 안 읽힌다 (이름·역할·값)

퀴즈 플레이어의 보기는 `<button class="opt">`다. `role`도 `aria-pressed`도 없다.

- 스크린리더는 "버튼"이라고만 읽는다. **4지선다라는 사실이 전달되지 않는다.**
- 고른 뒤에도 상태가 바뀌지 않는다. 화면에는 남보라 테두리가 생기지만, 그건 눈으로만
  보이는 신호다. **무엇을 골랐는지 소리로는 알 수 없다.**

이 화면은 이 앱이 존재하는 이유다. 다른 화면이 다 통과해도 여기가 막히면 의미가 없다.

고치는 방향은 두 가지다. `role="radio"` + `aria-checked`로 라디오 그룹을 만들거나,
버튼을 유지하고 `aria-pressed`를 다는 것. 라디오 쪽이 "넷 중 하나"라는 뜻을 정확히
전달하지만 화살표 키 이동까지 구현해야 한다(라디오 그룹의 규약이다).

**고침 — 뒤를 골랐다.** 라디오 그룹은 "화살표로 옮기고 탭은 그룹을 통째로 건너뛴다"는
약속이 붙어 있는데, 이 화면의 키보드 규약은 이미 다르다(숫자키로 고르고 탭으로 보기를
하나씩 지난다). 역할만 라디오로 바꾸면 화살표를 눌렀는데 아무 일도 안 일어나는,
**말과 행동이 다른** 상태가 된다. 지금 있는 규약을 정확히 설명하는 쪽을 골랐다 —
누를 수 있는 것들이고(button), 그중 눌린 것이 있다(`aria-pressed`). 묶음에는
`role="group"`과 이름("보기 4개")을 줬다. 다섯 유형 전부에 적용했다.

### 2.4 자유 퀴즈 필터에 레이블이 없다 (7.3.2 레이블 제공)

`quiz.html`의 `fDomain`·`fLevel`·`fType`·`fSize` 넷이 `<label for>` 연결이 없다.
화면에는 글자가 보이지만 `for`가 없어 **연결이 아니라 배치일 뿐**이다.
같은 화면의 다른 폼들은 연결돼 있어서, 이 넷만 빠졌다.

**고침.** `for`를 넷 다 연결했다. 라벨을 눌러도 칸이 잡히므로 손가락 표적도 넓어진다.

## 4. 통과한 것

재서 확인한 것만 적는다.

| 항목 | 실측 |
| --- | --- |
| 명도 대비 (4.5:1) | 16개 화면 두 테마, 글자 요소 2,195개 미달 0 |
| 비텍스트 대비 (3:1) | 보기 칩 4.99~5.62, 입력 칸 3.45~3.92 |
| 초점 표시 | 2px 실선, 라이트 6.29:1 · 다크 4.98:1 (기준 3:1) |
| 확대/리플로우 | 320px 폭에서 가로 스크롤 없음(5개 화면) |
| 기본 언어 | 전 화면 `lang="ko"` |
| 제목 제공 | 화면마다 고유한 `<title>`, `h1` 정확히 1개 |
| 조작 표적 크기 | 버튼 최소 44px |
| 진행 표시 | `role="progressbar"` + `aria-valuenow/min/max/label` |

| 색에 무관한 인식 | 정답·오답은 색과 함께 "✓ 정답"·"✕ 내 답" 글자를 준다 |
| 자동 재생 · 깜빡임 · 시간 제한 | 해당 기능 없음 |

## 5. 이번 점검에서 배운 것

**눈금을 하나만 대고 있으면 통과 표시가 거짓말을 한다.**

며칠 전까지 이 프로젝트의 접근성 확인은 "글자 대비 4.5:1"이 전부였다. 그 눈금으로는
0건 실패였는데, 정작 사용자는 "안 읽힌다"고 했다. 재 보니 원인이 셋이었고 셋 다
그 눈금 밖에 있었다.

1. **작은 글자의 4.5:1은 편하지 않다.** 11px 회색 글자가 4.76:1로 통과하고 있었다.
   AA는 "읽을 수 있다"는 하한이지 "읽기 편하다"가 아니다.
2. **글자만 재고 상자를 안 쟀다.** 보기 칩은 글자가 12:1인데 칩과 카드가 같은 색이고
   테두리가 1.23:1이었다. 규격에도 이 항목이 따로 있다(비텍스트 대비 3:1).
3. **재는 방법이 대상을 건드리고 있었다.** 테마를 런타임에 뒤집고 재니 없는 미달이
   90개 나왔다. 새로 고쳐 들어가 재야 진짜 값이 나온다.

그리고 이번 점검의 큰 세 건은 **대비와 아무 상관이 없다.** 키보드로 못 가는 카드,
역할이 없는 보기, 없는 건너뛰기 링크 — 색을 아무리 고쳐도 나오지 않는 것들이다.
접근성은 색의 문제가 아니라 **"보이는 것과 조작할 수 있는 것이 같은가"** 의 문제다.
