# 카드 1 — 복합 인덱스 설계와 실측 검증 (1.8초 → 16ms)

## 30초 버전

> "오답노트 조회에 `(user_id, is_correct, submitted_at)` 복합 인덱스를 설계 단계에서 걸어뒀는데,
> 정말 효과가 있는지 확인하려고 제출 데이터 50만 건을 넣고 인덱스를 뺐다 넣었다 하며 실측했습니다.
> API 응답이 16ms에서 1.8초로, 실행 계획이 5행 Index lookup에서 50만 행 Table scan으로 갈렸습니다."

## 상세 버전

> "오답노트 조회에 `(user_id, is_correct, submitted_at)` 복합 인덱스를 설계 단계에서 걸어뒀고,
> 제출 50만 건을 넣고 실측해 인덱스 유무로 API 응답이 16ms ↔ 1.8초, 실행 계획이 5행 Index lookup ↔
> 50만 행 Table scan으로 갈리는 것을 확인했습니다.
>
> 컬럼 순서는 선택도가 높은 등호 조건인 `user_id`를 맨 앞, 등호 조건인 `is_correct`를 두 번째,
> 정렬에 쓰는 `submitted_at`을 마지막에 뒀습니다. `is_correct`는 값이 true/false 2개뿐이라
> 선택도만 보면 최악이지만, 복합 인덱스는 **등호 조건이 앞에 와야 뒤 컬럼의 정렬이 유지**되기 때문에
> 이 순서여야 `ORDER BY submitted_at DESC`가 filesort 없이 인덱스만으로 해결됩니다.
>
> 부수적으로, 이 인덱스가 FK 제약의 기반 인덱스를 겸하고 있어서 `DROP INDEX`가 거부되는 것도
> 경험했습니다."

## 근거 숫자 (외울 것)

| 측정 항목 | 인덱스 있음 | 인덱스 없음 | 차이 |
|---|---|---|---|
| API 응답 시간 (워밍업 후) | **12~17ms** | **1,081~1,769ms** | 약 70~100배 |
| SQL 실행 시간 (EXPLAIN ANALYZE) | 0.55ms | 390ms | 약 700배 |
| 읽은 행 수 (바깥 쿼리) | **5행** | **500,010행** | 10만 배 |
| 인덱스 재생성 시간 (50만 행) | 2.1초 | — | 운영 중 추가도 부담 적음 |

데이터: 회원 1,002명 / 제출 500,010건. 측정: `EXPLAIN ANALYZE` + `curl -w %{time_total}`.

```
있음:  -> Index lookup on s using idx_submission_user_correct (user_id=1, is_correct=0) ... rows=5
없음:  -> Table scan on s ... rows=500010  → Sort: s.submitted_at DESC
```

## 어떤 쿼리였나

`SubmissionRepository.findLatestWrongAnswers` — "내가 틀린 문제를, 문제마다 최근에 틀린 기록 1건씩, 최신순".

```sql
where s.user_id = :userId             -- ① 등호
  and s.is_correct = false            -- ② 등호
  and s.id = (select max(s2.id) ...)  -- ③ 문제당 최신 1건
order by s.submitted_at desc          -- ④ 정렬
```

`submission`은 전체 사용자의 제출이 쌓이는 테이블 → 인덱스가 없으면 내 5행을 찾으려고 50만 행을 전부 읽는다.

## 컬럼 순서 방어 논리 ← 진짜 질문은 이것

복합 인덱스 = **전화번호부**. 성 → 이름 순 정렬이면 "김"으로는 찾지만 "철수"만으로는 못 찾는다.
**앞 컬럼부터 순서대로 써야 작동한다**(leftmost prefix 규칙).

| 순서 | 컬럼 | 이유 |
|---|---|---|
| 1 | `user_id` | 등호 조건 중 **선택도 최고**. 1,002명이면 50만 → 평균 500행으로 한 번에 잘라낸다 |
| 2 | `is_correct` | 값이 2개뿐이라 선택도는 최악이지만 **등호 조건**이라 앞에 온다. 기준은 카디널리티가 아니라 **"등호 먼저, 범위/정렬 나중"** |
| 3 | `submitted_at` | 앞 둘이 등호로 고정되면 그 구간은 이미 이 컬럼 순으로 줄 서 있다 → **정렬이 공짜**(인덱스 역순 읽기) |

**"반대 순서면 왜 안 되나요?"**
→ `(submitted_at, user_id, is_correct)`였다면 첫 컬럼에 등호 조건이 없어 **탐색 시작 지점 자체가 없다.** 사실상 전체 스캔.

**"is_correct는 값이 2개뿐인데 넣을 가치가 있나요?"**
→ 단독 인덱스라면 무가치하다. 여기서는 `user_id`로 좁혀진 500행에서 다시 절반을 걸러내고,
무엇보다 **뒤의 `submitted_at`이 정렬용으로 살아나게 하는 징검다리**다.

## 부수 발견 — 인덱스가 FK의 버팀목이었다

```
Cannot drop index 'idx_submission_user_correct': needed in a foreign key constraint
```

InnoDB는 FK 컬럼(`user_id`)에 인덱스를 **반드시** 요구하는데, 복합 인덱스의 첫 컬럼이 `user_id`라
**FK용 인덱스를 겸하고 있었다** — MySQL이 별도 인덱스를 자동 생성하지 않은 이유가 이것.
실험을 위해 FK를 잠시 내리고 진행한 뒤 둘 다 복구했다.

→ **교훈: 인덱스는 조회 성능만이 아니라 제약조건의 기반이기도 하다.**
문서로는 안 배워지고 실제로 지우다 막혀야 아는 내용이라, 실습 증거로 강력하다.

## ⚠️ 표현 주의

이 인덱스는 **V1 마이그레이션 설계 단계(ADR-0002)에서 미리 걸어둔 것**이고, 실험은 **사후 검증**이다.

- ❌ "느려서 개선했습니다" → "언제 느린 걸 발견했나요?"에서 답이 꼬인다
- ✅ **"설계 단계에서 근거를 갖고 걸었고, 진짜 효과가 있는지 50만 건 넣어 검증했습니다"**

## 꼬리질문

**Q. 인덱스를 걸면 무조건 좋은가요?**
> "쓰기 비용이 붙습니다. INSERT/UPDATE마다 인덱스도 갱신하고 디스크도 더 씁니다.
> `submission`은 제출할 때 1행씩 INSERT되는 패턴이라 쓰기 부담이 작고 조회 이득이 압도적이라 걸었습니다.
> 실측으로 50만 행 인덱스 재생성이 2.1초였으니 운영 중 추가도 부담이 적습니다."

**Q. 다른 느린 쿼리는 없었나요?**
> "퀴즈 무작위 추출의 `ORDER BY RAND()`를 같이 측정했습니다. 문제 24개일 땐 12ms인데
> 10만 개를 넣으니 180ms로 15배가 됐습니다. `LIMIT 10`인데도 10만 행 전부에 rand()를 계산해
> 정렬하기 때문입니다."

**Q. 그럼 고쳤나요?** ← **"안 고쳤다"가 정답**
> "안 고쳤습니다. 개선 방향(랜덤 id 샘플링)까지 설계했지만, 현재 규모인 수백 문제에서는 12ms라
> 지금 바꾸는 건 과최적화입니다. 이번 실험의 성과는 성능 개선이 아니라 **'언제 바꿔야 하는지의
> 기준(수만 건 이상)'을 숫자로 확보한 것**이라고 봤습니다."

**Q. 서브쿼리(`max(s2.id)`)는 안 무거운가요?**
> "무거워질 수 있습니다. 그래서 ADR-0002에 재검토 트리거를 적어뒀고, 실제로 복습 추천 기능에서
> '다음 복습일·복습 횟수'라는 고유 상태가 생기는 순간 `ReviewItem` 테이블로 분리했습니다.
> 중복 데이터를 미리 만들지 않고 **분리 시점을 데이터의 고유성으로 판단한** 사례입니다."

# 카드 2 — 토큰 버킷 요청 제한을 Redis Lua로 직접 구현

## 30초 버전

> "로그인 무차별 대입을 막으려고 요청 제한을 직접 구현했습니다. 고정 윈도우는 경계에서 한도가
> 2배로 뚫려서 토큰 버킷을 골랐고, 판정이 '읽고-계산하고-쓰는' 구조라 나누면 경쟁 상태가 생기기 때문에
> Lua 스크립트로 묶어 Redis가 원자적으로 실행하게 했습니다."

## 상세 버전

> "요청 제한을 토큰 버킷으로 직접 구현했습니다.
>
> **알고리즘**: 고정 윈도우는 경계에서 한도가 2배로 뚫리는 문제가 있고, 슬라이딩 윈도우 로그는
> 요청마다 타임스탬프를 다 저장해서 비쌉니다. 토큰 버킷은 **버스트와 평균 속도를 독립적으로 제어**할 수
> 있어서 골랐습니다. 저희 프론트는 페이지 하나가 API를 5~6개 동시에 부르는데, 그 정상 패턴을 막지
> 않으면서 평균 속도만 제한할 수 있다는 게 결정적이었습니다.
>
> **저장 위치**: 앱 메모리에 두면 서버가 늘어날 때 한도가 서버 수만큼 뻥튀기되고, RDB에 두면
> DB를 지키려는 장치가 매 요청 UPDATE로 DB를 죽이는 자충수가 됩니다. 서버가 늘어도 한도가
> 공유되도록 Redis에 뒀습니다.
>
> **왜 Lua인가**: 읽고-계산하고-쓰는 판정을 GET/SET로 나누면, 동시에 들어온 두 요청이 같은
> '토큰 1개 남음'을 읽고 둘 다 통과하는 경쟁 상태가 생깁니다. Lua 스크립트로 묶으면 Redis가
> 통째로 원자 실행하므로 이 문제가 사라집니다. 분산 락보다 훨씬 싸고 간단합니다.
>
> **부속 결정**: 시각은 서버 간 clock skew를 없애려고 Redis TIME을 쓰고, 충전은 스케줄러 없이
> 요청 시점에 흐른 시간만큼 몰아서 하는 lazy refill입니다. 제한기 장애가 서비스 장애가 되지 않도록
> fail-open으로 두되 경고 로그로 관측 가능하게 했고, 키는 로그인 전 경로만 IP·나머지는 사용자 id로
> 세서 NAT 뒤 사용자들이 억울하게 묶이지 않게 했습니다."

## 왜 토큰 버킷인가 — 버린 선택지가 곧 근거

**토큰 버킷이란**: 사용자마다 양동이 하나. 요청 1번 = 토큰 1개 소모.
토큰은 시간에 비례해 차되 양동이 크기(capacity)를 넘지 않는다. 빈 양동이면 거부.

| 후보 | 버린 이유 |
|---|---|
| **고정 윈도우 카운터** | **경계 문제.** 0:59에 60번 + 1:01에 60번 = 2초간 120번 통과. "분당 60회"라 해놓고 순간 120회를 허용하면 무차별 대입 방어 목적 자체가 흔들린다 |
| **슬라이딩 윈도우 로그** | 요청 타임스탬프를 전부 ZSET에 저장. 정확하지만 요청당 메모리·연산 비용이 크다 |
| **토큰 버킷** ✅ | **버스트와 평균을 분리 제어.** 저장은 키당 숫자 2개(`tokens`, `ts`). 경계 문제 없음 |

**"버스트와 평균의 분리"가 왜 결정적이었나** — 우리 프로젝트의 구체적 사정:
프론트에서 **페이지 하나가 API를 5~6개 동시 호출**한다. 순간 속도만 보는 방식이면 정상 사용자도 차단된다.
토큰 버킷은 "평균은 분당 60회로 묶되, 순간에 60개까지는 몰아 써도 된다"를 표현할 수 있다.

## 카운터를 어디에 둘 것인가

| 후보 | 판단 |
|---|---|
| 앱 메모리(Caffeine) | 제일 빠르지만 **서버 2대면 한도도 2배**. 재시작하면 리셋 |
| RDB | 매 요청 UPDATE = **DB를 지키려는 장치가 DB를 죽이는 자충수** |
| **Redis** ✅ | 메모리 속도 + 서버 간 공유 + TTL로 청소 공짜. 로드맵 2에서 이미 도입해 **추가 인프라 없음** |

## 왜 Lua인가 — 경쟁 상태를 칠판에 그린다

판정은 3단계: **① 현재 토큰을 읽고 → ② 충전·차감을 계산하고 → ③ 다시 쓴다.**

```
토큰이 1개 남은 상태에서 요청 A와 B가 동시 도착

A: GET → "1개 남음"  ┐
B: GET → "1개 남음"  ┘  둘 다 같은 값을 읽는다
A: SET → "0개"  → 통과
B: SET → "0개"  → 통과    ← 토큰 1개로 2번 통과. 제한이 뚫렸다
```

이것이 **check-then-act 경쟁 상태**.

| 해결책 | 판단 |
|---|---|
| 분산 락 | 락 획득/해제 왕복이 더 붙고 만료·데드락 처리까지 따라온다. 요청마다 거는 건 과하다 |
| **Lua 스크립트** ✅ | Redis는 **싱글 스레드**라 스크립트 실행 중 다른 명령이 못 끼어든다. 읽기-계산-쓰기가 **한 덩어리**가 된다 |

## Lua 안에 넣은 설계 판단 3가지

**① 시각을 자바가 아니라 Redis에서 — `redis.call('TIME')`**
앱 서버가 여러 대면 시계가 미묘하게 다르다(clock skew). "마지막 충전 시각"을 서로 다른 시계로
기록하면 토큰이 더 생기거나 덜 생긴다. **Redis 시계 하나로 기준 통일.**

**② lazy refill — 배경 스케줄러 없음**
요청이 왔을 때 "지난번 이후 흐른 시간만큼" 몰아서 채운다. 스케줄러 불필요, 안 오는 키는 만료로 소멸.
단 `min(capacity, ...)` 상한이 필수 — 없으면 오래 쉬었다 온 사용자가 **무한 버스트를 쌓는다.**

**③ TTL = "빈 버킷이 가득 차는 시간"**
그보다 오래 안 온 버킷은 **"가득 참"과 구별되지 않으므로** 지워도 결과가 같다. 메모리 청소가 공짜.

## 정책과 응답

| 정책 | 대상 | 키 | 한도 | 이유 |
|---|---|---|---|---|
| `auth` | login·signup·refresh | **IP** | 분당 5회 | 자격 증명을 "맞혀 볼 수 있는" 공격 표면. 사람 손 속도면 충분 |
| `api` | 그 외 `/api/**` | **사용자 id**(비로그인은 IP) | 분당 60회 | 정상 사용은 안 막고 폭주만 거르는 상한 |

키 구조: `rl:{정책}:{user:id|ip:주소}` → 해시 `{tokens, ts}`

**왜 로그인 후엔 IP가 아니라 사용자 id인가**
> "IP로 세면 두 방향으로 다 틀립니다. 회사·학교는 수백 명이 NAT로 IP 하나를 공유해서 남의 사용량에
> 내가 차단되고, 반대로 공격자는 IP를 바꿔가며 회피합니다. 사용자 id 기준이 양쪽을 동시에 해결합니다.
> 로그인 **전** 경로는 신원을 모르니 IP밖에 쓸 게 없고요."

**거부 응답** (RFC 6585):
```
HTTP/1.1 429 Too Many Requests
Retry-After: 12
{"success":false,"data":null,"error":{"code":"COMMON_429","message":"요청이 너무 많습니다..."}}
```
필터 단계라 `@RestControllerAdvice`가 못 잡으므로 공통 봉투 JSON을 필터에서 직접 쓴다.

**필터 순서**: `JwtAuthenticationFilter` → `RateLimitFilter`
사용자 id로 세려면 토큰이 먼저 해석돼야 한다. 대가로 제한 전에 JWT 검증 비용을 치르지만
HMAC 검증은 메모리 연산이라 무시할 수준.

## 트레이드오프 — 내가 먼저 꺼낸다

**fail-open: Redis가 죽으면 전부 통과 + 경고 로그**
> "제한기는 **보조 장치**입니다. 보조 장치의 장애가 서비스 전체 정지로 번지는 건 주객전도라
> 판단해서, 캐시·refresh 토큰과 같은 철학으로 통일했습니다. 대신 정직한 대가가 있습니다 —
> **장애 동안은 무제한**이 되고, 요청마다 Redis 타임아웃 2초를 기다리므로 장애가 길어지면
> 전 API가 2초씩 느려집니다. 개선 후보로 **회로 차단기**를 문서에 적어뒀습니다."

**X-Forwarded-For 신뢰 문제**
> "프록시 없이 직접 노출되면 클라이언트가 헤더를 위조해 IP 제한을 회피할 수 있습니다.
> 실 배포는 '신뢰하는 프록시가 덮어쓴 값만 믿는' 구성이 전제라고 문서에 명시했습니다."

## 꼬리질문

**Q. Bucket4j 같은 라이브러리 두고 왜 직접 만들었나요?** ← 반드시 나온다
> "실무 대규모라면 Bucket4j가 합리적인 선택이라고 생각합니다. 다만 이 프로젝트는 원리 체득이
> 목적이라, '왜 GET/SET 두 번이면 안 되고 Lua여야 하는가'를 직접 겪는 게 라이브러리 설정법을
> 배우는 것보다 남는 게 많다고 판단했습니다. 핵심이 Lua 40줄이라 구현 비용도 작았고요."

**Q. Lua 스크립트가 길어지면요?**
> "Redis는 싱글 스레드라 스크립트가 도는 동안 서버 전체가 멈춥니다. 그래서 스크립트는 짧고
> O(1)이어야 합니다. 저희 것은 HMGET/HSET/PEXPIRE 세 번에 산술 몇 줄이라 안전합니다.
> 반대로 슬라이딩 윈도우 로그였다면 ZSET을 훑어야 해서 이 제약이 부담이 됐을 겁니다."

# 카드 3 — N+1 쿼리 제거 (10방 → 2방)

## 30초 버전

> "문서 목록 API의 태그 로딩이 N+1이었습니다. Hibernate SQL 로그로 요청당 쿼리를 세어
> 문서 9건에 10방이 나가는 걸 확인했고, QueryDSL DTO 프로젝션과 태그 IN 조회 2단계로 바꿔
> **어떤 설정에서도 2방으로 고정**했습니다."

## 어느 조회였나

**`GET /api/documents`** — 문서 목록(9건)과 각 문서의 태그를 함께 내려주는 API.
`Document`와 `Tag`가 다대다이고 `tags`가 LAZY라, 목록을 순회하며 태그를 꺼낼 때마다 쿼리가 나갔다.

## 어떻게 발견했나 ← 정확히 이렇게 답한다

**p6spy나 별도 도구는 안 썼다.** `application.yml`에 이미 켜둔 Hibernate SQL 로그로 셌다.

```yaml
logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace   # 바인딩 파라미터 값까지
```

> "요청 한 번을 보내고 그 구간의 `org.hibernate.SQL` 로그 이벤트 수를 셌습니다.
> 문서 9건일 때 쿼리가 **10개(1 + 9)** 나가는 걸로 N+1을 확인했습니다.
> p6spy를 붙일 수도 있었지만, 쿼리 '개수'를 세는 게 목적이라 기본 로그로 충분했습니다."

**정직한 디테일 하나** — 이걸 말하면 훨씬 신뢰가 간다:
> "사실 처음 켜봤을 땐 쿼리가 2방밖에 안 나갔습니다. `default_batch_fetch_size=100`이 켜져 있어서
> 이미 완화돼 있었거든요. 그래서 **그 설정을 끄고 다시 측정**해서 10방이 나오는 걸 확인했습니다.
> 즉 문제가 '없던' 게 아니라 **설정에 가려져 있었던** 거죠."

## 실측 결과

| 구성 | 쿼리 수 | 비고 |
|---|---|---|
| 개선 전 + `batch_fetch_size` 없음 | **10** (1+9) | N+1의 원형 — 문서마다 태그 쿼리 1방 |
| 개선 전 + `batch_fetch_size=100` | 2 | IN 한 방으로 완화. 단 **설정 지우면 10으로 회귀** |
| **개선 후 (QueryDSL 프로젝션)** | **2 (설정 무관 고정)** | batch를 꺼도 2 — 구조적으로 N+1 불가능 |

## 해결 방법과 고른 이유 ← 핵심 질문

후보가 셋이었고, **셋 다 나름의 이유로 부적합**했다.

| 후보 | 판단 |
|---|---|
| **`default_batch_fetch_size`** (기존 상태) | 이미 켜져 있어 2방이긴 했다. 하지만 **설정 파일 한 줄에 성능이 의존**한다. 누가 지우거나 프로파일이 갈리면 조용히 10방으로 회귀하는 **잠복 구조** |
| **`@EntityGraph` / fetch join** | 컬렉션(`tags`)에 fetch join + 페이징을 걸면 Hibernate가 **전체를 메모리로 가져와 자르는** 함정이 있다(`HHH90003004`). 조인으로 행이 (문서×태그)만큼 불어나 DB가 offset/limit을 못 자르기 때문 |
| **QueryDSL DTO 프로젝션 2단계** ✅ | 채택 |

**채택 이유 3가지**:
1. **구조적 보장** — 설정이 아니라 코드로 2방이 고정된다. `batch_fetch_size`를 지워도 2방.
2. **본문(LONGTEXT) 전송 제거** — 덤으로 잡은 낭비. 아래 참조.
3. **fetch join의 표준 우회보다 단순** — 표준 우회는 "id만 페이징 → IN으로 엔티티 조회" 2단계인데,
   목록은 어차피 DTO로 나가므로 **엔티티를 아예 거치지 않는 프로젝션이 더 싸고 단순**했다.

```java
// ① 목록 페이지: 필요한 5개 컬럼만 DTO로 (content_md는 select에 없음)
List<DocRow> rows = queryFactory
        .select(Projections.constructor(DocRow.class, d.id, d.domain, d.title, d.slug, d.updatedAt))
        .from(d).where(where).orderBy(...).offset(...).limit(...).fetch();

// ② 이 페이지 문서 id들의 태그만 IN 한 방 → 메모리에서 결합
Map<Long, List<String>> tagsByDocId = loadTags(rows.stream().map(DocRow::id).toList());
```

## 덤으로 잡은 낭비 — 이걸 말하면 점수가 오른다

개선 전 SQL을 보니 `select ..., d1_0.content_md, ...` 가 있었다.
**목록 DTO는 본문을 버리는데 DB는 매번 마크다운 본문 전체를 읽어 앱으로 보내고 있었다.**

> "엔티티로 조회하면 필요 없는 컬럼까지 다 읽어옵니다. 목록에는 제목·slug만 필요한데
> LONGTEXT 본문까지 매번 전송되고 있었어요. 프로젝션으로 바꾸니 `content_md`가 SQL에서
> 아예 사라져서, 문서가 수백 KB로 자라도 목록 API는 영향을 안 받게 됐습니다."

→ **N+1은 "쿼리 수" 문제지만, 이건 "쿼리 1방의 무게" 문제**다. 둘을 구분해서 말하면 깊이가 드러난다.

## 부수 개선 2가지

**태그 필터를 join이 아니라 EXISTS로** (`d.tags.any().name.in(...)`)
> "join으로 걸면 태그 수만큼 행이 복제돼서 `distinct`가 필요해지고 페이징 개수 계산도 꼬입니다.
> EXISTS는 행을 안 불려서 그 문제가 없습니다."

**정렬 화이트리스트 + id 보조 정렬**
> "클라이언트가 보낸 정렬 문자열을 그대로 쓰면 없는 컬럼으로 500이 나거나 의도치 않은 컬럼으로
> 정렬됩니다. 허용 목록으로 막고, 마지막에 id를 보조 정렬로 붙여서 **같은 값이 많을 때 페이지를
> 넘길 때마다 행이 겹치거나 빠지는 불안정 정렬**을 방지했습니다."

## 삽질 기록 (물어보면)

> "프로젝션 대상 record를 `private`으로 선언했더니 QueryDSL이 리플렉션으로 생성자를 못 찾아
> `No constructor found`로 500이 났습니다. `Projections.constructor`는 public 생성자만 봅니다."

## 꼬리질문

**Q. `@EntityGraph`는 왜 안 썼나요?**
> "`@EntityGraph`도 결국 fetch join으로 번역돼서 컬렉션 + 페이징의 인메모리 페이징 함정이
> 그대로 있습니다. 그리고 엔티티를 가져오는 방식이라 LONGTEXT 본문 낭비도 못 잡습니다."

**Q. 2방도 결국 쿼리 2번인데 1방으로 못 줄이나요?**
> "1방으로 하려면 join이 필요한데, 그러면 문서 하나가 태그 수만큼 행으로 복제돼서 페이징이
> 깨집니다. **행 복제 없이 페이징을 정확히 하는 대가로 쿼리 1방을 더 쓰는 트레이드오프**를
> 택한 겁니다. 게다가 2방째는 id 목록에 대한 IN 조회라 인덱스를 타서 매우 쌉니다."

**Q. N+1을 애초에 예방하려면?**
> "설정에 기대지 않는 게 핵심이라고 생각합니다. `open-in-view`도 false로 꺼서 지연 로딩 경계를
> 서비스 계층으로 못 박았습니다. 뷰에서 무심코 프록시를 건드려 쿼리가 나가는 걸 원천 차단하려고요."

| `ReviewFlowIntegrationTest` | 3 | `@SpringBootTest` | **MySQL + Redis** |
| `StudyProjectApplicationTests` | 1 | 컨텍스트 로드 | **MySQL + Redis** |
| **합계** | **64** | | |

**DB/Redis는 어디서 오나**: 로컬은 `docker-compose`로 띄운 것, CI는 GitHub Actions **서비스 컨테이너**
(`mysql:8.0`, `redis:7-alpine`). 자격증명·포트를 `docker-compose.yml`과 동일하게 맞춰서
`application.yml` 기본값 그대로 양쪽에서 돈다.

## 왜 H2가 아니라 진짜 MySQL인가 ← 핵심 질문

> "H2는 **다른 DB**입니다. 문법 호환 모드가 있어도 실제로는 다르게 동작합니다.
>
> 구체적으로 저희 프로젝트에서는 세 가지가 걸립니다. 첫째, **Flyway 마이그레이션**을 MySQL 문법으로
> 썼는데 H2에서는 안 도는 구문이 있습니다. 둘째, **FK 제약과 인덱스 동작**이 다릅니다 —
> 인덱스가 FK의 기반 인덱스를 겸하는 InnoDB 특성 같은 건 H2에서 재현이 안 됩니다.
> 셋째, 이 프로젝트의 핵심 학습 주제가 **실행 계획과 인덱스**인데, H2로 테스트하면 정작
> 검증하려는 대상이 사라집니다.
>
> **테스트에서 통과했는데 운영에서 깨지는 게 제일 나쁜 시나리오**라, 테스트 환경을 운영과
> 최대한 같게 맞추는 쪽을 택했습니다. 대가는 테스트가 인프라에 의존한다는 것이고,
> 그래서 CI에 서비스 컨테이너를 붙여 자동화했습니다."

## 어느 범위를 테스트하나

**3층 구조로 나눴고, 경계를 의식적으로 그었다.**

**① 단위 (34개)** — 인프라 없이 항상 돈다
로직 조각만 본다. JWT 발급·검증, 인증 서비스, 복습 간격 계산, LLM 생성 규약.
→ 빠르고, 실패하면 원인이 바로 좁혀진다.

**② 인프라 단위 (4개)** — Redis만 필요
`TokenBucketRateLimiterTest`. **판정 로직이 자바가 아니라 Lua 스크립트 안에 있어서**
자바를 mocking하면 정작 핵심(원자적 판정·충전 계산)을 하나도 검증하지 못한다. 그래서 진짜 Redis에 붙는다.
스프링 컨텍스트 없이 Lettuce 연결만 직접 만들어 부팅 몇 초를 절약했다.

**③ 통합 (18개)** — MySQL + Redis 필요
`@SpringBootTest` + MockMvc로 **실제 HTTP 요청**을 만들어 필터 체인
(`JwtAuthenticationFilter` → 인가 규칙 → 예외 처리기)까지 전부 태운다.
단위 테스트가 못 보는 것: 실제 `Authorization` 헤더 파싱, 경로별 접근 규칙(공개/인증/ADMIN),
인증 실패가 **공통 응답 봉투로 나오는지**, refresh 토큰 1회성(회전)이 Redis 포함해 진짜 지켜지는지.

**❌ 리포지토리 슬라이스 테스트(`@DataJpaTest`)는 없다** — 물어보면 이렇게 답한다:
> "따로 두지 않았습니다. 통합 테스트가 실제 MySQL을 쓰기 때문에 리포지토리도 그 경로로 함께
> 검증됩니다. 다만 QueryDSL 쿼리처럼 **SQL 자체가 관심사인 코드**는 슬라이스 테스트로 따로 보는 게
> 맞다고 생각합니다 — 지금은 쿼리 수를 로그로 수동 확인했는데, 그걸 자동화하는 게 다음 과제입니다."

→ **공백을 인정하되 왜 그런지와 다음 계획까지 말하면** 약점이 아니라 판단으로 보인다.

## 테스트 설계에서 신경 쓴 것 3가지

**① 테스트 격리 — 랜덤 값으로 충돌 차단**
> "이메일은 매번 UUID로 만들고, Redis 버킷 키도 테스트마다 랜덤 UUID입니다.
> DB는 클래스의 `@Transactional`로 롤백되지만 **Redis는 롤백 대상이 아니라서**,
> 값 자체를 안 겹치게 만들고 TTL로 알아서 청소되게 뒀습니다."

**② 인프라 부재를 실패로 보고하지 않는다**
> "`TokenBucketRateLimiterTest`는 Redis가 안 떠 있으면 실패가 아니라 **건너뜁니다**(Assumption).
> 로컬 인프라 부재를 코드 결함처럼 빨간불로 띄우면 **신호가 오염**되거든요. 대신 건너뛴 이유를
> 메시지로 남깁니다."

**③ 각 테스트가 한 가지만 검증하게 경계를 나눴다**
> "`RateLimitFilterTest`는 limiter를 mock으로 두고 필터의 **분기 로직만** 봅니다.
> 버킷 판정 자체는 `TokenBucketRateLimiterTest`가 실제 Redis로 전담하고요.
> 책임을 나눠서 필터 테스트는 Redis 없이도 항상 돌게 했습니다."

## 꼬리질문

**Q. 테스트 커버리지는 얼마인가요?**
> "측정하지 않았습니다. 커버리지 수치를 목표로 잡으면 숫자를 채우는 테스트를 쓰게 돼서,
> 대신 **'이 기능이 깨지면 사용자가 뭘 못 하게 되나'**를 기준으로 골랐습니다.
> 인증 흐름, 요청 제한, 복습 간격 계산처럼 깨지면 치명적인 것부터 덮었습니다."
> (JaCoCo 도입은 솔직히 "안 했다"고 말한다. 안 한 걸 했다고 하면 리포트를 보여달라 할 수 있다.)

**Q. 테스트가 인프라에 의존하면 불편하지 않나요?**
> "불편합니다. 그게 Testcontainers를 검토했던 이유이기도 하고요. 다만 로컬은 docker-compose가
> 항상 떠 있고 CI는 서비스 컨테이너가 자동으로 뜨니까 실제 마찰은 크지 않았습니다.
> 팀 규모가 커져서 '내 PC에선 안 돌아요'가 나오기 시작하면 그때가 Testcontainers 도입 시점이라고 봅니다."

# 카드 5 — CI/CD 파이프라인

## 30초 버전

> "GitHub Actions로 main에 push하거나 PR을 열면 MySQL·Redis 서비스 컨테이너를 띄우고
> 빌드와 테스트 64개를 돌립니다. main에 반영된 코드만 Docker 이미지로 만들어 GHCR에 올립니다.
> **실서버 배포는 안 하고 이미지 저장까지**입니다."

## 실제로 돌아가는가 — 증거가 있다 ← 이게 제일 강력하다

**돈다. 그리고 실패도 잡았다.** 커밋 로그가 증거다.

```
97aa49d fix(db): 누락된 기반 시드(문서1-2·태그1-2) 보충 — 빈 DB에서 V3 FK 위반 수정
1e7ccc3 fix(test): AuthFlowIntegrationTest에서 요청 제한 끄기 — CI에서 429로 오탐
```

**두 버그 모두 로컬에서는 안 보이고 CI에서만 재현됐다.** 이게 CI의 존재 이유를 실증한다.

> "CI를 붙이고 나서 바로 두 가지가 터졌습니다. 둘 다 **제 로컬에서는 절대 안 나던 버그**입니다.
>
> 첫째, **Flyway 마이그레이션이 빈 DB에서 실패**했습니다. 제 로컬 DB에는 개발하면서 쌓인 데이터가
> 이미 있어서 V3 시드가 참조하는 문서·태그가 존재했는데, CI는 **매번 완전히 빈 MySQL**로 시작하니까
> FK 제약 위반이 났습니다. 마이그레이션이 '처음부터 순서대로' 도는 걸 검증받은 셈이라,
> 이건 사실 **잠재적 운영 사고를 미리 잡은 것**입니다.
>
> 둘째, **요청 제한에 제 테스트가 걸렸습니다.** 인증 통합 테스트가 login/signup을 20번 넘게
> 호출하는데 MockMvc는 전부 127.0.0.1이라 같은 IP로 잡혀서 429가 섞여 나왔습니다.
> 로컬에서는 테스트를 하나씩 돌려서 못 봤던 거죠. 그 클래스에서만 요청 제한을 끄고,
> 요청 제한 자체의 검증은 전담 테스트에 맡기는 걸로 정리했습니다."

→ **"CI를 만들었다"보다 "CI가 내가 못 본 걸 잡아줬다"가 훨씬 설득력 있다.**

## 어디까지 자동화했나 — 정직하게 선을 긋는다

```
push/PR → ┌─────────────────────────────────────┐
          │ ① build-and-test                    │  ← 항상 실행
          │   - MySQL 8 + Redis 7 서비스 컨테이너 │
          │   - JDK 21 설치, Gradle 캐시 복원     │
          │   - ./gradlew build (테스트 64개)     │
          │   - 테스트 리포트 업로드 (실패해도)     │
          └──────────────┬──────────────────────┘
                         │ main에 push일 때만
          ┌──────────────▼──────────────────────┐
          │ ② build-and-push-image              │
          │   - Docker 이미지 빌드               │
          │   - GHCR에 push (:latest + :SHA)     │
          └──────────────┬──────────────────────┘
                         ╳
          ┌ ─ ─ ─ ─ ─ ─ ─▼─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
            ③ 실서버 배포 — 안 함
          └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘
```

> "**CI는 완전히 자동화, CD는 이미지 저장까지**입니다. 실제 서버로 내리는 단계는 안 붙였습니다.
> 배포할 서버를 아직 안 정했고, 외부 서비스 가입과 Secrets 관리가 따라붙는데 그건 이 프로젝트의
> 학습 목표(빌드-테스트 자동화)와 별개 주제라고 판단했습니다. 이미지가 GHCR에 있으니
> 배포 대상만 정해지면 `docker pull` 한 줄로 이어붙일 수 있는 상태입니다."

→ 안 한 걸 "안 했다"고 말하되 **왜 안 했는지 + 어디까지 준비됐는지**를 붙이면 미완성이 아니라 판단이 된다.

## 설계 판단들 (물어보면)

**PR에서는 이미지를 안 만든다**
```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```
> "PR 단계에서는 검증만 하고, main에 실제로 반영된 코드만 이미지로 남깁니다.
> 안 그러면 머지도 안 된 코드의 이미지가 창고에 쌓입니다."

**태그를 `:latest`와 커밋 SHA 둘 다 남긴다**
> "`:latest`는 편의용이고, **커밋 SHA 태그는 그 시점 코드를 정확히 가리키는 고정 태그**입니다.
> 문제가 생겼을 때 '어느 커밋의 이미지인지'를 되짚거나 특정 버전으로 롤백하려면 SHA 태그가 필요합니다."

**왜 GHCR인가 (Docker Hub 아니고)**
> "저장소에 딸린 `GITHUB_TOKEN`만으로 push할 수 있어서 별도 계정 가입이나 Secrets 등록 없이
> 비용 0원으로 CD 흐름을 완성할 수 있었습니다. 그 토큰은 실행마다 자동 발급되는 임시 출입증이라
> 유출 위험도 낮습니다."

**테스트 실패해도 리포트를 올린다** (`if: always()`)
> "실패했을 때야말로 리포트가 필요한데, 기본 동작은 실패 시 후속 스텝을 건너뜁니다.
> `if: always()`를 붙여서 Actions 탭에서 바로 원인을 볼 수 있게 했습니다."

**gradlew 권한 문제** (실제 삽질)
> "윈도우에서 만든 `gradlew`는 실행 권한 비트가 없어서 리눅스 러너에서 Permission denied가 났습니다.
> 커밋 자체를 건드리는 대신 CI에서 `chmod +x`를 한 줄 넣어 해결했습니다."

## 도입 전후로 달라진 점

| | 도입 전 | 도입 후 |
|---|---|---|
| 검증 시점 | 내가 기억날 때 로컬에서 | **모든 push/PR마다 자동** |
| 검증 환경 | 내 PC (데이터 쌓인 DB, 한글 경로) | **깨끗한 리눅스 + 빈 DB** |
| 발견한 것 | — | **로컬에선 안 보이던 버그 2건** |
| 결과물 | 내 PC의 jar | GHCR에 커밋별로 남는 이미지 |

> "가장 크게 달라진 건 **'내 PC에서는 되는데'를 구조적으로 없앤 것**입니다.
> 특히 제 로컬은 사용자 경로에 한글이 있고 DB에 개발 데이터가 쌓여 있는 특수 환경이라,
> 깨끗한 환경에서 검증받는 것 자체가 의미가 컸습니다. 실제로 그 차이 때문에 버그 2개가 나왔고요."

## 꼬리질문

**Q. 배포까지 안 했는데 CI/CD라고 할 수 있나요?** ← 나올 수 있다. 물러서지 말 것
> "CD를 '지속적 전달(Delivery)'로 보면 **배포 가능한 산출물을 항상 준비해 두는 것**까지가 범위이고,
> 그 기준으로는 충족합니다. '지속적 배포(Deployment)'까지는 안 했다는 게 정확한 표현이고,
> 그건 배포 대상 인프라가 정해지면 붙일 부분입니다."

**Q. 테스트가 느려지면요?**
> "지금은 서비스 컨테이너 기동 포함 몇 분 수준입니다. Gradle 캐시를 붙여서 의존성은 매번 안 받고요.
> 더 느려지면 단위 테스트와 통합 테스트를 분리해서 PR에서는 단위만, main 머지에서는 전체를
> 돌리는 식으로 나눌 수 있다고 봅니다."

# 카드 6 — QueryDSL

## 30초 버전

> "csquiz에서 씁니다. 다만 **딱 한 곳, 문서 목록 조회에만** 씁니다.
> 동적 필터·프로젝션·페이징이 한꺼번에 필요한 유일한 쿼리라서요. 나머지는 Spring Data JPA와
> `@Query` JPQL로 충분해서 굳이 안 바꿨습니다."

## 어디에 쓰는가 (정확히)

| 파일 | 역할 |
|---|---|
| `document/repository/DocumentRepositoryImpl.java` | **유일한 사용처.** 문서 목록 조회 |
| `global/config/QuerydslConfig.java` | `JPAQueryFactory` 빈 등록 |

나머지 리포지토리 9개는 전부 **Spring Data JPA 메서드 + `@Query` JPQL**이다.

## ⚠️ "한 곳뿐"을 약점으로 만들지 않는 법

면접관이 "그거 한 곳 쓰려고 QueryDSL을 도입했나요?"라고 물을 수 있다. **이렇게 답한다**:

> "네, 한 곳입니다. 그게 의도한 결과입니다.
> QueryDSL이 좋다고 전부 갈아엎으면 단순한 `findByEmail` 같은 것까지 장황해집니다.
> **JPQL로 충분한 곳은 JPQL로 두고**, JPQL로는 감당이 안 되는 한 곳에만 썼습니다.
> 도구를 도입하는 기준은 '좋아서'가 아니라 '이게 없으면 안 풀리는 문제가 있어서'여야 한다고 생각합니다."

→ **일관성 없음이 아니라 절제**로 프레이밍한다. 실제로도 그게 맞는 판단이다.

## 왜 순수 JPQL이 아니라 QueryDSL이었나 ← 핵심 질문

이 쿼리 하나에 **세 가지가 동시에** 필요했다.

**① 동적 조건 — 이게 가장 큰 이유**
문서 목록은 도메인 필터와 태그 필터가 **각각 있을 수도 없을 수도** 있다.

```java
// JPQL로 하면: 문자열을 이어 붙이거나, 이런 트릭을 쓴다
where (:domain is null or d.domain = :domain)
```
> "JPQL은 문자열이라 조건을 붙였다 뗐다 하려면 문자열 연결이나 `:param is null` 트릭을 씁니다.
> 전자는 오타가 런타임에야 터지고, 후자는 **조건이 늘수록 쿼리가 읽기 어려워지고 옵티마이저에도
> 불리**합니다. QueryDSL은 `BooleanBuilder`에 필요한 조건만 담으면 되고,
> **조건이 없으면 SQL에 아예 안 나갑니다.**"

```java
BooleanBuilder where = new BooleanBuilder();
if (domain != null)  where.and(d.domain.eq(domain));
if (tagNames != null && !tagNames.isEmpty())  where.and(d.tags.any().name.in(tagNames));
```

**② 컴파일 타임 타입 안전성**
> "JPQL은 문자열이라 컬럼명 오타나 타입 불일치가 **앱을 띄우고 그 API를 호출해야** 발견됩니다.
> QueryDSL은 엔티티에서 Q클래스를 생성해서 `d.title`처럼 쓰기 때문에 **오타는 컴파일 에러**고
> IDE 자동완성도 됩니다. 엔티티 필드명을 바꾸면 관련 쿼리가 전부 컴파일 단계에서 잡힙니다."

**③ 동적 정렬**
> "`Pageable`의 정렬 조건을 `OrderSpecifier`로 변환해서 화이트리스트로 걸렀습니다.
> JPQL 문자열로는 정렬 컬럼을 안전하게 갈아끼우기가 까다롭습니다."

## 도입 비용도 말한다 (신뢰가 오른다)

> "공짜는 아닙니다. `annotationProcessor`가 엔티티마다 Q클래스를 생성하니까 빌드 시간이 늘고,
> 생성된 클래스가 꼬이면 clean 빌드를 해야 합니다. Spring Boot 3에서는 `:jakarta` 분류자를
> 안 붙이면 javax 기준이라 컴파일이 아예 안 되는 함정도 있었고요.
> 그 비용을 치를 만한 쿼리가 하나뿐이라 딱 하나만 옮긴 겁니다."

```gradle
implementation 'com.querydsl:querydsl-jpa:5.1.0:jakarta'      // :jakarta 필수
annotationProcessor 'com.querydsl:querydsl-apt:5.1.0:jakarta'
```

## 꼬리질문

**Q. Criteria API는요?**
> "동적 쿼리를 타입 안전하게 짤 수 있다는 목적은 같지만 코드가 훨씬 장황하고,
> 완성된 코드만 봐서는 어떤 SQL이 나가는지 읽어내기가 어렵습니다.
> QueryDSL은 **SQL과 코드 모양이 거의 1:1**이라 읽는 사람이 SQL을 바로 떠올릴 수 있습니다."

**Q. Native Query는요?**
> "실제로 쓰는 곳이 있습니다. 대시보드의 문제별 정답률 집계는 네이티브 쿼리입니다 —
> `GROUP BY` 집계가 목적이고 엔티티 매핑이 필요 없어서요.
> 대신 DB 종속이 생기니까, 그런 판단이 필요한 곳에만 씁니다."

**Q. 교회 사이트에서도 쓰나요?**
> (프로젝트마다 사실대로. csquiz 기준으로는 위 내용이 전부다.)

## 다룰 사실 — 이것만 설명하면 된다

- AI가 만든 문제는 **바로 출제되지 않는다.** 별도 초안 테이블에 격리되고, 사람이 승인해야
  정식 문제가 된다.
- **`problem`에 `status` 컬럼을 얹지 않고 표를 나눈 이유**: 얹었다면 기존 모든 조회에
  `WHERE status='APPROVED'`가 번지고, **한 군데만 빠뜨려도 미검수 문제가 사용자에게 나간다.**
  표를 나누면 "검수 안 된 문제는 `problem`에 아예 없는" 구조라 빠뜨릴 곳 자체가 없다.
- **단일 경로 원칙**: 승인은 관리자가 손으로 등록할 때와 **같은 서비스**를 재사용한다.
  직접 저장했다면 slug 중복 검사·태그 생성·캐시 무효화를 다시 구현해야 하고,
  나중에 검색 색인이 추가되면 "AI가 승인한 것만 검색에 안 잡히는" 버그가 된다.
- **구조화 출력**: "JSON으로 줘"라고 부탁하는 게 아니라 스키마를 API에 보내 형식을 강제한다.
  그래서 **파싱 실패 처리 코드가 없다.**
- 형식이 못 막는 **내용 규약**(객관식 정답 정확히 1개 등)은 저장 전 + 승인 시 **두 번** 검증한다.
- **거절 사례 되먹이기**: 검수자가 거절한 지문과 사유를 다음 프롬프트에 넣는다.
  시스템 프롬프트의 금지 규칙이 "일반론"이라면 이건 **우리 검수자의 판례**다.

## 근거 숫자 (외울 것)

- 자동화가 손댈 수 있는 최대 범위 = **"검수 대기함에 종이 한 장 넣기"**
- 문서 1편 생성 비용 **1~2분 / $0.2** (그래서 화면에 생성 버튼을 안 뒀다)
- 검증 규칙은 **실물 2편을 읽고** 도출 — 추측이 아니다

## 꼬리질문 (대비할 것)

# §끝. 전체를 관통하는 무기

면접관이 좋아하는 건 "썼다"가 아니라 **"안 쓴 것과 왜 안 썼는지"** 다.
이 프로젝트는 6개 카드 전부가 그 구조를 갖고 있다.

| 주제 | 채택 | 버린 것 + 이유 |
|---|---|---|
| **인덱스** | `(user_id, is_correct, submitted_at)` | 다른 순서(leftmost prefix 위반) / `ORDER BY RAND()` 개선(과최적화라 **의도적 보류**) |
| **요청 제한** | 토큰 버킷 + Redis + Lua | 고정 윈도우(경계 2배) / 슬라이딩 로그(비용) / 앱 메모리(한도 뻥튀기) / RDB(자충수) / Bucket4j(학습 목적) |
| **N+1** | QueryDSL 프로젝션 2단계 | `batch_fetch_size`(설정 의존) / fetch join(인메모리 페이징 함정) |
| **테스트 DB** | 진짜 MySQL + Redis | H2(다른 DB) / Testcontainers(**검토 후 미도입 — 솔직하게**) |
| **CI/CD** | 빌드·테스트·이미지 저장 | 실서버 배포(**대상 미정, 학습 목표와 별개**) |
| **QueryDSL** | 딱 1곳 | 전면 도입(JPQL로 충분한 곳까지 장황해짐) |

## 최종 점검 (면접 전날)

**사실 관계**
- [ ] **Testcontainers를 "안 쓴다"고 말할 준비가 됐는가** (§0 정정 대본)
- [ ] 실서버 배포는 **안 했다**고 먼저 말하는가
- [ ] 리포지토리 슬라이스 테스트는 **없다**고 인정하는가
- [ ] 이력서·자기소개서에서 ❌ 항목을 다 지웠는가

**숫자 암기**
- [ ] 인덱스: **16ms / 1.8초 / 50만 행 / 5행**
- [ ] N+1: **10방 → 2방** (그리고 "설정 무관 고정"이라는 표현)
- [ ] 테스트: **200개** (2026-08-13 기준. "200개 남짓"으로 말해도 됨)
- [ ] 요청 제한: **auth 5/분, api 60/분**
- [ ] 배치: **06:17 KST 예약 / 실측 48~50분 지연 / 4일 주기 / 분야 8개 → 32일 한 바퀴**

**논리 재현**
- [ ] 인덱스 컬럼 순서 3줄: **선택도 높은 등호 → 등호 → 정렬**
- [ ] 경쟁 상태 4줄 그림(A GET / B GET / A SET / B SET)을 손으로 그릴 수 있는가
- [ ] N+1을 **"쿼리 수"와 "쿼리 1방의 무게"** 두 축으로 나눠 설명할 수 있는가

**태도**
- [ ] "그럼 고쳤나요?" → **"안 고쳤습니다, 과최적화라서"** 를 자신 있게 말하는가
- [ ] "왜 라이브러리 안 썼나요?" → **"실무 대규모면 Bucket4j가 맞습니다, 다만"** 으로 시작하는가
- [ ] 인덱스는 **"개선했다"가 아니라 "설계하고 검증했다"** 로 말하는가
- [ ] QueryDSL 1곳을 **약점이 아니라 절제**로 프레이밍하는가
- [ ] CI는 **"만들었다"가 아니라 "내가 못 본 버그 2개를 잡아줬다"** 로 말하는가
- [ ] 배치 이전은 **"설계가 틀렸다"가 아니라 "설계가 딛고 선 가정이 틀렸다"** 로 말하는가
- [ ] AI 생성은 **"AI가 문제를 만든다"가 아니라 "환각이 사용자에게 닿지 못하게 경계를 뒀다"** 로 시작하는가
- [ ] 스케줄링 버그는 **"내가 스스로 찾아서 고쳤다"** 로 말하는가 (안전장치가 증상을 가리고 있었다는 것까지)
