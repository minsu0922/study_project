# 개념 문서 글쓰기 기준

사용자가 문서를 첨삭하고 조언한 말에서 뽑은 기준이다. 기준마다 근거가 된 말과 날짜를 붙였다.
문서를 새로 쓰거나 고칠 때, 그리고 생성 프롬프트를 손볼 때 이 문서를 먼저 본다.
첨삭을 받을 때마다 여기에 쌓는다. 근거 없이 지어낸 기준은 넣지 않는다.

## 1. 독자와 범위

| 기준 | 근거 |
|---|---|
| 입문편 독자는 배경지식이 전혀 없는 비전공자다. 아는 사람만 알아듣는 말로 시작하지 않는다 | "그렇게 쓰면 너만 알지. 아무 배경지식 없이 패킷에 대해 접하는 사람이 대상인데" (11-08) |
| 심화편 독자는 입문편만 읽고 온 사람이다. 입문편에 없던 전제를 깔지 않는다 | "입문편만 읽은 독자로 가정하고 심화편을 읽어 봤을 때 평가해 줘" (11-08) |
| 한 편은 그 주제의 장치 하나를 깊게 판다. 코스 밖 인프라·제품, 코스 뒤 글의 주제를 끌어오지 않는다 | "과도하게 많은 내용을 전달하려고 한 거 같고 VPN, 클라우드 개념을 같이 넣는 게 맞는지 의문" (11-12) |
| 코스의 글은 앞 글의 개념을 받아 다음 글로 이어져야 한다 | "이 주제들이 연결된 개념으로 이어지고 있는 거 맞아?" (11-11) |
| 주제는 비전공자 기준으로 기초부터 차근차근 오른다 | "비전공자를 기준으로 수준을 더 낮춰서 주제를 선정해 줘" (10-29) |

## 2. 글의 주제

글 맨 앞의 「글의 주제」 상자는 사람이 쓴다(11-12). 모델이 쓴 상자는 한 번에 맞은 적이 없다.

| 기준 | 근거 |
|---|---|
| 말하고자 하는 바가 분명해야 한다. 읽고 나서 "그래서 이 글이 뭘 말하는데"가 남으면 다시 쓴다 | "글의 주제에서 말하고자 하는 바가 더 명확해야 해" (11-11), "넌 이 글을 통해 뭘 말하고 싶었던 거야?" (11-08) |
| 입문편은 일상 장면으로 흥미를 끈다. 심화편은 더 구체적인 장면으로 들어간다 | "입문편 글의 주제는 일상적 소재가 적당하지. 심화편은 조금 더 구체적인 내용을 담는 게 좋지" (11-08) |
| 이 글을 읽으면 무엇을 알게 되는지 쓴다 | "이 글을 읽어서 어떤 내용을 알 수 있는지를 써 줘" (11-08) |
| 상자는 본론 앞, 글 맨 처음에 둔다 | 같은 날 |

지금 쓰는 틀은 아래와 같다. 사용자가 다듬은 서브넷·TCP 편의 모양이다.

- 입문편: 일상 장면 → 개념 이름(굵게)과 한 줄 뜻 → "이 글은 …을 따라간다. 다 읽으면 …할 수 있다."
- 심화편: "입문편에서는 …. 실제 서버에서는 …" → 그 차이로 실제로 벌어지는 사고 → 따라갈 세 갈래나 세 장면

## 3. 문장

| 기준 | 근거 |
|---|---|
| 사람이 이해하기 쉽게 쓴다. 짧게 줄이려다 뜻이 흐려지면 길어져도 확실하게 쓴다 | "갑자기 바깥, 안쪽이 나오는데 그냥 좀 길어져도 되니까 확실하게 설명해 봐" (11-08) |
| 앞에서 소개하지 않은 말을 갑자기 꺼내지 않는다. 대비어(바깥/안쪽 등)도 처음 나올 때 무엇을 가리키는지 밝힌다 | 같은 날 |
| 아무 정보도 없는 꾸밈 문장을 쓰지 않는다 | "'늘 그래 왔으니 신기할 일도 아니다' 라는 문구는 빼고" (11-08) |
| 조건을 "이야기", "것" 같은 명사로 감싸지 않는다. (X) "설명을 시작할 수 없는 이야기라면 벗어난 것이다" (O) "장치와 용어만으로 설명할 수 없으면 벗어났다" | "설명할 수 없으면 처럼 쓰라고" (11-13) |
| 판정을 "그렇다", "이런 경우다"로 흐리지 않는다. 결과를 동사로 바로 쓴다. (X) "도메인 업체가 처리하는 일이면 그렇다" (O) "백엔드 개발자가 직접 다룰 일이 아니면 뺀다" | 판정 질문 다듬기 (11-13) |
| 확인할 길이 없는 기준어를 쓰지 않는다. 읽는 즉시 판정할 수 있는 말로 쓴다. (X) "코스 뒤쪽 글이 따로 다루는 주제인가" (O) "다른 글의 주제에 더 어울리면 뺀다" | "더 구체화하고 간략화할 수 있잖아" (11-13) |
| 같은 일을 하는 기준을 두 번 두지 않는다. 다른 기준이 이미 거르는 것은 뺀다 | "4번은 뭔 검증이야" (11-13) |
| 번역투를 쓰지 않는다. 금지 목록은 전역 CLAUDE.md의 문체 표를 따른다 | "번역투 말투가 많이 나오는 게 느껴져서 수정하고 싶은데" (10-31) |
| 이름은 직관적인 쉬운 말로 짓는다. 어색한 이름은 다른 말로 바꾸거나 없앤다 | "줄이라는 단어를 다른 단어로 바꿀 순 없어?" → "규칙" (11-11), "이 글의 지도라는 명칭을 좀 더 직관적으로" → 절을 없앰 (11-12), "이 글이 답하는 질문이라는 말도 이상하니까 글의 주제라고" (11-08) |
| 결론을 먼저 쓴다. 위험은 비유가 아니라 실제로 벌어지는 일로 쓴다 | "두괄식으로 말하고 장황하게 말하지 마" (09-16) |
| 일상 비유는 한 번 쓰고 버리지 않는다. 글 처음에 세운 비유를 끝까지 끌고 가, 새 개념도 그 비유 안의 자리로 설명한다(NAT 편의 경비실·1203호처럼) | "끝까지 끌고 가는 게 좋고" (11-13) |

## 4. 줄바꿈과 구성

| 기준 | 근거 |
|---|---|
| 내용이 달라지면 줄을 바꾼다. 한 문단에는 이야기 하나만 둔다 | "내용이 달라지면 줄바꿈이 들어가야 해" (11-08) |
| 오해 제목 바로 뒤에 설명을 붙여 쓰지 않는다. 줄을 갈라 보기 쉽게 한다 | "'패킷은 보낸 순서대로 도착한다'라고 하고 바로 이어서 문장이 이어지는데 이러면 보기 힘드니까" (11-08) |
| 심화편의 실패 조건은 장면 ①②③으로 나눠 「어떤 때 통하지 않는가」 아래에 둔다 | "어떤 때 통하지 않는가 아래에 1, 2, 3 사례가 오는 게 자연스럽지 않아?" (11-10) |
| 각 절이 무엇을 말하려는지 분명해야 한다. 절끼리 무엇이 다른지 설명할 수 없으면 합친다 | "여기서는 뭘 말하고 싶은 거야? 이 런타임 밖에서만 만나는 것은 위에서 말하는 내용과 어떤 다른 점이 있는 거야?" (11-08) |
| 심화편도 「용어 한눈에」와 「실무」는 본론 뒤에 둔다 | "용어 한눈에와 실무에서는 이렇게 쓴다 부분을 입문편처럼 뒤에 위치시켜 줘" (11-08) |
| 글 끝에 「참고 자료」를 둔다. RFC·공식 문서만 쓴다 | "참고 자료 절을 추가하면 좋을 거 같아서" (11-10) |

## 5. 강조

| 기준 | 근거 |
|---|---|
| 굵게 하나만 쓰지 않는다. 결론 상자, 오해와 바른 사실, 꼬리표 칩처럼 모양을 나눠 강조한다 | "굵은 글씨로만 표현을 하는데 좀 더 다양한 방식의 강조를 사용해서" (11-08), "볼드, 기울임, 배경색, 색상 등의 시각적인 요소로 가독성을 높이고 싶다" (11-11) |
| 중요한 곳은 글자색을 진하게 한다 | "중요한 부분에는 글자색이 좀 더 진하면 좋겠어" (11-11) |

모양은 문서 화면(`static/document.html`의 `decorateBody`)이 마크다운 꼴을 보고 칠한다.
글쓴이는 정해진 꼴로만 쓰면 된다. 어떤 꼴이 어떤 모양이 되는지는 그 함수가 원본이다.

## 6. 그림

| 기준 | 근거 |
|---|---|
| 그림으로 보면 쉬워지는 자리에는 모두 넣는다. 개수를 제한하지 않는다 | "그림은 왜 1~2개만 넣도록 한 거야? 납득할 이유가 없으면 제한을 두지 않을 거야" (10-30), "그림으로 설명하면 독자가 이해하기 쉽겠다고 생각되는 부분에 모두" (11-08) |
| 단계를 차례로 설명하는 자리에는 그림을 붙인다 | "1단계~4단계까지 설명을 할 때 그림을 넣으면 더 이해하기 쉽지 않을까? 왜 그림을 안 넣었어?" (11-08) |
| 같은 종류만 되풀이하지 않는다 | "그림 스타일이 참 한결같구나? 좀 더 다양한 그림을 섞어서" (11-08) |
| 상자와 화살표보다 장면이 보이는 그림을 쓴다. 지금 가장 좋은 것은 손으로 그린 SVG다 | "막대, 도형, 그래프 말고 다른 직관적인 그림은 못 그려?" (11-09), "손으로 그린 그림 퀄리티가 제일 좋아서" (11-11) |
| 그림과 글자는 크게 그린다 | "그림이 너무 작아서 잘 안 보이네" (11-09), "결과가 너무 작아서 안 보여" (10-25) |

## 7. 문제와 해설

| 기준 | 근거 |
|---|---|
| 기초 지식 없이 해설만 읽어도 정답을 이해할 수 있어야 한다. 규칙 → 구체적인 값으로 한 걸음씩 → "그래서" 정답 | "해설이 불친절하게 느껴져. 기초 지식 없이 해설만 보고 정답을 이해할 수 있을지" (10-25) |
| 코드 문제 해설은 실행 흐름을 실제 값으로 따라간다 | "해설에서 실행 흐름을 실제 예시로 들어 주면서 설명하는 걸 추가해 줘" (10-25) |
| 상황 지문은 있을 법한 실무 장면이다. 정답에서 거꾸로 지어낸 실험 장치를 쓰지 않는다 | "사람은 이해할 수가 없다" (08-18) |
| 문서를 고쳐 근거 문장이 사라진 문제는 지우지 않고 같은 개념을 묻도록 바꿔 쓴다 | 11-12 서브넷 심화편 개편 때 정한 방식 |

## 8. 제목과 주제 문자열

| 기준 | 근거 |
|---|---|
| 문서 제목은 개념을 가리키는 명사구다. 의문문·줄표 부제를 쓰지 않고, 제품 이름은 괄호에 넣는다 | 사용자가 Flyway 문서 제목을 손으로 고침 (09-17) |
| 주제 이름과 메모에는 무엇을 뽑고 싶은지 의도가 드러나야 한다 | "주제의 제목과 메모는 어떤 주제를 뽑고 싶은지 의도가 보여야 하니까" (10-29), "뭘 말하고 싶은지 더 드러나게 표현해 줘" (10-29) |
| 주제 이름은 "개념 — 출발 장면" 꼴이다. 답을 이름에 넣지 않는다 | 09-14 실측(이름에 답이 들어가면 문서가 결론부터 쓴다) |

## 9. 심화편에 넣을 것과 뺄 것

독자는 백엔드 개발자다(분야가 달라도 같다). 항목 하나를 넣을지는 아래 세 질문으로 가린다. 하나라도 걸리면 뺀다.

| 질문 | 이럴 때 뺀다 | 뺀 예 | 넣은 예 |
|---|---|---|---|
| 1. 입문편에서 배운 걸로 설명되나? | 입문편에 나온 말만으로 설명이 안 되면 뺀다 | 서브넷 편의 VPN, TCP 편의 창 크기 조절 옵션 | NAT 편의 "장부 칸이 모자란다" |
| 2. 백엔드 개발자가 하는 일에 맞나? | 백엔드 개발자가 실무에서 직접 다룰 일이 아니면 뺀다 | DNS 캐시 위조 막기, 회사망 포트 차단, DB 디스크 교체 | 연결 시간 제한, 커넥션 풀, 인덱스 추가 |
| 3. 이 글의 이야기인가? | 다른 글의 주제에 더 어울리면 뺀다 | 패킷 편의 NAT, HTTP 메시지 편의 쿠키 | TCP 편의 3-way handshake 실패 |

근거: 11-12 서브넷 심화편 지적과 심화편 일곱 편 점검, 11-13 질문 다듬기("백엔드 개발자로 한정하는 게 좋겠네").

## 10. 실패 사례를 쓰는 꼴

장면 ①②③마다 첫 사례는 이야기로 길게 풀고, 나머지는 꼬리표(`증상`·`원인`·`대처`)로 쓴다.
이야기로 장면을 보여 주고 꼬리표로 문제 재료와 7개 이상 기준을 챙긴다.

| 기준 | 근거 |
|---|---|
| 이야기 순서: 구체적인 상황(누가, 언제, 숫자) → 무슨 일이 벌어졌나 → 왜 그런가 → 비유로 옮기기 → 대처 | 사용자가 고친 NAT 심화편(11-10). "행사 날 결제가 줄줄이 실패하는 이유"가 본보기다 |
| 이야기 사례의 소제목은 "비유 속 장면: 기술 이름" 꼴이다. 예: "이사 간 집을 가리키는 메모: 사설 주소가 바뀐다" | 같은 글 |
| 대처에는 숫자 비교 그림이나 비유 주석을 단 짧은 코드를 붙인다 | 같은 글("퀵 기사를 매번 부르지 말고 단골을 둔다") |
| 장면 소제목 아래 첫 문장은 앞 장면과 잇는다. 예: "장부가 처음 말썽을 부리는 곳은 줄을 적을 칸 자체가 바닥날 때다" | 같은 글 |
| 분량이 늘어도 뜻이 확실한 쪽을 고른다 | 고친 판은 12,069자에서 14,927자가 됐다 |
