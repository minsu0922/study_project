## 고친 것

### 1. 파일 들여오기가 IOException에 롤백하지 않았다

가장 중요한 발견이었습니다. 규칙은 `java:S8989`, 검사 예외에 롤백 여부를 정하라는 지적입니다.

이 프로젝트는 GitHub Actions가 매일 문제 초안을 JSON 파일로 만들고, 앱이 뜰 때 그 파일을 DB로 들여옵니다. 들여온 파일은 이력을 남겨 다음 부팅에 다시 읽지 않습니다.

```java
@Transactional
public int importFile(Path file) throws IOException {
    // 1. 파일을 읽는다
    // 2. 초안을 저장한다
    // 3. AI 검수 지적을 JSON으로 바꿔 초안에 붙인다  ← 여기서 IOException 가능
    // 4. 들여온 이력을 남긴다
}
```

Spring의 `@Transactional`은 기본값으로 런타임 예외에만 롤백합니다. `IOException` 같은 검사 예외는 커밋합니다. 그래서 3번에서 예외가 나면 이렇게 됩니다.

1. 2번에서 저장한 초안은 커밋된다.
2. 4번 이력은 남지 않는다.
3. 다음 부팅에 같은 파일을 다시 들여와 초안이 두 벌이 된다.

코드 주석에는 "예외를 던지면 이력이 남지 않아 다음 부팅에 다시 시도된다(의도된 동작)"라고 적혀 있었습니다. 다시 시도하려면 앞에서 저장한 것까지 되돌려야 하는데, 검사 예외에서는 그렇게 되지 않았습니다.

```java
// IOException은 검사 예외라 기본값으로는 롤백하지 않는다
@Transactional(rollbackFor = IOException.class)
public int importFile(Path file) throws IOException {
```

같은 모양의 메서드 세 곳을 고치고, 세 메서드에 `rollbackFor`가 붙어 있는지 확인하는 테스트를 더했습니다. JSON 변환이 실제로 실패하는 일은 드물어서 그동안 겪지 않았을 뿐입니다.

### 2. 모델이 쓴 코드를 돌리는 job이 쓰기 권한을 쥐고 있었다

규칙은 `githubactions:S8233`, 쓰기 권한을 워크플로 전체가 아니라 job에 주라는 지적입니다.

자바 코드 문제를 만드는 워크플로는 job이 두 개입니다. 첫 job은 모델이 쓴 코드를 실제로 컴파일하고 실행해 정답을 확인합니다. 둘째 job은 깨끗한 러너에서 결과를 커밋합니다. 일부러 나눈 구조인데, 권한은 워크플로 맨 위에 `contents: write`로 한 번에 주고 있었습니다. 모델이 쓴 코드를 돌리는 job도 저장소에 쓸 수 있는 토큰을 받고 있었던 셈입니다.

```yaml
# 기본은 읽기만 준다
permissions:
  contents: read

jobs:
  code-problems:        # 모델이 쓴 코드를 돌리는 job
    ...
  review-and-commit:    # 결과를 커밋하는 job
    permissions:
      contents: write
```

### 3. 같은 클래스 안에서 부른 @Transactional

규칙은 `java:S2229`입니다.

```java
@Transactional(readOnly = true)
public Optional<Course> find(PathKey key, boolean includeUnpublished) { ... }

public Optional<Course> find(PathKey key) {
    return find(key, false);   // 같은 클래스 안의 호출
}
```

Spring의 `@Transactional`은 프록시가 메서드 호출을 가로채서 동작합니다. 같은 클래스 안에서 부르면 프록시를 거치지 않아 안쪽 메서드의 트랜잭션 설정이 적용되지 않습니다.

이 프로젝트는 `open-in-view: false`라 트랜잭션 밖에서 지연 로딩을 건드리면 바로 예외가 납니다. 지금은 `find(key)`를 부르는 곳이 모두 트랜잭션 안이라 터지지 않았습니다. 다만 누군가 트랜잭션 없이 부르는 순간 깨집니다. 바깥 메서드에도 `@Transactional(readOnly = true)`를 붙였습니다.

### 4. 긴 입력에서 스택이 넘칠 수 있는 정규식

규칙은 `java:S5998`입니다. 자바 정규식 엔진은 반복 그룹을 재귀로 처리합니다. 그래서 `(a|b)*` 같은 패턴에 아주 긴 문자열이 들어오면 `StackOverflowError`가 나고 요청은 500으로 끝납니다.

소유 수량자(`*+`, `++`)로 바꿨습니다. 한 번 먹은 글자를 되돌려 보지 않는 수량자라 재귀가 쌓이지 않습니다. 고친 다섯 곳 모두 뒤에 오는 패턴과 겹치는 글자가 없어 결과는 그대로이고 되짚기만 사라집니다.

```java
// 전
"^[a-z0-9]+(-[a-z0-9]+)*$"
// 후
"^[a-z0-9]++(?:-[a-z0-9]++)*+$"
```

### 5. 정리 수준의 지적

| 지적 | 조치 |
|---|---|
| 상수 `CONCEPTS`와 필드 `concepts`가 이름이 같다 (4건) | 상수에 `_LABEL`을 붙였다 |
| 확인문(assert) 없는 테스트 (2건) | "예외가 안 나면 통과"라는 뜻을 `doesNotThrowAnyException()`으로 적었다 |

## 안전으로 표시한 것

### 도구가 맥락을 못 본 경우 (False positive)

| 지적 | 안전한 이유 |
|---|---|
| 요청 값으로 파일 경로를 만든다 (경로 조작) | 요청 경로가 "보낼 파일 목록"에 있을 때만 읽는다. 도구는 이 목록 검사를 따라가지 못했다 |
| null을 참조할 수 있다 | 바로 앞에서 그림 자료인지 확인한다. 그림 자료면 자료 칸이 비어 있을 수 없다 |

두 건 모두 검사 코드가 다른 메서드에 있었습니다. 도구는 한 메서드 안에서 값을 따라가는 데는 강하지만 메서드 사이에 걸친 조건은 놓칠 때가 있습니다.

### 위험 요소는 맞지만 이 프로젝트에서는 문제없는 경우 (Accept)

| 지적 | 건수 | 이 프로젝트에서 괜찮은 이유 |
|---|---|---|
| 누구나 쓸 수 있는 임시 폴더를 쓴다 | 4 | 자바 `Files.createTempFile`은 리눅스에서 본인만 읽고 쓸 수 있는 권한으로 만든다 |
| 문자열을 이어 붙여 SQL을 만든다 | 2 | 이어 붙이는 조각은 코드에 고정된 문자열이고 사용자 값은 바인딩으로 넣는다 |
| 보안에 약한 난수를 쓴다 | 1 | 퀴즈 보기 순서를 섞는 데 쓴다. 보안과 관계없다 |
| CI 설정에 MySQL 비밀번호가 있다 | 1 | 테스트 동안만 떴다 사라지는 컨테이너의 값이다 |
| CSRF 보호를 껐다 | 1 | API는 쿠키가 아니라 Authorization 헤더의 토큰으로 인증한다. 브라우저가 자동으로 붙이는 값이 없어 CSRF가 성립하지 않는다 |
| 정규식이 느려질 수 있다 | 14 | 입력이 관리자 입력이나 모델 출력이라 길이에 한도가 있다. 고치다가 검증 규칙이 바뀔 위험이 더 크다 |

마지막 14건은 고민이 가장 길었습니다. 앞의 "스택이 넘칠 수 있는 정규식"은 요청이 500으로 죽는 문제라 고쳤습니다. 이쪽은 "아주 긴 입력에서 느려진다"는 지적이고, 대부분 문서 검증 규칙에 쓰는 정규식입니다. 그 규칙을 건드리면 지금까지 통과하던 문서가 떨어질 수 있어 이번에는 두기로 했습니다.

## 돌아보며

41건 가운데 고친 것은 16건이고 실제 결함은 그중 두 건이었습니다. 하나는 파일 들여오기 롤백이고 하나는 워크플로 권한입니다. 두 건 모두 AI와 함께 짜고 검토하는 동안에는 드러나지 않았습니다. 같은 모델로 짜고 검토하면 같은 곳을 놓친다는 1편의 걱정이 근거 없는 걱정은 아니었습니다.

반대로 25건은 도구가 틀렸거나 이 프로젝트에서는 문제가 없었습니다. 정적 분석 결과를 그대로 다 고치면 안 되는 이유입니다. 지적마다 실제 입력과 호출 경로를 따라가 봐야 판단할 수 있었습니다. 판단한 이유는 메모로 남겨 다음 사람이 같은 고민을 되풀이하지 않게 했습니다.

다음 단계는 품질 기준을 넘지 못하면 CI를 막도록 바꾸는 일입니다. 기존 지적을 모두 정리했으니, 이제부터는 새 코드에서 나오는 지적만 막으면 됩니다.
